# 自动化 AI 产出工厂需求与概要设计

## 1. 文档定位

本文定义一个以需求为起点、能够自动完成分析、设计、任务拆分、代码修改、实际测试、独立门禁、缺陷修复、总结沉淀和审计追踪的 AI 产出工厂。

- 系统暂定建设目录：`已退役本地驱动应用`
- 当前工程：SELPLAT
- 当前稳定用户：`XUNAN`
- 主要参考：`OPTION/AI开发工厂_需求与概要设计.md`
- 边界参考：`OPTION/架构脑与执行脑边界规范.md`
- 组织参考：`OPTION/AI软件工厂_Agent组织架构与职责规范.md`
- 异常参考：`OPTION/异常处理.md`
- 沉淀参考：`OPTION/AI软件工厂_知识库与经验沉淀体系规范.md`
- 辅助参考：现有规则引擎的授权、线程隔离、规则加载、门禁、测试登记和审计思想
- 设计性质：重新设计，不以迁移、重建或替代原规则引擎为目标

本文只负责需求和概要设计；数据库只定义逻辑实体和职责，不进入物理 DDL、字段类型、索引或类与方法实现细节。

## 2. 项目名称

AI 需求驱动自动开发与门禁治理工厂，简称“AI 产出工厂”。

## 3. 建设目标

用户通过一个需求会话提交目标后，系统围绕同一个 ThreadID 自动完成：

1. 需求理解和需求文档生成。
2. 概要设计和详细设计生成。
3. 可执行任务拆分和依赖排序。
4. 隔离工作空间与需求分支创建。
5. 程序、配置、文档或其他目标产物生成。
6. 使用实际数据执行单元、集成和场景测试。
7. 由独立 Gate 对产物和过程实施硬性门禁。
8. 对失败进行诊断、修复、重测和重新门禁。
9. 生成发布说明、复盘报告和规则优化提案。
10. 通过 ThreadID 还原全部 Agent、文档、命令、变更、测试和审批过程。

最终目标不是“让 AI 写一次代码”，而是建立一条可重复、可控制、可审计、可持续改进的自动化生产线。

## 4. 核心原则

1. 需求驱动：任何执行都必须关联根任务、明确需求和验收标准；需求是整条流水线的业务起点。
2. 规则先行：每个阶段开始前必须加载并冻结适用中文核心规则，执行脑只能依据本阶段规则快照和 Architecture Package 工作。
3. 文件必验：只要产生或修改文件，就必须按文件类型执行对应验收 Gate；需求、设计、代码、配置、SQL、PPT、测试、日志和发布文件只有验收通过后才能进入下一阶段。
4. 根任务串联阶段线程：一个需求建立一个根任务和初始 ThreadID；需求、设计、执行、测试、Gate 等阶段由不同角色在独立阶段线程中完成，通过根任务 ID、父子线程关系和标准文件名串联。
5. 一需求一工作空间：不同需求不得共享未受控运行状态。
6. 一需求一分支：代码变更通过需求级 Git 分支隔离。
7. Rule 负责指导：规则告诉 Agent 应该怎样工作，只保留不超过 30 条中文核心原则。
8. Gate 负责执法：门禁独立验证产物是否满足文件类型验收标准并允许流转。
9. 测试与门禁分离：测试通过不等于 Gate 通过；Gate 必须验收同一产物版本。
10. 设计先行：没有达到精度要求且未通过设计文件 Gate 的详细设计不得进入执行。
11. 真实结果：测试必须记录实际输入、实际命令、实际结果和证据。
12. 失败闭环：失败必须进入诊断、修复、重测和复盘链路。
13. 规则受控演进：Rule Evolution Agent 只能生成一句话规则修正建议和正式变更提案，审核后才能生效。
14. 审计先于状态变更：关键写操作没有审计能力时必须阻断。
15. 人工可接管：高风险、歧义、越权和循环超限必须暂停并请求人工决策。
16. 禁止仅通过堆叠 Prompt 提高质量：稳定约束进入 Rule，可机械判断的错误进入 Gate。
17. 一个角色一个逻辑 Agent：每个 Agent 只承担一个职责领域，不得跨越生产、门禁、修复和进化边界。
18. 问题在哪层产生就在哪层修复：实现、设计、架构和流程问题分别路由到对应修复角色，修复后必须回到原 Gate 复验。
19. 要件定义承上启下：需求整理通过后必须形成可编号、可验收、可追踪的正式要件；要件 Gate 通过后才能进入架构设计。

## 5. 范围与非范围

### 5.1 本期范围

1. 单一需求会话驱动完整开发链路。
2. 多 Agent 分工、交接、并行和汇总。
3. 五个治理入口及其规则、索引和模板。
4. 需求级工作空间、ThreadID 和 Git 分支。
5. 需求、设计、任务、测试、Gate、审计、复盘和发布文档。
6. 自动测试、独立门禁和受限自动修复。
7. 全链追踪、失败恢复和规则优化提案。
8. 面向程序源码，也支持配置、文档、PPT、数据和其他交付物。

### 5.2 本期非范围

1. 不迁移或删除原规则引擎。
2. 不把原规则引擎目录和分层直接复制到新工厂。
3. 不允许 Rule Evolution Agent 无审核修改生产规则。
4. 不允许 AI 自动批准高风险发布、删除或外部生产变更。
5. 不在本阶段确定具体编程语言、框架、类和方法。
6. 不承诺所有需求在无人干预下必然完成。
7. 不把聊天记录作为唯一权威需求源。

## 6. 五个 AGENTS 治理入口

五个 AGENTS 指五个业务治理入口，不表示系统只有五个运行时 Agent。

1. `AGENTS_AI产出工厂总入口.md`
2. `需求文档/AGENTS_需求文档入口.md`
3. `设计文档/AGENTS_设计文档入口.md`
4. `测试文档/AGENTS_测试文档入口.md`
5. `审计日志/AGENTS_审计日志入口.md`

### 6.1 总入口

负责接收需求、建立 Thread、创建工作空间、识别主流程、加载唯一根索引、协调专业 Agent、执行阶段转换和处理人工接管。

### 6.2 需求文档入口

只负责需求分析、需求澄清、范围、非范围、约束、验收条件和概要设计。禁止写方法级详细设计、实现代码或伪造测试结论。

### 6.3 设计文档入口

负责架构、详细设计、任务拆分、实现范围和执行合同。架构及详细设计分别通过 Gate 后，Development Agent 才能在授权范围内生成或修改目标产物。

### 6.4 测试文档入口

负责测试设计、真实数据执行、结果回写和 Gate 评估。Gate 可以调用测试证据，但 Gate 的职责和结果必须独立。

### 6.5 审计日志入口

负责审计事件规范、追加写、脱敏、查询、校验、归档和多 Agent 因果链。它不替代需求、设计、测试或 Gate 文档。

### 6.6 启动发现

现有工具通常只自动识别标准 `AGENTS.md`。新工厂必须由 SELPLAT 根 `AGENTS.md` 或专用启动器显式路由到 `AGENTS_AI产出工厂总入口.md`，再由唯一根索引进入四个分入口，禁止扫描目录猜测入口。

## 7. 运行时专业 Agent

### 7.1 角色与 Agent 一一对应

1. 一个业务角色对应一个逻辑 Agent 身份和一个 `role_id`。
2. 一个 Agent 只负责一个职责领域，不得同时作为生产者、同层 Gate 和修复者。
3. 同一底层模型可以承载多个 Agent，但每个 Agent 必须使用不同 `agent_id`、角色版本、上下文、权限、阶段运行和审计链。
4. Agent 不得在一次运行中切换角色；需要其他职责时由工作流创建新的阶段运行。
5. 所有产出必须由对应门禁 Agent 检查，门禁 Agent 不能修改被检查产物。

### 7.2 生产体系 Agent

| Agent | 中文角色 | 主要职责 | 关键输出 |
| --- | --- | --- | --- |
| Requirement Agent | 需求分析师 | 整理和补全需求、范围及验收标准 | `requirement.md` |
| Requirements Definition Agent | 要件定义师 | 把已确认需求转为业务、系统、功能、非功能、数据、接口和验收要件 | `requirements-definition.md` |
| Architecture Agent | 解决方案架构师 | 总体架构、模块划分、技术方案和风险分析 | `architecture.md`、`architecture.pptx` |
| Design Agent | 系统设计师 | 详细设计、接口、数据结构、文件和方法定位 | `design.md`、`design.pptx` |
| Development Agent | 开发工程师 | 按 Architecture Package 编码、重构和实现 | 源码、配置、`execution.md` |
| Test Agent | 验证工程师 | 单元、集成、边界、异常测试和覆盖率 | `test_result.md`、测试证据 |

生产 Agent 只负责创造本层产物，不得检查并批准自己的产物，也不得修正规则、Gate 或流程。

### 7.3 门禁体系 Agent

| Agent | 中文角色 | 检查内容 | 关键输出 |
| --- | --- | --- | --- |
| Requirement Gate Agent | 需求评审官 | 需求明确性、范围和验收条件 | `requirement_gate.md` |
| Requirements Definition Gate Agent | 要件评审官 | 要件完整性、一致性、可测试性、唯一 ID 和追踪关系 | `requirements-definition_gate.md` |
| Architecture Gate Agent | 架构评审官 | 架构完整性、技术合理性和风险 | `architecture_gate.md` |
| Design Gate Agent | 设计评审官 | 文件、方法、接口和数据结构定位 | `design_gate.md` |
| Code Gate Agent | 代码评审官 | 编码规范、安全、范围和设计一致性 | `code_gate.md` |
| Test Gate Agent | 测试评审官 | 测试通过率、覆盖率、边界和异常测试 | `test_gate.md` |
| Quality Gate Agent | 质量总审官 | 文档、审计、流程和全部前置 Gate | `quality_gate.md`、PASS/FAIL |

每个门禁 Agent 是对应 Gate Definition 的独立 Runner。Quality Gate 只能汇总和裁决，不能替代缺失的前置 Gate，也不能直接生成“已发布”事实。

### 7.4 修复体系 Agent

| Agent | 修复对象 | 典型问题 |
| --- | --- | --- |
| Requirement Fix Agent | 需求文档 | 范围、验收条件或需求表述缺陷 |
| Requirements Definition Fix Agent | 要件定义文档 | 要件遗漏、冲突、不可测试或追踪缺失 |
| Architecture Fix Agent | 架构文档 | 技术路线、模块划分和架构风险缺陷 |
| Design Fix Agent | 详细设计 | 设计遗漏、接口和数据结构问题 |
| Code Fix Agent | 源码和配置 | Bug、编译失败、SQL 或测试失败 |
| Test Fix Agent | 测试资产 | 测试设计、数据、环境或证据缺陷 |
| Rule Fix Agent | Rule Library 提案 | 规则失效、冲突和重复 |
| Gate Fix Agent | Gate Library 提案 | 门禁漏检、误检和逻辑错误 |
| Process Fix Agent | Process Library 提案 | 流程缺陷、职责冲突和审批链问题 |

修复 Agent 只能修改其负责对象；修复后必须重新执行受影响测试并返回失败的原 Gate，不得更换 Gate 或降低标准绕过失败。

### 7.5 进化体系 Agent

| Agent | 主要职责 | 关键输出 |
| --- | --- | --- |
| Quality Monitor Agent | 识别覆盖率下降、Bug 增长、重复问题和发布失败趋势 | 质量趋势事件 |
| Retrospective Agent | 根因分析、任务结论和失败复盘 | `retrospective.md` |
| Rule Evolution Agent | 新增、合并或删除失效规则的提案 | `rule_update.md` |
| Gate Evolution Agent | 新增、强化或优化 Gate Definition 的提案 | `gate_update.md` |
| Process Improvement Agent | 优化流程、生命周期和组织职责的提案 | `process_update.md` |

进化 Agent 只生成提案。规则、Gate 和流程的新版本必须经影响分析、独立 Gate 和审批后发布，并默认从后续根任务生效。

### 7.6 支撑体系 Agent

| Agent | 主要职责 | 禁止事项 |
| --- | --- | --- |
| Intake Agent | 接收需求、创建根任务和识别风险 | 擅自设计或实现 |
| Planning Agent | 拆分任务、依赖和执行顺序 | 修改生产产物 |
| Process Agent | 解析已批准流程版本并生成阶段实例 | 自行改变流程定义 |
| Workspace Agent | 创建隔离工作空间和 Git 分支 | 合并或发布 |
| Diagnosis Agent | 依据证据分类问题并选择修复路由 | 直接修改产物 |
| Review Agent | 审查实现与 Architecture Package 一致性 | 代替 Gate 或修复 |
| Audit Agent | 写入、校验和查询审计事件 | 人工改写历史 |
| Release Agent | 在 Quality Gate PASS 后生成发布说明和交付包 | 自行批准、合并或发布 |

## 8. 架构脑与执行脑边界

### 8.1 双脑定位

AI 产出工厂采用架构脑、执行脑和独立控制面三方分离：

| 分区 | 核心问题 | 主要职责 | 禁止事项 |
| --- | --- | --- | --- |
| 架构脑（Architecture Brain） | 做什么、为什么做、应该如何做 | 需求、设计、规则提案、Gate 定义、流程和 Agent 职责 | 修改业务代码、提交代码、执行发布 |
| 执行脑（Execution Brain） | 如何按批准合同完成并验证 | 修改代码、执行测试、修复实现缺陷、生成执行和 Review 报告 | 重定义需求、修改设计、规则、Gate 或流程 |
| 独立控制面（Control Plane） | 当前动作是否被允许、产物是否合格 | 状态机、权限、Gate 执行、审计完整性、人工审批和流程阻断 | 直接修复被检查产物、为自己放行 |

架构脑与执行脑不能通过共享未声明内存隐式交接，必须使用已版本化、可审计的正式文档和结构化合同。

### 8.2 架构脑输入与输出

架构脑输入：

- 用户需求和已确认补充材料。
- 测试总结、失败证据和 Review 结论。
- Gate 失败记录和违规代码。
- 原始事实日志、当前任务复盘以及已批准的 Rule、Gate、Process 版本；不读取独立经验库或知识库。
- 当前规则快照、工程约束和风险策略。

架构脑输出：

- `requirement.md`
- `requirements-definition.md`
- `architecture.md` 与 `architecture.pptx`
- `design.md` 与 `design.pptx`
- `rule-context.md` 或 `rules-proposal.md`
- `gate-plan.md`
- `process.md`
- `architecture-package.yaml`

架构脑可以创建或修改草稿规则、Gate 定义、流程和 Agent 职责，但生产生效仍需经过影响分析、独立 Gate 和规定审批；禁止把“架构脑拥有定义权”解释为可以静默修改生产规则。

### 8.3 执行脑输入与输出

执行脑只能接收已批准并冻结版本的：

- `requirement.md`
- `requirements-definition.md` 与要件 Gate 结果。
- `architecture.md` 与架构 Gate 结果。
- `design.md` 与对应 PPT 对象引用。
- `rule-context.md`
- `gate-plan.md`
- `process.md`
- `tasks.yaml`
- `architecture-package.yaml`

执行脑输出：

- 代码、配置、文档或其他批准产物变更。
- `execution.md`
- `test.md`
- `fix.md`
- `review.md`
- `changes.md`

执行脑发现需求、设计、规则、Gate 或流程有误时，不得自行修改上游合同；必须生成 `architecture-change-request.md`，附带问题、证据、影响和建议，随后进入 BLOCKED 并交回架构脑。

### 8.4 架构执行包

每次进入执行阶段前，架构脑必须发布不可变的 Architecture Package，至少记录：

1. ThreadID、任务 ID 和包版本。
2. 需求、要件定义、架构、详细设计、PPT、规则快照、Gate 计划、流程和任务清单的版本及摘要。
3. 允许修改的文件、目录、对象和操作类型。
4. 禁止修改的对象和外部副作用。
5. 必需测试、Gate、覆盖率和验收条件。
6. 风险级别、人工审批点、修复次数和预算上限。
7. 发布者、批准者、发布时间和审计事件 ID。

Development Agent 只能针对当前有效包执行。Architecture Package 发生变化后，未完成执行必须重新评估；旧测试和 Gate 结果自动失效。

### 8.5 问题归属

| 类别 | 示例 | 首要归属 | 处理方式 |
| --- | --- | --- | --- |
| A 类：实现问题 | 代码报错、SQL 错误、测试失败、接口实现异常 | 执行脑 | Diagnosis 后由 Code/Test Fix Agent 在批准范围修复 |
| B 类：设计问题 | 设计遗漏、边界缺失、接口定义错误、模块划分不合理 | 架构脑 | 执行脑提交变更请求，架构脑修订并重新批准 Architecture Package |
| C 类：架构问题 | 服务拆分、技术路线、模块边界或架构风险错误 | 架构脑 | Architecture Fix Agent 修订架构并重新经过架构 Gate |
| D 类：流程问题 | 同类问题重复、Rule 失效、Gate 漏检、Agent 职责或审批链冲突 | 架构脑与控制面 | Process Improvement 流程生成规则、Gate 或流程提案，独立验证并审批后生效 |

无法确定类别时进入 BLOCKED，由 Diagnosis Agent 请求架构脑分类，禁止执行脑在不确定状态下扩大修改范围。

### 8.6 重复问题升级

对具有相同问题指纹的失败采用三级升级：

1. 第一次：按实际 A/B/C 类路由到对应修复 Agent。
2. 第二次：继续按层修复，同时强制记录事实日志、无效尝试，并生成当前任务复盘输入。
3. 第三次：视为 D 类潜在流程缺陷，停止自动修复并启动 Process Improvement，检查是否需要新增或调整 Rule、Gate、流程和 Agent 职责。

问题指纹必须基于违规代码、受影响对象、根因类别和关键证据生成，不能仅凭错误文本相似就合并计数。人工可以提前升级；高风险问题第一次出现即可直接进入架构脑。

问题处理同时保留两个正交分类：`failure_domain` 使用 A 实现、B 设计、C 架构、D 流程决定由谁修复；`improvement_target` 使用 NONE、RULE、GATE、PROCESS 决定复盘后形成哪类治理提案。禁止把“设计问题”和“规则缺陷”混为同一个分类维度。

### 8.7 Rule 与 Gate 分工

1. Rule 由架构脑定义，告诉 Agent 应该怎样做。
2. Gate Definition 由架构脑定义，说明如何机械验证 Rule 和阶段合同。
3. Gate Runner 位于独立控制面，针对固定产物快照执行 Gate。
4. Gate Runner 只能返回 PASS、FAIL、违规和证据，不能修改受检产物。
5. 执行脑根据失败证据修复实现，但不能修改 Gate 让自己通过。

示例：

- Rule：设计必须指定文件、方法和验收标准。
- Gate Definition：检查设计对象是否同时存在文件、方法和验收标准。
- Gate Runner：对指定设计版本执行检查并输出结果。

### 8.8 文档归属

| 归属 | 文档 |
| --- | --- |
| 架构脑 | `requirement.md`、`requirements-definition.md`、`architecture.md`、`architecture.pptx`、`design.md`、`design.pptx`、`rule-context.md`、`rules-proposal.md`、`gate-plan.md`、`process.md`、`architecture-package.yaml` |
| 执行脑 | `execution.md`、`changes.md`、`test.md`、`fix.md`、`review.md` |
| 独立控制面 | Gate 执行记录、状态转换、审批记录和原始审计账本 |
| 共同提供事实、指定角色汇总 | `audit.md`、`retrospective.md`、`release.md` |

共享文档必须指定唯一汇总角色；“双方共享”不表示双方可以无锁覆盖同一文件。

### 8.9 Agent 归属

- 架构脑：Requirement Agent、Requirements Definition Agent、Architecture Agent、Design Agent、Planning Agent、Rule Evolution Agent、Gate Evolution Agent、Process Improvement Agent。
- 执行脑：Development Agent、Test Agent，以及 Requirement/Requirements Definition/Architecture/Design/Code/Test Fix Agent。
- 独立控制面：Requirement/Requirements Definition/Architecture/Design/Code/Test/Quality Gate Agent、Workflow Controller、Approval Controller、Audit Agent。
- 诊断与进化：Diagnosis Agent 只分类和路由；Quality Monitor 与 Retrospective Agent 只产出事实趋势和复盘分析。
- Release Agent：汇总架构、执行和控制面结果，但发布动作受独立审批。

### 8.10 决策矩阵

| 决策或动作 | 负责方 | 必需约束 |
| --- | --- | --- |
| 接收和解释用户需求 | 架构脑 | 重大歧义请求用户确认 |
| 编写需求、要件定义、架构和详细设计 | 架构脑 | 各层先过对应 Gate，再形成版本化 Architecture Package |
| 拆分任务 | 架构脑 | 每项任务绑定设计对象和验收条件 |
| 修改业务代码或目标产物 | 执行脑 | 仅限 Architecture Package 授权范围 |
| 执行测试和生成测试报告 | 执行脑 | 使用固定产物版本和实际证据 |
| 定义 Rule、Gate 和流程 | 架构脑 | 变更提案需审核和独立验证 |
| 执行 Gate | 独立控制面 | 不得修改受检产物 |
| 修复实现缺陷 | 执行脑 | 不得借修复改上游合同 |
| 修复设计或架构缺陷 | 对应 Fix Agent | 返回原 Design/Architecture Gate，重新发布包并使旧验证失效 |
| 修复 Rule、Gate 或流程缺陷 | 对应进化/修复 Agent | 只生成提案，经委员会、Gate 和审批发布新版本 |
| 记录原始审计事件 | 独立控制面 | 双脑都只能提交事件，不得改历史 |
| 发布审批 | 人工或授权审批控制器 | Release Agent 不能自批 |

### 8.11 越权门禁

以下行为必须被 Gate 阻断：

1. 架构脑直接修改、提交或发布业务代码。
2. 执行脑修改需求、设计、规则、Gate 定义、流程或 Agent 职责。
3. Development Agent 使用过期 Architecture Package。
4. Gate 定义者直接修改 Gate 结果。
5. Gate Runner 修改被检查产物。
6. 双脑绕过正式文档通过隐式上下文改变执行合同。
7. 共享文档缺少唯一汇总者或发生无锁并发覆盖。

## 9. 主生产流程

```text
用户需求
  → Intake
  → 创建根任务、初始 ThreadID 和数据库记录
  → 加载需求阶段规则快照
  → Requirement Agent
  → Requirement Gate Agent
  → 需求确认
  → 创建要件定义阶段 Thread
  → 加载要件定义阶段规则快照
  → Requirements Definition Agent
  → Requirements Definition Gate Agent
  → 要件确认
  → 创建架构阶段 Thread
  → 加载架构阶段规则快照
  → Architecture Agent
  → Architecture Gate Agent
  → 架构确认
  → 创建详细设计阶段 Thread
  → 加载设计阶段规则快照
  → Design Agent
  → Design Gate Agent
  → 设计确认
  → Planning
  → Workspace
  → 创建执行阶段 Thread
  → 加载执行阶段规则快照
  → Development Agent
  → Code Gate Agent
  → Test Agent
  → Test Gate Agent
  → Quality Gate Agent
  ├─ PASS → Release Agent → Retrospective Agent → RELEASED
  └─ FAIL → Diagnosis Agent → 对应 Fix Agent → 受影响测试 → 原失败 Gate
                                      └─ 超限/高风险 → 人工接管
```

质量监控与系统进化是旁路治理流程：

```text
事实日志 / Quality Monitor / Retrospective
  → Root Cause Analysis
  → 选择 improvement_target：NONE / RULE / GATE / PROCESS
  → Rule Evolution / Gate Evolution / Process Improvement
  → 改进提案
  → 流程改进委员会或授权审批者
  → 独立 Gate 验证
  → 发布新的 Rule / Gate / Process 版本
```

进化流程不建立独立经验库或知识库，不得在当前需求执行中静默改变其 Rule、Gate 或 Process 快照。

## 10. 状态模型

### 10.1 主状态

```text
NEW
→ REQUIREMENT_PRODUCING
→ REQUIREMENT_GATING
→ REQUIREMENT_READY
→ REQUIREMENTS_DEFINITION_PRODUCING
→ REQUIREMENTS_DEFINITION_GATING
→ REQUIREMENTS_DEFINITION_READY
→ ARCHITECTURE_PRODUCING
→ ARCHITECTURE_GATING
→ ARCHITECTURE_READY
→ DESIGN_PRODUCING
→ DESIGN_GATING
→ DESIGN_READY
→ IMPLEMENTING
→ CODE_GATING
→ TESTING
→ TEST_GATING
→ QUALITY_CHECKING
→ RELEASING
→ RELEASED
```

失败分支：

```text
任一 Gate FAIL
→ FAILED
→ CLASSIFYING
→ CORRECTING
→ RETESTING
→ REGATE_CHECKING（必须返回原 Gate）
→ 原流程下一状态或再次 FAILED
```

人工分支：

```text
任意状态
→ BLOCKED
→ WAITING_FOR_HUMAN
→ 原状态或 CANCELLED
```

### 10.2 里程碑标记

保留参考设计中的里程碑语义，但不与主状态混用：

- `tested=true`：当前产物快照的必需测试均通过。
- `gate_approved=true`：独立 Gate 对同一产物快照判定 PASS。
- `done=true`：测试、Gate、审计和交付条件全部满足。

产物发生变化后，相关 `tested` 和 `gate_approved` 必须失效并重新计算。

### 10.3 状态转换要求

每次转换必须记录：来源状态、目标状态、根任务 ID、初始 ThreadID、阶段 ThreadID、产物版本、触发事件、执行者、时间、规则回执、Gate 结果和审计事件 ID。禁止口头声明或跳过中间状态。

## 11. 根任务、阶段 Thread、工作空间与分支

### 11.1 根任务与初始 ThreadID

1. 用户第一次提交需求时立即创建根任务，并保存 `task_id` 和 `root_thread_id`。
2. `root_thread_id` 使用最初需求会话 ThreadID，贯穿需求全生命周期，不因角色、阶段、重试、修复或页面切换而改变。
3. 根任务是数据库中的权威串联对象；所有阶段、文档、Agent、测试、Gate、错误和审计都必须引用同一 `task_id`。
4. `root_thread_id` 是跨系统关联键和文件名组成部分，但不能代替数据库主键。
5. ThreadID 不包含敏感业务正文。

### 11.2 阶段 ThreadID

1. 需求文档、详细设计、执行、测试、Gate、修复等阶段由不同角色负责，每次实际执行使用独立 `stage_thread_id`。
2. 每个阶段线程保存 `root_thread_id`、`parent_stage_thread_id`、角色、阶段、尝试次数和负责 Agent。
3. 需求 Gate PASS 后才能创建要件定义阶段线程；要件 Gate PASS 后才能创建架构阶段线程；架构 Gate PASS 后才能创建详细设计阶段线程；详细设计 Gate PASS 后才能创建执行阶段线程。
4. 阶段线程只拥有当前阶段权限，禁止继承上一角色的写权限。
5. 重试和修复创建新的运行记录；是否复用阶段线程由详细设计确定，但必须保留父子关系和全部历史。

### 11.3 工作空间命名

```text
<中文需求名称>_<初始ThreadID>
```

示例：

```text
用户导入功能_10001
```

中文名称必须经过文件名安全化；初始 ThreadID 负责唯一性。显示名称可以改变，根任务 ID、初始 ThreadID 和工作空间标识不得改变。

### 11.4 标准文件命名

所有正式文件使用“文档类型 + 中文需求名称 + 初始 ThreadID”命名：

```text
<文档类型>_<中文需求名称>_<初始ThreadID>.<扩展名>
```

示例：

```text
需求文档_用户导入功能_10001.md
要件定义文档_用户导入功能_10001.md
架构设计文档_用户导入功能_10001.md
架构设计图_用户导入功能_10001.pptx
详细设计文档_用户导入功能_10001.md
详细设计图_用户导入功能_10001.pptx
测试文档_用户导入功能_10001.md
Gate验收_用户导入功能_10001.md
审计日志_用户导入功能_10001.md
```

文件名用于人工识别、目录验收和跨阶段引用；数据库 `artifact` 记录才是路径、版本、摘要和状态的权威来源。文件改名必须通过工厂能力同步数据库和引用，禁止只改文件名。

### 11.5 Git 分支

```text
feature/thread-<初始ThreadID>
```

每个需求使用独立分支。分支创建、提交、推送、合并和关闭必须是不同权限动作；创建工作空间不等于授权推送或合并。

### 11.6 运行目录

`已退役本地驱动应用` 保存工厂程序、入口、规则、索引、模板和 Schema。需求运行时工作空间、调试日志、临时证据和导出件遵循工程运行数据规则，进入工程 `OPTION/temp` 下的专属工厂目录。长期审计账本和发布归档位置需要在详细设计前确定。

## 13. 文档精度要求

### 13.1 需求文档

只包含背景、问题、目标、范围、非范围、角色、场景、约束、验收条件、概要流程、组件边界、数据边界、风险和开放问题。不得提前写具体方法实现。

### 13.2 要件定义

要件定义把已确认的自然语言需求转成可设计、可测试、可验收和可追踪的正式合同，不负责选择具体模块实现或编写方法设计。

要件定义文档至少包含：

1. 业务目标、成功指标、范围和非范围。
2. 利益相关者、用户角色、权限和业务责任。
3. 现状流程、目标流程、业务规则和例外流程。
4. 功能要件及输入、输出、前置条件、后置条件和异常结果。
5. 非功能要件：性能、容量、可用性、安全、审计、可维护性、可移植性和可观测性。
6. 数据要件：数据来源、字段语义、质量、保留、隐私、迁移和归档。
7. 外部接口要件：对接系统、协议、身份、时序、错误和兼容约束。
8. 运维要件：部署环境、监控、告警、备份、恢复和支持边界。
9. 迁移、切换、回滚、依赖、假设和已知限制。
10. 验收要件、验证方式、优先级、风险和未决事项。

每条正式要件必须具有稳定 `REQ-<范围>-<序号>`、类型、来源需求引用、描述、理由、优先级、状态、验收标准、验证方式和追踪关系。状态至少包括 `draft`、`reviewed`、`approved`、`superseded` 和 `rejected`；未批准要件不得进入 Architecture Package。

要件定义必须建立：原始需求 → 正式要件 → 架构对象 → 详细设计对象 → 任务 → 测试 → Gate 的双向追踪。文件名只能辅助识别，数据库追踪记录是权威来源。

### 13.3 架构设计

架构设计负责总体结构，不进入方法实现，至少明确系统边界、模块划分、组件职责、技术方案、数据与调用方向、部署关系、关键质量属性、风险和取舍。架构文档和 PPT 必须使用稳定架构对象 ID，并通过 Architecture Gate 后才能进入详细设计。

### 13.4 详细设计文档

有程序方法的对象必须精确到方法，至少包含：

1. 文件和类或模块路径。
2. 方法名称和方法作用。
3. 参数及真实传参示例。
4. 返回及真实返回示例。
5. 异常或副作用示例。
6. 状态变化和调用关系。
7. 对应需求 ID 和测试 ID。

没有程序方法的对象必须精确到真实内容：配置精确到键和值域，数据精确到字段和约束，流程精确到节点和失败分支，规则精确到逻辑 ID 和声明，界面和文档精确到实际区域、章节或内容。

### 13.5 PPT

总体架构、模块和部署视图进入 `architecture.pptx`；详细流程、时序、状态和无方法对象进入 `design.pptx`。Markdown 与同阶段 PPT 必须使用相同对象 ID；对应 Architecture/Design Gate 必须检查引用一致，禁止 PPT 成为无法追踪的孤立材料。

## 14. 功能需求

### FR-001 需求会话

用户通过一个会话提交需求。系统建立 Thread 和工作空间，生成初始 `metadata.yaml`，并把聊天内容整理为正式 `requirement.md`。

### FR-002 需求分析

Requirement Agent 必须识别目标、范围、非范围、约束、依赖、风险、验收条件和开放问题。影响实现方向的歧义必须阻断并请求确认。

### FR-003 要件定义

Requirements Definition Agent 必须把已确认需求转换为带稳定 ID、优先级、状态、验收标准和验证方式的正式要件，建立原始需求到要件的来源关系。Requirements Definition Gate PASS 后才能进入架构生成。

### FR-004 架构生成

Architecture Agent 基于已确认需求生成 `architecture.md` 和 `architecture.pptx`，明确系统边界、模块、技术方案、数据与调用方向、风险和取舍。Architecture Gate PASS 后才能进入详细设计。

### FR-005 详细设计生成

Design Agent 基于已通过 Gate 的架构生成 `design.md` 和 `design.pptx`。未达到方法级或内容级精度，或 Design Gate 未通过时，不得进入任务拆分。

### FR-006 任务拆分

Planning Agent 把设计拆成稳定任务 ID，例如 `TASK-001`、`TASK-002`。每项必须有输入、输出、依赖、涉及对象、验证责任和完成条件。

### FR-007 工作空间管理

Workspace Agent 按需求创建隔离工作空间和 `feature/thread-<ThreadID>` 分支，记录基线提交、目标工程和工作区状态。

### FR-008 自动执行

Development Agent 只允许修改设计和任务清单明确登记的对象。发现必须修改设计外文件时，先更新影响分析并回到设计确认，不得静默扩大范围。

### FR-009 自动测试

Test Agent 负责单元测试、集成测试、场景测试、必要的端到端测试和覆盖率统计。测试必须使用受控实际数据，并保存可复现命令和证据。

### FR-010 独立门禁

每个生产阶段对应独立门禁 Agent，统一输出 PASS 或 FAIL。任一必需 Gate 为 FAIL 时禁止进入下一生产阶段；Quality Gate 不得替代缺失的需求、架构、设计、代码或测试 Gate。

### FR-011 自动诊断与修复

测试或 Gate 失败后，由 Diagnosis Agent 按 A/B/C/D 分类，再路由到对应 Fix Agent。修复后必须重跑受影响测试并返回原失败 Gate。

### FR-012 修复循环控制

每个失败必须拥有稳定问题 ID。系统记录尝试次数、实际修改和结果；达到配置的次数、时间、成本或风险上限后转人工接管，禁止无限循环。

### FR-013 复盘

任务成功、失败、取消或人工接管后都生成 `retrospective.md`，记录基于日志事实的根因、有效修复、无效尝试和改进提案。复盘是当前任务产物，不汇总成独立经验库或知识库。

### FR-014 规则优化

Rule Evolution Agent 根据事实日志和复盘，把稳定结论转为 `rules-proposal.md`。规则提案必须经过重复检查、影响分析、测试和人工审核后才能进入规则库。

### FR-015 发布交付

Release Agent 仅在测试通过、Gate PASS、审计完整、无未决高风险项时生成 `release.md`。生成发布说明不等于自动合并或生产发布授权。

### FR-016 查询

系统支持通过根任务 ID 或初始 ThreadID 查询 Requirement、Requirements Definition、Architecture、Design、Task、Change、Test、各层 Gate、Audit、Branch、Retrospective 和 Release。

### FR-017 中断恢复

进程中断后必须从持久状态和审计事件恢复，识别已完成动作、待执行动作和不确定动作。具有外部副作用的不确定动作不得盲目重放。

### FR-018 多 Agent 协作

系统允许无依赖任务并行；存在依赖或写冲突的任务必须串行。父 Agent 负责汇总，不得把子 Agent 口头结论当作已验证结果。

### FR-019 双脑隔离

系统必须把架构脑、执行脑和独立控制面的权限、输入和输出分离。架构脑不得修改业务代码，执行脑不得修改需求、设计、Rule、Gate Definition 和 Process，Gate Runner 不得修改受检产物。

### FR-020 架构执行包

进入执行前必须生成版本化 `architecture-package.yaml`。执行脑只能使用当前批准包；包版本变化后必须重新确认任务影响，并使相关旧测试和 Gate 结果失效。

### FR-021 架构变更请求

执行脑发现上游合同错误或缺失时必须生成 `architecture-change-request.md` 并暂停相关任务。架构脑完成修订、评审和重新发布后才能恢复执行。

### FR-022 根任务与阶段数据库

系统必须在开始生成需求文档前创建根任务、初始 ThreadID、需求阶段和负责角色记录。后续每个阶段建立独立阶段 Thread 和运行记录，由数据库工作流状态串联整套生产流程。

### FR-023 角色登记与 Codex 启动

角色定义在 AGENTS 文件中，数据库保存角色路径、版本、摘要、权限和状态。Python Worker 根据当前阶段的固定角色版本加载 AGENTS、规则快照和 Architecture Package 后启动 Codex。

### FR-024 文件级验收

任何生成或修改的文件必须登记文件类型、中文标准文件名、路径、版本和摘要，并执行对应文件类型 Gate。全部文件 Gate 和阶段 Gate 通过后才允许创建下一阶段。

### FR-025 实时进度页面

SelUI 页面必须实时展示根任务、流水线阶段、负责角色、阶段 Thread、Agent、心跳、当前动作、文件、测试、Gate、错误和阻断状态；页面刷新后能够从数据库恢复并继续订阅事件。

### FR-026 Python 错误与复盘

Python Worker 必须记录结构化错误事实和脱敏堆栈。Retrospective Agent 基于错误事实生成代码修正依据和一句话中文规则修正建议，为 Fix 和进化体系提供证据；原始错误日志不得记录推测、不得直接改变生产规则。

### FR-027 治理资产收敛

系统不建设全局 Experience Library、Knowledge Base、Case Library、Memory Library 或 Knowledge Wiki。长期治理资产只保留 Log Library、Rule Library、Gate Library 和 Process Library；任务复盘和改进提案按任务归档，不形成第五类全局知识资产。

## 15. Rule Library

### 15.1 定位

Rule 是 Agent 的指导合同，描述应该做什么、适用范围、依赖、优先级和冲突处理。Rule 不承担最终执法结果。

### 15.2 分类

- Requirement Rules
- Requirements Definition Rules
- Architecture Rules
- Design Rules
- Planning Rules
- Coding Rules
- Documentation Rules
- Testing Rules
- Security Rules
- Release Rules
- Audit Rules
- Gate Rules

### 15.3 规模治理

Rule Library 只保留中文书写的核心原则，生产有效规则硬上限为 30 条。

1. 每条 Rule 只表达一个稳定核心原则，正文、业务注释和人类可读名称使用中文。
2. Rule 只回答“应该怎样做”，不得塞入大量可机械判断的检查细节。
3. 可机械判断的文件格式、字段、路径、数量、覆盖率和状态条件进入 Gate Library。
4. 新增第 31 条 Rule 前必须先合并近义规则、删除失效规则或把检查项提升为 Gate；未完成治理时阻断新增。
5. 错误日志可以生成一句话中文规则修正建议，但该建议不是正式 Rule，必须经过影响分析、验收 Gate 和人工审核。
6. 每个阶段只加载适用规则子集和固定版本快照，执行中途不得静默切换规则。

### 15.4 规则命名和索引

- 规则：`RUL_<中文主题>规则.md`
- 索引：`IDX_<中文范围>索引.md`
- 根索引：`IDX_AI产出工厂总索引.md`

所有规则使用稳定逻辑 ID，由唯一根索引递归加载。禁止扫描目录猜测规则；重复 ID、依赖循环、失效路径和作用域冲突必须阻断。

### 15.5 规则变更

规则变更必须记录来源事件、问题证据、适用范围、影响分析、替代关系、验证结果和审批人。当前任务使用固定规则快照，处理中途批准的新规则默认从后续任务生效。

## 16. Gate Library

### 16.1 定位

Gate 是独立执法能力，接收确定输入并返回 PASS 或 FAIL、违规代码、证据和修复建议。Gate 数量不设业务上限，但必须有唯一 ID、责任范围、执行成本和适用阶段。

### 16.2 基础 Gate

| Gate | 检查内容 |
| --- | --- |
| `G001` | 需求完整性与验收条件 |
| `G002` | 要件完整性、一致性、可测试性、唯一 ID 和追踪关系 |
| `G003` | 架构完整性、技术方案合理性和风险分析 |
| `G004` | 详细设计精度、需求/要件/架构追踪和 PPT 一致性 |
| `G005` | 实际变更是否超出批准设计和任务范围 |
| `G006` | 必需测试是否执行且通过 |
| `G007` | 覆盖率是否达到模块策略 |
| `G008` | 审计事件是否完整、连续、可校验 |
| `G009` | 安全扫描和敏感信息检查 |
| `G010` | 规则、索引、路径和依赖合法性 |
| `G011` | 发布材料、已知限制和回滚信息完整性 |
| `G012` | Thread、工作空间、分支和产物版本一致性 |
| `G013` | 架构脑、执行脑和控制面是否存在越权操作 |
| `G014` | Architecture Package 是否获批、未过期且与执行产物版本一致 |
| `G015` | 重复问题升级、架构变更请求和原 Gate 复验闭环是否完整 |

### 16.3 文件类型验收

任何新增、修改、移动或生成的文件都必须拥有明确 `artifact_type` 和对应验收标准。没有登记文件类型或没有可执行验收标准时，文件 Gate 直接 FAIL。

| 文件类型 | 最小验收标准 |
| --- | --- |
| 需求文档 | 目标、范围、非范围、约束、验收条件、风险、初始 ThreadID 和根任务引用完整 |
| 要件定义文档 | 每条要件有稳定 ID、类型、来源、优先级、状态、验收标准、验证方式且不存在未解决冲突 |
| 架构设计 Markdown | 系统边界、模块划分、技术方案、数据与调用方向、风险和取舍完整 |
| 详细设计 Markdown | 代码对象精确到方法和真实示例；无方法对象存在内容级合同；全部对象关联需求 ID |
| PPT | 页面可打开、对象 ID 与设计文档一致、无截断重叠、视觉复核完成 |
| 程序源码 | 位于正确语言目录、只改批准范围、可编译或解释、专项测试和编码 Gate 通过 |
| 配置文件 | Schema、必填键、值域、环境边界、敏感字段和默认值合法 |
| SQL | 语法、参数化、事务、影响范围、回滚或幂等策略及数据库隔离符合要求 |
| 测试文档 | 实际数据、命令、预期、实际结果、证据、状态和产物摘要齐全 |
| Gate 报告 | Gate ID、版本、输入摘要、PASS/FAIL、违规代码和证据完整 |
| 审计日志 | 事件连续、哈希可校验、敏感信息违规为零、根任务和阶段 Thread 可追踪 |
| 错误事实日志 | 错误 ID、上下文、输入输出摘要、异常、脱敏堆栈、退出码和关联证据完整，不含推测 |
| 复盘报告 | 引用事实日志，包含根因、A/B/C/D 分类、代码修正依据和 RULE/GATE/PROCESS 改进目标 |
| 改进提案 | 引用复盘和事实证据，包含一句话中文变更结论、影响分析、验证和审批状态 |
| 发布说明 | 交付范围、版本、测试、Gate、已知限制、回滚和审批信息完整 |

文件 Gate 必须检查当前文件摘要；文件内容变化后旧验收结果立即失效。一个阶段包含多个文件时，每个文件先通过类型 Gate，随后再通过阶段聚合 Gate。

### 16.4 门禁约束

1. Gate Agent 不得修改被检查产物。
2. Gate 必须检查确定的产物版本和摘要。
3. 产物变化后旧 Gate 结果自动失效。
4. Gate 自身失败、超时或缺少证据时按 FAIL 处理，不得默认为 PASS。
5. Gate 规则变化必须版本化，结果记录 Gate 版本。
6. Gate Definition 与 Gate Runner 必须分离；同一实现承担两者时必须使用不同权限和独立运行上下文。
7. 检测到双脑越权时必须阻断，不允许通过事后补文档修复审计事实。

## 17. 测试策略

### 17.1 覆盖率基线

- 普通模块：不低于 85%。
- 核心模块：不低于 95%。
- 新增代码：不低于 90%。

覆盖率是 Gate 之一，不代替行为、异常、安全和集成验证。无法适用覆盖率的非代码产物必须定义等价结果型验证。

### 17.2 测试合同

每项测试至少包含：测试 ID、需求 ID、要件 ID、架构对象 ID、设计 ID、前置条件、实际数据来源与脱敏、环境、执行命令、预期结果、实际结果、证据、执行者、时间和状态。

### 17.3 数据安全

真实数据必须在隔离、可恢复环境使用。禁止把敏感生产数据、密钥或连接串写入标准产物和审计日志。测试结束后按策略清理或归档证据。

## 18. 自动修复闭环

1. 任一 Gate FAIL 后生成稳定失败 ID、事实日志和证据。
2. Diagnosis Agent 判断 A 实现、B 设计、C 架构或 D 流程问题，并选择对应修复 Agent。
3. A 类进入 Code/Test Fix；B 类进入 Design Fix；C 类进入 Architecture Fix；D 类进入 Process Improvement。
4. 修复 Agent 生成最小修正计划，只修改本层负责对象；超出本层时重新分类和路由。
5. 修复后运行受影响测试，并返回最初失败的同一 Gate ID 和 Gate Definition 版本复验。
6. 原 Gate 通过后才能恢复正常流程；禁止改用其他 Gate、降低标准或由 Quality Gate 覆盖失败。
7. 相同失败重复出现时不得重复同一无效修复；第三次触发 D 类流程改进。
8. 达到循环上限、预算上限或风险阈值时进入人工接管。

## 19. 审计机制

### 19.1 审计内容

所有关键操作至少记录：时间、稳定用户、Agent、父 Agent、ThreadID、任务、动作、目标对象、修改文件、命令摘要、规则回执、测试结果、Gate 结果、状态转换和失败原因。

### 19.2 原始账本与可读文档

1. 原始审计事实采用 append-only JSONL，一事件一行。
2. `audit.md` 是按 ThreadID 生成的可读派生视图。
3. 查询索引和数据库可重建，不替代原始账本。
4. 历史事件禁止直接修改；纠错通过追加替代事件完成。

### 19.3 完整性

事件包含唯一 ID、前一事件哈希和当前事件哈希。按日或按任务生成 manifest，记录首尾哈希、事件数和账本摘要。普通本地存储只能做到篡改可检测；需要不可抵赖时再引入外部签名或 WORM 存储。

### 19.4 敏感信息

审计使用字段白名单。令牌、密码、Cookie、Authorization、私钥、完整环境变量、数据库连接串和用户敏感正文不得落账；只记录脱敏值、摘要或受控证据引用。

### 19.5 写入失败

产生状态变化的操作必须先写 attempted 事件。attempted 写入失败时，目标写操作 fail-closed；审计器自身故障走独立应急记录，恢复后追加 recovery 事件。

## 20. 治理资产与经验沉淀

### 20.1 长期资产边界

系统不建设传统 Experience Library 或 Knowledge Base。长期治理资产只保留：

1. Log Library：保存不可变事实。
2. Rule Library：保存不超过 30 条中文核心方法原则。
3. Gate Library：保存可执行检查定义和版本。
4. Process Library：保存工作流、角色职责、状态转换和审批版本。

`已退役本地驱动应用` 是应用工程名，不代表建立 Memory Library。禁止新增全局 Experience Library、Case Library、Memory Library、Knowledge Wiki 或其他需要 Agent 全量阅读的经验堆积层。

### 20.2 Log Library 只记录事实

日志只记录实际发生的内容：谁在何时、在哪个根任务和阶段 Thread、使用哪个角色和版本、接收什么输入摘要、执行什么动作、产生什么输出、返回什么结果、出现什么异常和证据在哪里。

日志禁止记录：

- 未经分析验证的根因猜测。
- “应该新增规则”等治理结论。
- 没有证据的经验判断。
- 密钥、令牌、连接串和敏感原文。

事实更正只能追加纠正事件，不能覆盖原日志。

### 20.3 根因分析与改进目标

```text
Log Library 事实
  → Root Cause Analysis
  → failure_domain：A实现 / B设计 / C架构 / D流程
  → improvement_target：NONE / RULE / GATE / PROCESS
  → 当前任务 retrospective.md
  → 必要时生成改进提案
```

不是每个错误都必须修改 Rule、Gate 或 Process。单次实现错误修复完成且没有稳定治理价值时，`improvement_target=NONE`。

### 20.4 改进提案

- Rule 提案：一句话中文核心原则、适用范围、现有规则关系和不超过 30 条的容量影响。
- Gate 提案：可机械判断的输入、算法、PASS/FAIL、违规代码、证据和成本。
- Process 提案：阶段、角色、权限、状态转换、修复路由和审批变化。

提案必须引用事实日志和复盘，不得把日志原文直接复制成规则。提案完成影响分析、独立 Gate 和审批后发布新版本；未批准提案只按任务归档，不进入长期有效 Library。

### 20.5 质量趋势与流程改进

Quality Monitor Agent 只基于事实指标识别覆盖率下降、Bug 增长、重复问题和发布失败率变化。D 类问题交由流程改进委员会或授权审批组处理：根因分析 → 改进提案 → Rule/Gate/Process 验证 → 发布新流程版本。新版本默认不回写正在执行任务的冻结快照。

## 21. 人工审批与权限边界

以下节点默认需要显式人工确认或已配置的可信审批策略：

1. 需求范围和验收条件确认。
2. 高风险或跨系统详细设计确认。
3. 删除、迁移、大范围覆盖和生产数据操作。
4. 推送远程分支、创建 PR、合并和生产发布。
5. 规则库生产变更。
6. 审计账本导出、归档、删除和保留策略变化。
7. 自动修复超限后的继续执行。

Agent 权限采用最小授权。读取、修改、执行命令、提交、推送、合并和发布是不同权限，不得因取得其中一项推断拥有其他权限。

## 22. 并发、幂等与恢复

1. 同一根任务的状态转换串行化；无依赖阶段也必须由工作流定义明确允许后才能并行。
2. 不同根任务的工作空间、分支、锁和审计分区隔离；同一根任务的不同阶段线程按权限隔离。
3. 每个外部动作使用稳定幂等键。
4. 批量文档更新要求一次锁和一次原子写。
5. Agent 并行前检查任务依赖和文件写集合；重叠写集合必须串行或由单一所有者合并。
6. 中断恢复以持久状态、产物摘要和审计事件为依据，不以 Agent 内存为依据。
7. 无法判断外部动作是否成功时进入人工核对，不得自动重复高风险动作。

## 23. 时间、成本和资源控制

参考设计提出普通需求处理时间不超过 30 分钟。该指标作为目标服务等级，而不是牺牲质量的硬截止：

1. Intake 阶段评估需求规模和预计耗时。
2. 超过普通需求规模时拆分里程碑或请求确认。
3. 每个 Agent 记录耗时、模型、工具和资源使用量。
4. 修复循环受次数、总耗时、令牌或费用预算约束。
5. 超预算时保留已完成产物和恢复点，进入人工决策。
6. 不允许为满足 30 分钟目标跳过测试、Gate 或审计。

## 25. 数据库、服务与实时进度架构

### 25.1 技术选型建议

推荐采用“Java 管理面 + Python 执行面 + SelUI 页面”的混合架构：

| 层 | 推荐技术 | 职责 |
| --- | --- | --- |
| 页面 | SelUI 原生 JavaScript/CSS | 任务列表、流水线、阶段、角色、文件、测试、Gate、错误和日志展示 |
| 管理面 | Java Spring Boot，接入 SELPLAT Host | API、鉴权、数据库事务、工作流状态机、角色登记、任务调度、SSE 实时推送 |
| 数据层 | Java 公共数据库层；MVP 可复用 H2 | 根任务、阶段、角色、运行、产物、Gate、错误、进度和审计摘要 |
| 执行面 | Python Worker | 读取 AGENTS 定义、启动 Codex、文件生成与修改、测试、修复、心跳和错误采集 |
| AI 执行器 | Codex | 在角色权限和 Architecture Package 范围内完成阶段任务 |

选择依据：

1. SELPLAT 已有统一 Java Host、Spring Web、公共数据库层和 H2/MyBatis 基础，可以直接承载长期运行的管理面。
2. SelUI 已由公共模块发布为 `/sel/**`，与业务后端语言无关，但现有标准开发方式由 Java Host 统一提供 8080 端口。
3. Python 已有规则能力和 HTTP 原型，适合文件、文档、测试及 Codex 进程编排；当前依赖中没有成熟 Python Web/ORM 框架，不适合作为企业管理面的默认基础。
4. Java 与 Python 同时直写同一数据库会形成双写、锁、事务和状态竞争，因此数据库必须有唯一写入者。

推荐方案中 Java 是数据库唯一写入者。Python 不直接修改业务表，而是通过受控 API 上报领取任务、心跳、进度、产物、错误和完成事件，由 Java 在一个事务内校验状态并持久化。

### 25.2 Python 直管数据库备选方案

如果首期明确限定为单机、单用户、快速 MVP，也可以采用 Python 服务作为数据库唯一写入者并直接提供 JSON/SSE API，Java Host 只发布 SelUI 静态资源或进行反向代理。

该方案必须满足：

1. Java 不得同时写 AI 工厂业务表。
2. Python 服务负责完整事务、锁、迁移、恢复、鉴权和状态机。
3. SelUI 只能通过 Python API 访问业务数据，禁止浏览器直连数据库。
4. 从 Python 管理面迁移到 Java 管理面时需要额外接口和数据迁移成本。

综合现有 SELPLAT 架构、长期可维护性和实时页面需求，本文选择 Java 管理面方案，Python 保持执行面。

### 25.3 数据库逻辑实体

| 逻辑表 | 主要职责 | 关键关联 |
| --- | --- | --- |
| `ai_role` | 角色名称、脑区、职责、权限、AGENTS 路径和当前有效版本 | 关联角色版本和阶段定义 |
| `ai_role_version` | 固定某次角色定义内容摘要、状态和生效时间 | 阶段运行必须引用固定版本 |

| `ai_requirement_item` | 正式要件 ID、类型、来源、描述、理由、优先级、状态、验收标准和验证方式 | 归属根任务和要件定义版本 |
| `ai_trace_link` | 原始需求、要件、架构、设计、任务、产物、测试和 Gate 的有向追踪关系 | 支持双向影响查询 |
| `ai_workflow_definition` | 流程版本、阶段顺序、允许转换、人工节点和失败分支 | 根任务创建时冻结版本 |
| `ai_workflow_stage_definition` | 阶段类型、顺序、负责角色、输入、输出、规则集和 Gate 集 | 创建任务阶段实例 |
| `ai_task_stage` | 某根任务的阶段实例、负责角色、状态、当前运行和前后依赖 | 归属根任务 |
| `ai_stage_run` | 一次实际角色执行，保存阶段 ThreadID、Agent、尝试、心跳、开始结束和结果 | 归属任务阶段 |
| `ai_artifact` | 文件类型、中文标准文件名、相对路径、版本、摘要、生产阶段和验收状态 | 关联阶段运行和 Gate 结果 |
| `ai_rule_version` | 已批准中文核心 Rule、版本、适用范围、替代关系和生效状态 | Rule Library 权威元数据 |
| `ai_rule_snapshot` | 当前阶段不超过 30 条中文核心规则的固定版本和摘要 | 关联阶段运行 |
| `ai_gate_definition_version` | 已批准 Gate 输入、算法、违规代码、适用阶段和版本 | Gate Library 权威元数据 |
| `ai_gate_result` | 文件或阶段 Gate 的版本、输入摘要、PASS/FAIL、违规和证据 | 关联产物或阶段运行 |
| `ai_process_version` | 已批准流程、角色、状态转换、修复路由和审批版本 | Process Library 权威元数据 |
| `ai_progress_event` | 可顺序消费的进度事件、百分比、消息和时间 | 页面实时推送来源 |
| `ai_error_log` | Python/Codex/命令/测试/Gate 的不可变错误事实，不保存根因猜测和治理建议 | 关联阶段运行和证据 |
| `ai_retrospective` | 基于事实日志形成的根因、A/B/C/D 分类、修正依据和改进目标 | 关联根任务、错误和失败 Gate |
| `ai_improvement_proposal` | RULE、GATE、PROCESS 改进提案、影响、验证、审批和发布状态 | 关联复盘和目标 Library 版本 |
| `ai_quality_metric` | 覆盖率、Bug、重复问题、Gate 失败和发布结果等事实指标 | Quality Monitor 趋势输入 |
| `ai_audit_event` | 状态变化、权限、命令、文件、审批和关键事实摘要 | 关联根任务和阶段运行 |
| `ai_approval` | 需求、设计、规则、发布和高风险操作的审批决定 | 关联产物版本或状态转换 |

详细设计必须补充主键、唯一键、外键、状态枚举、乐观锁版本、查询索引、归档和删除策略。

### 25.4 任务与阶段创建

1. 用户开始生成需求文档时，Java 管理面先创建 `ai_task`，保存初始 ThreadID、中文标题、工程、工作空间和工作流版本。
2. Java 创建需求阶段 `ai_task_stage`，绑定 Requirement Agent 的固定角色版本。
3. Python Worker 领取阶段运行，Java 创建 `ai_stage_run` 和独立阶段 ThreadID。
4. Python 加载角色 AGENTS、阶段规则快照和 Architecture Package 后启动 Codex。
5. Codex 产出文件后，Python 上报相对路径、摘要和文件类型，Java 创建或更新 `ai_artifact`。
6. 要件定义阶段必须解析并登记 `ai_requirement_item` 和来源追踪；存在重复 ID、冲突、无验收标准或无验证方式时 Gate FAIL。
7. 文件类型 Gate PASS 后，Java 才把阶段置为完成并创建下一阶段。
8. 要件定义、架构、详细设计、执行、测试和各层 Gate 均重复上述流程，各自使用新的阶段线程和负责角色。

### 25.5 角色创建与 Codex 启动

1. 角色权威定义写在五个治理 AGENTS 文件之一，以稳定 `role_id` 和中文角色章节登记；默认不为每个运行时角色增加第六个及以后的 AGENTS 文件。
2. 数据库不复制完整 Prompt，只保存角色 ID、所属 AGENTS 相对路径、章节锚点、版本、摘要、权限和启用状态。
3. 新建或修改角色定义后必须通过 AGENTS 文件 Gate，再登记新的 `ai_role_version`。
4. 工作流阶段只引用已批准角色版本，运行中途角色定义改变不影响当前运行。
5. Python Worker 根据阶段记录解析角色章节、适用规则、输入产物和允许工具，组合为 Codex 执行上下文。
6. Python 启动 Codex 后立即上报进程标识和心跳；退出时上报退出码、产物、错误和实际结果。
7. Codex 不直接更新工作流状态，只有 Java 管理面可以根据事件和 Gate 结果转换状态。

### 25.6 实时进度

1. Python Worker 在领取、加载规则、启动 Codex、生成文件、运行测试、执行修复和结束时上报结构化进度事件。
2. Java 将事件写入 `ai_progress_event`，同时通过 SSE 向 SelUI 页面推送。
3. 页面按根任务展示总体流水线，按阶段展示角色、阶段 ThreadID、状态、耗时、尝试次数、进度、当前动作、文件和错误。
4. 页面刷新后先从数据库恢复当前快照，再从最后事件序号继续订阅，不能只依赖内存消息。
5. 长时间无心跳的运行进入 `STALE`，由控制面判断重试、终止或人工接管。
6. 进度百分比只用于展示；状态转换仍以持久化事件、文件 Gate 和阶段 Gate 为准。

建议 API 概要：

- `POST /api/ai-factory/tasks`：创建根任务。
- `GET /api/ai-factory/tasks/{taskId}`：取得任务、阶段和当前状态。
- `GET /api/ai-factory/tasks/{taskId}/events`：SSE 实时进度。
- `POST /api/ai-factory/stage-runs/{runId}/claim`：Python Worker 领取运行。
- `POST /api/ai-factory/stage-runs/{runId}/heartbeat`：上报心跳和进度。
- `POST /api/ai-factory/stage-runs/{runId}/artifacts`：登记产物。
- `POST /api/ai-factory/stage-runs/{runId}/errors`：登记错误。
- `POST /api/ai-factory/stage-runs/{runId}/complete`：提交实际结果，等待 Gate 和状态转换。

### 25.7 Python 错误日志与复盘依据

Python 必须同时保留结构化错误事件和脱敏运行日志。数据库保存可查询摘要，完整日志按运行数据规则写入当前工程 `OPTION/temp` 的任务专属目录。

每条原始错误事实至少包含：

1. `error_id`、根任务 ID、初始 ThreadID、阶段 ThreadID、运行 ID、角色和 Agent。
2. 时间、错误类型、错误代码、退出码和失败状态。
3. 当前文件、命令摘要、产物版本、规则快照和 Gate 版本。
4. 脱敏异常消息和堆栈，不记录令牌、密码、完整环境变量和数据库连接串。
5. 实际执行步骤、已发生的修复尝试、实际结果和问题指纹；不得写未经验证的根因。
6. 关联测试、Gate、审计事件和证据路径。

Retrospective Agent 读取错误事实后，在 `ai_retrospective` 和复盘文档中生成：

1. `failure_domain`：A 实现、B 设计、C 架构或 D 流程。
2. `root_cause`：引用证据的根因结论。
3. `code_fix_basis`：修正代码所依据的需求、架构、设计、测试或 Gate 证据；非代码问题明确写“不适用”。
4. `improvement_target`：NONE、RULE、GATE 或 PROCESS。
5. `rule_change_sentence`：一句话中文规则修正建议；不需要规则变化时明确写“无需修改规则”。

原始错误日志和复盘分析必须物理或逻辑分离。错误事实只提供复盘依据，不能自动修改生产规则；Rule Evolution Agent 只能根据已审核复盘形成不超过 30 条核心原则内的规则变更提案。

## 27. 非功能需求

### 27.1 可追溯性

任何最终产物都能追踪到原始需求、正式要件、架构对象、详细设计、任务、Agent、规则快照、实际变更、测试、Gate 和审计事件。

### 27.2 安全性

最小权限、路径防逃逸、敏感信息脱敏、命令白名单或风险分级、外部副作用审批、隔离测试数据和审计失败阻断。

### 27.3 可扩展性

新增 Agent、Rule、Gate、产物类型和执行器时通过注册和索引扩展，不修改无关角色的核心合同。

### 27.4 可恢复性

每个关键阶段保存可验证快照和恢复点。失败后可以恢复到最近已确认阶段，不要求从头执行。

### 27.5 可观测性

按根任务展示流水线总状态，按阶段 Thread 展示角色、耗时、Agent 运行、任务进度、文件验收、失败、修复次数、测试、Gate、预算和阻断原因。

### 27.6 可移植性

路径配置保存工程相对路径，运行时依据实际操作系统和工程根解析；禁止提交机器绝对路径。

## 28. MVP

第一阶段只建设一条可闭环的最小生产线：

1. 五个治理入口和唯一根索引。
2. 生产、门禁、修复、进化和支撑五套逻辑 Agent 体系；一个角色对应一个隔离 Agent 身份。
3. 一需求一根任务和初始 ThreadID，各阶段使用独立阶段 Thread，并共享一个工作空间和 Git 分支。
4. Java 管理面、SelUI 流水线页面、数据库逻辑模型和 Python Worker 最小通信闭环。
5. 标准中文文件命名、产物模板和 metadata 状态管理。
6. 需求、要件定义、架构、详细设计确认和发布前人工门禁。
7. 15 个基础 Gate 和需求/要件/架构/设计/代码/测试/质量分层门禁。
8. 不超过 30 条中文核心规则的加载、冻结和快照。
9. 有上限的自动诊断与修复闭环。
10. append-only 审计账本、Python 错误日志和根任务/阶段 Thread 查询。
11. 复盘与 Rule/Gate/Process 提案，但暂不自动激活治理资产新版本，也不建立经验库。
12. 一个真实、低风险 SELPLAT 需求的端到端试运行。

MVP 暂不包含生产自动发布、跨组织审批、外部 WORM、复杂可视化编排和全量旧规则迁移。

## 29. 验收标准

1. 用户开始需求文档时立即建立根任务、初始 ThreadID、需求阶段记录、工作空间和需求分支。
2. 自动生成全部标准产物，缺失必需产物时 Gate FAIL。
3. 原始需求、正式要件、架构、详细设计、任务、变更、测试和各层 Gate 具有完整双向引用。
4. 设计中代码对象精确到方法，无方法对象精确到内容，并与 PPT 对象 ID 一致。
5. Development Agent 修改设计外文件时被阻断。
6. 测试记录包含实际数据、命令、结果和证据，不允许只写“通过”。
7. 测试通过但任一 Gate 失败时不得完成任务。
8. 自动修复后，旧测试和 Gate 结果失效并重新执行。
9. 修复循环超限后进入人工接管，不出现无限循环。
10. 规则优化只生成提案，未审核规则不会进入生产加载。
11. 通过根任务 ID 或初始 ThreadID 可以还原所有阶段 Thread、角色、Agent、文件、命令、变更、测试、Gate 和审批。
12. 篡改任一原始审计事件后校验非零失败。
13. 敏感信息检查违规数为零。
14. 审计不可用时关键写操作被阻断。
15. 中断后能够从最近持久恢复点继续，不重复已确认外部副作用。
16. 架构脑不能直接修改业务代码，执行脑不能修改需求、要件定义、架构、设计、Rule、Gate Definition 或 Process。
17. 每次执行都能定位唯一已批准 Architecture Package，包变化后旧验证结果自动失效。
18. 执行脑发现 B 类设计或 C 类架构问题时生成架构变更请求并暂停，不自行重定义上游合同；D 类进入流程改进。
19. 同一问题指纹第三次出现时自动归为 D 类并启动 Process Improvement，检查 Rule、Gate、流程和 Agent 职责。
20. Gate Definition 与 Gate Runner 分离，Gate Runner 对固定产物摘要执行且不能修改受检产物。
21. 需求、要件定义、架构、详细设计、源码、配置、SQL、PPT、测试、错误、审计和发布文件均有类型 Gate；任一文件未验收时阶段不能完成。
22. Java 是工作流数据库唯一写入者，Python 通过 API 上报；不存在 Java/Python 双写同一业务表。
23. Python 能按数据库角色版本加载 AGENTS 并启动 Codex，页面实时看到阶段状态、心跳、进度和错误。
24. 页面刷新后能从数据库恢复任务快照并继续订阅后续 SSE 事件。
25. 生产有效 Rule 不超过 30 条且以中文表达；第 31 条未治理时被阻断。
26. Python 原始错误日志只记录事实；代码修正依据、根因和一句话规则建议由引用该日志的复盘产生，二者可独立校验。
27. 一个角色只对应一个逻辑 Agent；同一模型承担多个角色时具有不同 agent_id、权限、上下文和运行记录。
28. Requirement、Requirements Definition、Architecture、Design、Code、Test 和 Quality Gate 均存在且顺序不可跳过。
29. 任一 Gate 失败后按 A/B/C/D 路由修复，并返回原 Gate 版本复验，不得换 Gate 或降低标准。
30. 系统不存在全局 Experience Library、Knowledge Base、Case Library、Memory Library 或 Knowledge Wiki。
31. 长期治理资产只有 Log、Rule、Gate、Process Library；未批准复盘和提案不能进入有效 Library。
32. 每条正式要件都有稳定 ID、来源、类型、优先级、状态、验收标准和验证方式；缺少任一必填内容时要件 Gate FAIL。
33. 未通过要件 Gate 的内容不能进入架构阶段，架构对象不能引用未批准或已被替代的要件。
34. 通过任一要件 ID 可以双向查询原始需求、架构、设计、任务、测试和 Gate；要件变化能够计算受影响对象。

## 30. 主要风险与待确认项

1. 五个 AGENTS 是否最终确认采用本文的“总入口 + 四个文档治理入口”。
2. `design.pptx` 是权威设计组成部分还是由结构化设计生成的派生件。
3. 长期审计账本、发布归档和完成工作空间的正式存储位置。
4. 根任务 ID、初始 ThreadID、阶段 ThreadID 的生成规则和跨系统唯一性来源。
5. 哪些需求允许全自动执行，哪些必须预先人工批准。
6. 自动修复默认次数、时间和费用上限。
7. Git 推送、PR、合并和发布分别接入哪个审批系统。
8. 普通、核心和新增代码覆盖率是否允许按技术栈配置例外。
9. 规则提案的评审人、审批门槛和生效周期。
10. 第一个端到端试运行需求及目标工程。
11. 审计是否记录所有只读操作，还是仅记录敏感读取和状态变化。
12. 原始 `AI开发工厂_需求与概要设计.md` 在本文确认后是保留参考、归档还是停止维护。
13. 架构脑和执行脑由不同模型、不同进程还是同一执行器的不同权限角色实现。
14. Architecture Package 的批准者、有效期和变更后任务重算范围。
15. 重复问题升级的默认问题指纹算法和跨 Thread 统计窗口。
16. MVP 数据库使用 H2 文件库还是直接选用后续正式数据库。
17. Python Worker 领取任务采用轮询、长轮询还是独立消息队列。
18. SSE 断线保留的进度事件周期和历史归档周期。
19. Python 直管数据库备选方案是否明确排除，避免详细设计同时维护两套写入架构。
20. 流程改进委员会由哪些人工角色或授权审批服务组成。
21. 任务复盘和未批准改进提案的保留期、访问权限和清理策略。
22. Quality Monitor 的趋势窗口、阈值和跨根任务问题指纹范围。
23. 要件优先级采用 MoSCoW、数值等级还是工程自定义枚举。
24. 要件定义的批准角色，以及业务要件和系统要件是否需要不同审批人。
25. 单条要件允许的最大粒度、拆分原则和跨需求复用规则。

## 31. 与原规则引擎的关系

原规则引擎只提供以下经验参考：

1. 独立授权后才能开始修改。
2. 使用 ThreadID 隔离任务和文档。
3. Rule 与 Gate 分工，阻断必须返回明确失败。
4. 测试登记与实际执行分离，未执行不得声称通过。
5. 规则使用唯一索引、稳定逻辑 ID 和显式依赖。
6. 审计、归档、路径防逃逸和运行数据归属。

新 AI 产出工厂不以兼容旧目录、迁移旧规则、复制旧分层或替代旧生产入口作为前提。需要复用的能力在详细设计阶段重新评估并通过适配接口引入，禁止直接形成隐式耦合。
