# Detailed Design Document Rules

## 说明

- 本文件用于约束“详细设计文档”的生成
- 本文件是高度抽象的通用规则，不绑定某一个具体业务模块
- 本文件适用于把需求说明、现状排查、目标方案和实现约束整理成结构化详细设计文档的场景

<!-- 本规则解决“设计文档只有目标方案，没有现状问题、边界和实施路径”的问题；适用于详细设计文档生成场景；业务含义是把输出固定为可评审、可实施、可追踪的设计文档，并以专属键标识作用域避免跨文件覆盖 -->
detailed_design_document_rule_scope = detailed_design_document_generation

<!-- 详细设计文档必须先说明现状与问题，再进入目标方案；适用于任何包含现状差距的设计场景；业务含义是避免把未来设计误写成当前实现 -->
must_describe_current_state_before_target_design = true

<!-- 输入必须优先使用需求正文、现状排查结果和上下文约束；适用于通用设计文档生成；业务含义是设计文档不能脱离需求和现实实现边界 -->
input_primary_sources = requirement_text,current_state_findings,implementation_constraints,business_context

<!-- 输出必须是结构化详细设计文档；适用于评审、实现和交接场景；业务含义是禁止生成零散结论或无层次长文 -->
output_must_be_structured_design_document = true

<!-- 文档必须同时覆盖问题、目标、方案、数据、流程、改动点、风险和验证；适用于工程实施设计；业务含义是避免只讲目标不讲落地 -->
required_design_sections = current_issues,design_goals,input_output_boundary,core_principles,solution_overview,data_design,process_design,change_points,risks,verification

<!-- 若需求依赖现有实现，应明确区分当前实现与目标实现；适用于重构、扩展和新能力补齐场景；业务含义是避免评审时混淆“已实现”和“待实现” -->
must_separate_current_vs_target_state = true

<!-- 文档必须包含开发前必须修正的事项；适用于存在明显实现缺口的场景；业务含义是先修主链路问题，再谈方案优化 -->
must_include_pre_fix_items_when_gap_exists = true

<!-- 文档必须说明输入与输出边界；适用于模型生成、接口设计、数据设计和切分方案；业务含义是避免责任边界模糊 -->
must_define_input_output_boundaries = true

<!-- 若方案包含配置项，必须明确哪些参数可配置以及默认值；适用于切分、时长、阈值、节奏等方案；业务含义是避免硬编码设计 -->
must_mark_configurable_parameters_and_defaults = true

<!-- 若方案依赖模板化输出，必须提供模板，并要求生成时参考模板；适用于规则驱动和结构化文本生成场景；业务含义是保证输出口径稳定 -->
must_include_reference_template_when_template_needed = true

<!-- 文档必须写明代码改动点；适用于需要进入实现阶段的详细设计；业务含义是让设计直接连接开发任务 -->
must_include_code_change_points = true

<!-- 文档必须写明是否可复用现有字段、何时需要补字段；适用于涉及存储和表结构的方案；业务含义是减少不必要扩表，同时避免长期字段不足 -->
must_analyze_field_reuse_and_schema_gap = true

<!-- 文档必须写明风险点和验证方案；适用于工程评审；业务含义是让方案可控、可验证、可回归 -->
must_include_risks_and_verification = true

<!-- 文档口吻应直接、专业、面向实现；适用于工程设计；业务含义是避免宣传式、汇报式或空泛描述 -->
design_doc_style_must_be_direct_and_implementation_oriented = true

<!-- 详细设计文档补到成品级时 必须同步收口当前实现 正式契约 异常处理和测试口径；适用于从方案稿提升到可直接开发交付稿的场景；业务含义是避免文档只补结构而不补实施所需关键口径 -->
finalized_design_doc_must_close_current_state_contract_error_handling_and_test_scope = true

<!-- 若文档目标是成品级详细设计稿 必须给出正式接口契约 请求响应样例和落库定稿；适用于前后端联调或生成链路设计场景；业务含义是让文档可直接指导开发与测试而不是继续靠实现阶段临场补齐 -->
production_ready_design_doc_must_include_final_interface_contract_examples_and_storage_decisions = true

## 生成要求

1. 先写当前实现问题、现状边界或已知缺口，再写目标方案。
2. 明确区分“当前实现”“第一阶段落地方案”“正式目标方案”。
3. 输入、输出、配置项、数据结构、流程和改动点都要写清楚。
4. 如果涉及字段复用或扩表，必须写出“可先复用什么”“为什么还不够”“什么时候需要补字段”。
5. 如果方案需要模板驱动，必须给出模板，并明确生成时参考模板。
6. 文档必须能直接支撑后续评审和开发，不要只停留在抽象愿景。
7. 如果目标是成品级详细设计文档，必须补齐当前实现口径、正式接口契约、异常处理规则和测试验证口径。
8. 如果文档用于直接实施，必须明确哪些能力已经实现、哪些仍是下一阶段，不得把未来目标误写成当前能力。

## 输出模板

生成时参考下面模板输出。  
模板是结构参考，不是固定业务内容。  
具体章节可按实际任务增减，但整体顺序不应偏离太多。

```text
# {设计文档标题}

## 0. 当前实现问题与优先修正项

### 0.1 当前实现现状
- 当前已经实现了什么
- 当前还没有实现什么
- 当前哪些能力仍是 mock、本地逻辑或临时方案

### 0.2 当前核心问题
- 问题 1：...
- 问题 2：...
- 问题 3：...

### 0.3 当前字段 / 结构是否可以复用
- 可以复用什么
- 为什么可以复用
- 哪些地方复用后仍然不足

### 0.4 开发前必须先修正的事项
1. ...
2. ...
3. ...

## 1. 目标
- 本次设计要解决什么问题
- 最终输出要达到什么状态

## 2. 输入与输出边界

### 2.1 输入
- 输入来源
- 输入字段
- 主输入与辅助输入

### 2.2 输出
- 输出对象
- 输出结构
- 输出限制

## 3. 核心设计原则
- 原则 1：...
- 原则 2：...
- 原则 3：...

## 4. 方案设计
- 总体方案
- 关键流程
- 模块协作关系

## 5. 数据与字段设计
- 现有字段复用
- 建议新增字段
- 配置项设计

## 6. 代码改动点
- 后端改动点
- 前端改动点
- 规则文件改动点
- 接口与任务链路改动点

## 7. 风险点
- 风险 1：...
- 风险 2：...

## 8. 验证方案
- 如何验证
- 验证通过标准
```

## 使用说明

- 如果任务本身就是“生成详细设计文档”，应优先遵守本规则，而不是临时自由发挥结构。
- 如果任务是为某个具体业务生成详细设计文档，可在本规则基础上叠加该业务的专项规则。
- 如果后续代码需要读取本文件作为 prompt 规则源，建议与具体业务规则分层使用：先套本通用规则，再补业务上下文。
