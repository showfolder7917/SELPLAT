# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.

## Product-specific visual contract

- Use `ai-desktop` as the canonical application directory, package, runtime client, and rule scope name; use `AI Desktop` as the product identity.
- Keep Copilot wording only where the office variant intentionally reproduces the supplied visual reference or preserves a documented compatibility launcher; do not reuse it as the engineering project identity.
- Dismiss transient settings panels when the user clicks outside or presses Escape; interactions inside the panel must not dismiss it, and the behavior must not resolve or suppress approval dialogs.
- Keep workspace roots in an independently expandable multi-panel Accordion. Register real directories through the Electron main-process folder picker, persist them in local user data, default new roots to workspace-write, preserve later manual read-only choices, and map only explicitly writable registered roots into the official Codex turn sandbox policy.
- Keep the developer shell typography at desktop-IDE readability: primary navigation, workspace tree, controls, chat content, and context values should normally render at 13–15 CSS px with matching row height; do not use 10–11px for critical readable content.
- Keep the developer resource explorer, workspace, and tasks section headings as real disclosure controls with visible expanded state. Workspace and Tasks form a single-active stack: opening either section collapses the other, moves the active section to the top, and lets it fill all available sidebar height while the inactive heading stays at the bottom as the switching entry. Collapsing the resource explorer must remove the entire explorer grid column, expand chat and composer into the released width, and leave the activity-bar folder icon available to restore it. Place the icon-only new-task action inside the `Codex Chat` tab immediately before its close icon, render it as a refresh-conversation glyph, and show the localized hover/focus Tip `重新建立一个 Codex 会话` in Simplified Chinese; do not duplicate it in the Tasks heading or as a separate full-width row.
- Keep the developer explorer's right edge adjustable by pointer and keyboard, and let resetting return it to the standard width. Do not render a workspace/tasks height divider: the single active section owns the available height instead of sharing a manual allocation with the inactive section.
- Let the outer workspace list own vertical scrolling. Do not impose a fixed maximum height or a second scroll container on an expanded workspace tree: every directory row, especially the final row, must remain fully visible while unused space exists above the inactive Tasks heading.
- Write append-only business event timelines and per-task summaries under `apps/ai-desktop/log`. Each task summary must correlate the request, workspace/sandbox snapshot, Harness turn, approvals, commands, changed files, completion state, build freshness, and explicit partial-completion reason codes; never persist raw reasoning or authentication secrets. Collaboration logs must record wall-clock timestamps plus monotonic durations for work, queueing, reviewer wait, review, rework, Codex/worktree preparation, verification, integration, conflicts, approvals, user input, dependencies, and recovery. Attribute every wait to its reason, occupied resource and releasing event, then generate per-integration-generation and cross-generation bottleneck reports from structured events. Expose the log directory and latest diagnosis in settings, but do not render collaboration timelines, duration breakdowns, resource-occupation chains, or bottleneck analysis in member pages; those pages show only current state, concise blocking reason and result access.
- Run managed work as an explicit four-stage state machine. `会话托管` is the default and only understands the user's intent. Its confirmation advances to read-only `需求托管`, which investigates causes and proposes a correction plan. Only the next confirmation opens `任务托管`, which must modify source, run static checks, launch one hidden isolated Electron, execute Playwright locator-based interaction tests, save screenshots only on failure under application temp, repair and retest for at most five validation rounds, close the isolated instance, and stop at code-level verification without a formal build or restart of the user's app. A final confirmation opens `测试托管`, which keeps the existing full build, post-build tests, repair loop, and at most one required restart. Conversation and requirement stages must reject file changes and privileged commands.
- Put icon-and-text actions at the lower right of the latest managed response. Keep the forward action sequence `就是这意思`, `按这个方案执行`, then `测试一下`; from downstream stages also show `回到会话托管` and, once Task management has been reached, `回到任务托管`. Return actions switch the local execution mode without automatically sending a new Harness turn, and the button for the already selected mode stays disabled. Keep the latest actions visible but disabled while that response is still running, then enable eligible actions only after completion; historical actions may retain their highlighted confirmation state but must not advance or roll back stages. Clicking the forward action advances exactly one stage; a standalone `1` or the matching configured phrase has the same effect, while a longer sentence containing a keyword is not authorization. After use, highlight the historical forward button and rename it to `重新分析需求`, `重新执行`, or `重新测试`.
- Keep the official Harness approval policy at `on-request` with the user reviewer. For an eligible project command, the first `允许` action means `允许并信任`; persist only the exact real project root, cwd, command text, and package-script signature under Electron user data, then automatically answer later identical official approval requests. Any identity change, file-change request, destructive command, privilege/permission expansion, or Git-state destructive command must still require explicit review. Show the trusted count and a confirmed clear-all action in settings, and audit both trust creation and automatic allowance.
- Keep exactly one current AI Desktop-owned Harness thread with official persistent storage. Save only its active thread ID under Electron user data, resume it after renderer or Electron reconstruction, and keep using it when only the managed-stage sandbox changes. The explicit new-task action must call official `thread/delete`, clear the saved ID and local transcript, and start a fresh thread only on the next send; do not add an application history list. Put locale and natural collaborator-style guidance in `developerInstructions`; keep the first user message limited to registered workspace context, the real task, and attachments so internal templates cannot become repeated task titles.
