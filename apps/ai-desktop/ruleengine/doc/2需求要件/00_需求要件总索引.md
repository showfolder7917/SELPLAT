## 2. 来源优先级与冲突裁决

1. `需求文档.md` 是本轮最新、最完整的权威来源。
2. `AI开发工厂_需求.md`、Agent 组织、审计、异常、知识沉淀和双脑边界规范用于补充来源和历史理由。
3. 辅助资料与主需求冲突时采用主需求：生产有效 Rule 硬上限为 30 条；长期资产只有 Log、Rule、Gate、Process；并非每个错误都必须修改治理资产；要件定义和对应 Gate 是架构阶段的强制前置。
4. `审计规范.md` 与 `AI软件工厂_全流程日志与审计规范.md` 内容相同，只作为一个事实来源计数。
5. 主需求“主要风险与待确认项”中的决定均保持 `draft/TBD`，不得由架构师自行假定为已批准。

## 3. 统一编号和状态

- 正式要件：`REQ-<范围>-<三位序号>`。
- 来源引用：`SRC-MAIN-<章节或FR>`、`SRC-BASE-<章节>`、`SRC-ORG-<章节>`、`SRC-AUD-<章节>`、`SRC-ERR-<章节>`、`SRC-KNOW-<章节>`、`SRC-BRAIN-<章节>`。
- 优先级：`Must`、`Should`、`Could`、`Won't(MVP)`。
- 状态：本轮统一为 `draft`；经过要件评审后才能改为 `reviewed` 或 `approved`。
- 后续追踪占位：`ARC-* → DES-* → TASK-* → TEST-* → GATE-*`，由后续阶段建立真实对象后回填，禁止在本阶段伪造。

## 6. 分包协作合同

1. 每位架构师只设计分包声明的业务边界，不得提前写业务源码或擅自决定 `DEC-*`。
2. 所有架构对象必须引用至少一个本目录 `REQ-*`；不得引用未批准或已替代要件。
3. 跨分包依赖通过稳定要件 ID 表达，不能通过聊天上下文隐式传递。
4. 同一对象被多个分包需要时，由总体架构师指定唯一所有者；其他分包只引用合同，不重复拥有。
5. 任一 `REQ-*` 变更后，必须沿追踪关系使受影响的架构、设计、任务、测试和 Gate 结果失效并重新评估。

## 7. 要件包完成门槛

本包只有同时满足以下条件后才能从 `draft` 进入 `approved`：

1. 所有 `REQ-*` ID 唯一，且必填字段完整。
2. 每条要件均有来源、理由、优先级、状态、验收标准和验证方式。
3. 分包之间不存在未解决冲突或循环所有权。
4. `DEC-*` 已由具备权限的人工角色确认，或明确排除在当前里程碑外。
5. Requirements Definition Gate 对固定文件摘要逐文件验收并对整个要件包聚合验收。
6. 审批结果、文件摘要、Gate 版本和审计事件已登记到权威数据库；本目录文件名不是权威状态来源。
