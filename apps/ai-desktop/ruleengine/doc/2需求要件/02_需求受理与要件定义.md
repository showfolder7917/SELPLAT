# 分包 02：需求受理与要件定义需求要件

## 1. 独立交付说明

本分包从客户首次提交需求开始，止于 Requirements Definition Gate 和人工确认通过。它定义根任务建立、需求澄清、正式要件拆分、来源追踪、冲突检查和阶段交接，输出可以直接被架构阶段消费的已批准要件集合。

## 2. 角色与责任

- Intake Agent：接收请求、建立根任务、识别风险，不进行设计。
- Requirement Agent：整理目标、范围、约束、场景和验收条件，并把确认后的需求按独立开发功能拆成需求要件。
- Requirement Gate Agent：独立检查需求明确性和可验收性。
- Requirements Definition Gate Agent：检查要件完整性、一致性、可测试性、唯一 ID 和追踪。
- 人工批准者：确认需求范围、验收条件和待决业务选择。

## 3. 目标流程

```text
客户提交 → 建立根任务与需求阶段 → 需求分析 → 需求 Gate
→ 人工确认 → 建立要件阶段 → 要件拆分与来源追踪 → 要件 Gate
→ 人工确认 → 允许建立架构阶段
```

任何 Gate 失败都返回对应 Fix Agent；重大歧义保持 BLOCKED，禁止带病进入架构。

## 5. 功能合同

| 场景 | 输入 | 前置条件 | 输出/后置条件 | 异常结果 |
| --- | --- | --- | --- | --- |
| 创建需求 | 用户正文、工程、稳定用户、风险信息 | 身份和目标工程有效 | 根任务、Thread、需求阶段及元数据 | 创建失败则不生成需求文件 |
| 需求分析 | 原始需求和补充材料 | 根任务存在 | 版本化需求文档和开放问题 | 重大歧义进入 BLOCKED |
| 要件拆分 | 已通过需求 Gate 的固定版本 | 人工确认已记录 | 稳定 ID 要件集合和来源链接 | 冲突或不可测试则 Gate FAIL |
| 要件变更 | 变更原因和当前版本 | 有修改权限 | 新版本、影响对象和旧状态 | 不覆盖历史版本 |

## 6. 数据质量与例外

1. 同义要件需合并并保留替代关系；不得保留两个权威 ID 表达同一合同。
2. 跨分包要件必须指定唯一所有者，引用方不能复制后独立演进。
3. 暂无可量化阈值的非功能需求必须关联 `DEC-*`，不能用“性能良好”等不可测试描述放行。
4. 客户聊天只作为来源事实，关键决定必须写入正式需求或审批记录。

## 7. 分包验收

本分包交付的架构必须说明需求解析、版本、审批、要件登记、冲突检测、Gate、修复和双向追踪边界，并用至少一个正常样例和四个失败样例证明不会跳过需求/要件阶段。
