# Uniauth 用户与主题权限实现方案

## 1. 文档目标

本文给出 Uniauth 用户权限第一版实现方案。方案参考 TRS WCM 的对象级授权思路，但不直接复制其旧式 JSP、数字对象类型和 63 位权限位图。

第一版需要同时覆盖：

- 用户、角色、组织与租户的关系；
- 页面、菜单、按钮和后端接口的访问控制；
- 主题、深浅模式和主题皮肤的可见、使用及管理权限；
- 个性化设置中用户级、页面级和系统级配置的权限；
- 前端权限 JSON 与后端最终鉴权的一致性；
- 权限缓存、变更失效、审计和测试。

本文是实现基线，不代表已经完成数据库与代码改造。

## 2. 当前工程事实

### 2.1 Uniauth 当前状态

当前 Uniauth 已具备以下基础：

- `UniauthTenant`：租户主数据；
- `UniauthUser`：带 `tenantId` 的用户主数据；
- `UniauthSettings.schema.json`：设置模块已声明 `scope` 和 `permission`；
- `selPersonalizationRegistry`：能够按 `permission` 调用应用传入的 `canAccess` 回调过滤设置模块；
- `selThemeRegistry`：能够注册主题、深浅模式、颜色皮肤、边框和背景素材；
- 主题和设置目前主要来自静态资源，尚无后端真实权限结论；
- 前端注册表明确不负责最终授权，后端应成为权限事实来源。

### 2.2 TRS 权限实现中值得保留的思路

TRS 的核心并非简单的“用户属于角色”，而是以下对象级关系：

```text
授权主体（用户 / 角色 / 用户组）
        +
资源对象（系统功能 / 站点 / 栏目 / 文档等）
        +
操作权限（查看 / 新建 / 编辑 / 删除 / 发布等）
        =
一条对象级授权
```

主要证据如下：

- `WCMROLE`、`WCMROLEUSER`、`WCMGRPUSER` 保存角色和组织成员关系；
- `WCMRIGHTDEF` 按资源类型定义可执行操作；
- `WCMRIGHT` 保存“资源类型、资源 ID、主体类型、主体 ID、权限值”；
- `AuthServer.hasRight` 统一判断权限；
- `RightValue.load` 汇总用户、Everyone 角色、其他角色和用户组权限；
- JSP 根据权限决定菜单和按钮是否出现；
- Service 或执行 JSP 在真正修改数据前再次校验权限；
- 对父子资源提供权限继承和向子节点同步的能力；
- 权限修改后通过缓存管理器刷新结果。

### 2.3 TRS 实现中不应照搬的部分

- 不使用 63 位整数保存全部权限，避免权限数量和迁移受到位宽限制；
- 不使用数字权限索引作为公开契约，改用稳定字符串编码；
- 不把鉴权逻辑散落在 JSP 或前端脚本中；
- 不把“隐藏按钮”等同于安全控制；
- 不采用“发现一条用户授权就完全跳过角色授权”的隐式规则；
- 不默认让资源创建者绕过全部权限，创建者特权必须是显式策略；
- 不使用跨租户主体或资源参与同一次权限合并。

## 3. 总体设计原则

### 3.1 后端是唯一授权事实来源

前端只消费后端已经计算完成的权限快照，用于：

- 隐藏无权访问的菜单、主题和设置模块；
- 禁用暂不可执行的按钮；
- 避免用户进入必然返回无权的操作流程。

所有读取敏感数据或改变状态的后端接口仍必须独立鉴权。用户即使手工构造请求，也不能越过后端权限判断。

### 3.2 采用“主体—资源—操作”模型

统一授权判断表达为：

```text
can(subject, action, resource, context)
```

- `subject`：当前用户及其角色、组织；
- `action`：稳定权限编码；
- `resource`：系统、项目、页面、组件、主题、模式或皮肤；
- `context`：租户、项目、请求来源及必要业务属性。

### 3.3 权限编码与展示文案分离

权限编码不可国际化，也不可因界面文字变化而修改。例如：

```text
uniauth.theme.read
uniauth.theme.use
uniauth.theme.manage
uniauth.page.layout.edit
```

中文、英文和日文名称通过独立国际化资源显示。

### 3.4 默认拒绝

没有明确授权时返回无权。权限数据缺失、资源不存在、租户不匹配或权限服务异常时均不得自动放行。

### 3.5 租户边界优先

除平台级系统管理员外，主体、角色、组织、资源和授权必须属于同一 `tenantId`。权限计算前先校验租户，禁止依靠权限编码弥补租户隔离。

## 4. 权限领域模型

### 4.1 授权主体

第一版支持三类主体：

| 主体类型 | 含义 | 用途 |
| --- | --- | --- |
| `USER` | 单个用户 | 少量例外授权或禁止 |
| `ROLE` | 角色 | 主要授权载体 |
| `GROUP` | 组织或用户组 | 按部门、班级、项目组授权 |

每个有效用户隐式拥有当前租户的 `Everyone` 角色，不需要为每个用户写一条成员关系。

### 4.2 资源类型

第一版建议支持以下资源：

| 资源类型 | 示例资源键 | 说明 |
| --- | --- | --- |
| `SYSTEM` | `uniauth` | Uniauth 系统级功能 |
| `PROJECT` | `uniauth` | 项目配置边界 |
| `PAGE` | `uniauth.user-grid` | 页面级授权 |
| `COMPONENT` | `UniauthUserGrid` | 表格或公共组件实例 |
| `ACTION` | `UniauthUserGrid.create` | 按钮及操作入口 |
| `THEME` | `crystal-tech` | 完整主题包 |
| `THEME_MODE` | `crystal-tech:dark` | 主题下深色或浅色模式 |
| `THEME_SKIN` | `crystal-tech:dark:stellar-blue` | 模式下具体颜色皮肤 |
| `SETTING_MODULE` | `uniauth.page.layout` | 个性化设置模块 |

资源使用字符串业务键，不把数据库主键暴露为前端配置契约。

### 4.3 操作权限

权限按实际业务动作定义，不按页面位置定义。建议第一批权限如下：

#### 用户与权限管理

```text
uniauth.user.read
uniauth.user.create
uniauth.user.update
uniauth.user.delete
uniauth.user.permission.assign
uniauth.role.read
uniauth.role.manage
uniauth.group.read
uniauth.group.manage
```

#### 页面与组件

```text
uniauth.page.read
uniauth.page.layout.edit
uniauth.page.fields.edit
uniauth.page.actions.edit
uniauth.component.configure
```

#### 个性化设置

```text
uniauth.preference.read
uniauth.preference.update
uniauth.setting.page.read
uniauth.setting.page.update
uniauth.setting.system.read
uniauth.setting.system.update
```

#### 主题

```text
uniauth.theme.read
uniauth.theme.use
uniauth.theme.manage
uniauth.theme.assign
```

含义区分：

- `theme.read`：能在主题库中看到主题；
- `theme.use`：能切换到主题、模式或皮肤；
- `theme.manage`：能新增、停用或修改主题元数据；
- `theme.assign`：能把主题使用权授予角色、组织或用户。

## 5. 数据库设计

所有表沿用当前工程公共字段约定，包括 `id`、`tenantId`、`lastOperateUserId`、`sortnum`、`status`、`createdAt` 和 `updatedAt`。

### 5.1 角色与成员

#### `UniauthRole`

- `roleCode`：租户内稳定角色编码；
- `roleName`：默认展示名；
- `roleType`：`SYSTEM` 或 `CUSTOM`；
- `everyoneFlag`：是否为租户 Everyone 角色；
- `removableFlag`：是否允许删除。

唯一约束：`tenantId + roleCode`。

#### `UniauthUserRole`

- `userId`；
- `roleId`；
- `validFrom`、`validUntil`：可选有效期。

唯一约束：`tenantId + userId + roleId`。

### 5.2 组织与成员

#### `UniauthGroup`

- `groupCode`；
- `groupName`；
- `parentGroupId`：形成组织树；
- `groupPath`：用于快速校验祖先关系；
- `inheritMemberFlag`：是否包含下级组织成员。

#### `UniauthGroupUser`

- `groupId`；
- `userId`；
- `administratorFlag`：是否为组织管理员。

组织管理员只获得组织管理能力，不自动获得全部业务资源权限。

### 5.3 权限定义

#### `UniauthPermission`

- `permissionCode`：例如 `uniauth.theme.use`；
- `resourceType`：该权限适用的资源类型；
- `permissionNameKey`：国际化名称键；
- `permissionDescriptionKey`：国际化说明键；
- `systemDefinedFlag`；
- `riskLevel`：`LOW`、`MEDIUM`、`HIGH`。

唯一约束：`permissionCode`。

### 5.4 资源登记

#### `UniauthResource`

- `projectCode`：例如 `uniauth`；
- `resourceType`；
- `resourceKey`：例如 `crystal-tech:dark:stellar-blue`；
- `parentResourceId`：主题到模式、模式到皮肤的父子关系；
- `resourceNameKey`；
- `inheritPolicy`：`INHERIT`、`ISOLATED` 或 `EXPLICIT`；
- `enabledFlag`。

唯一约束：`tenantId + projectCode + resourceType + resourceKey`。

系统内置主题可以登记为平台模板，再在租户层生成可授权资源映射；租户授权不得修改主题包静态文件。

### 5.5 授权关系

#### `UniauthGrant`

- `subjectType`：`USER`、`ROLE` 或 `GROUP`；
- `subjectId`；
- `resourceId`；
- `permissionId`；
- `effect`：`ALLOW` 或 `DENY`；
- `validFrom`、`validUntil`；
- `grantSource`：`MANUAL`、`SYSTEM_DEFAULT` 或 `IMPORT`；
- `remark`。

唯一约束：

```text
tenantId + subjectType + subjectId + resourceId + permissionId
```

不要把多个权限压缩进一个整数列。每条记录表达一个可审计的授权事实。

### 5.6 审计记录

#### `UniauthPermissionAudit`

至少记录：

- 操作人、租户和请求追踪号；
- 被修改的主体、资源和权限；
- 修改前与修改后的 `effect`；
- 授权来源、时间和客户端信息；
- 操作结果及失败原因。

权限查询不必全部落审计表，但高风险拒绝和所有授权变更必须记录。

## 6. 权限计算规则

### 6.1 计算顺序

一次判断按以下顺序执行：

1. 校验当前用户已认证且状态有效；
2. 校验当前租户有效；
3. 校验资源存在、启用并属于允许访问的租户或平台范围；
4. 平台系统管理员按显式系统策略放行；
5. 收集用户、Everyone 角色、普通角色和组织主体；
6. 收集当前资源和允许继承的父资源授权；
7. 移除已过期授权；
8. 先处理 `DENY`，再处理 `ALLOW`；
9. 无任何有效授权时拒绝；
10. 返回权限结论及用于审计的命中来源。

### 6.2 冲突规则

第一版采用以下稳定规则：

```text
同一资源层级：显式 DENY > 显式 ALLOW > 无配置时默认拒绝
不同资源层级：子资源显式规则 > 父资源继承规则
子资源同层冲突：显式 DENY > 显式 ALLOW
```

同一资源层级出现任意有效 `DENY` 时拒绝。对子资源的显式授权覆盖父资源继承结果，因此子资源显式 `ALLOW` 可以覆盖父资源继承的 `DENY`，子资源显式 `DENY` 也可以收紧父资源继承的 `ALLOW`；任何覆盖都不能跨越租户边界。

不采用 TRS 中“存在用户记录就直接返回、完全忽略角色和组织”的行为，避免一条不完整的用户授权意外截断其他权限。

### 6.3 资源继承

建议关系如下：

```text
THEME
  └─ THEME_MODE
       └─ THEME_SKIN
```

- 主题上的 `theme.read` 和 `theme.use` 默认可向模式、皮肤继承；
- 模式或皮肤可通过显式 `DENY` 收紧；
- `theme.manage` 和 `theme.assign` 默认不向下继承，必须在系统或主题资源上明确授权；
- 页面与组件是否继承由资源的 `inheritPolicy` 决定；
- 不提供默认的“创建者拥有全部权限”，如确有业务需要应生成可审计授权记录。

## 7. 后端分层设计

### 7.1 领域服务

建议新增 `permission` 业务模块：

```text
com.sp.selplat.uniauth.permission
├── controller
├── service
├── service.impl
├── dao
└── domain
```

核心接口职责：

```java
boolean can(CurrentSubject subject, String permissionCode, ResourceRef resource);
PermissionDecision decide(CurrentSubject subject, String permissionCode, ResourceRef resource);
PermissionSnapshot snapshot(CurrentSubject subject, PermissionSnapshotRequest request);
```

`PermissionDecision` 应包含 `allowed`、`reasonCode`、命中的主体和资源，但普通前端响应不得泄露敏感授权明细。

### 7.2 当前身份上下文

认证过滤器在请求进入业务层前建立不可变的当前身份上下文，至少包含：

- `userId`；
- `tenantId`；
- 登录会话或令牌 ID；
- 账号状态；
- 是否平台系统管理员。

业务方法不得相信前端传入的 `userId` 或 `tenantId` 代表当前操作者。

### 7.3 后端强制鉴权

推荐在 Service 入口使用统一授权服务，注解只作为声明辅助。例如：

```java
permissionService.require(
    currentSubject,
    "uniauth.theme.assign",
    ResourceRef.theme(themeId)
);
```

Controller 只负责参数接收与序列化，不复制权限计算逻辑。DAO 不承担当前用户鉴权，但所有查询必须携带已经校验的 `tenantId` 边界。

### 7.4 无权响应

- 未认证：HTTP 401；
- 已认证但无权：HTTP 403；
- 跨租户资源：对普通调用方统一按 404 或业务不可见处理，避免泄露资源存在性；
- 响应使用稳定错误码，例如 `UNIAUTH_PERMISSION_DENIED`；
- 不返回数据库授权记录或其他角色成员信息。

## 8. 权限接口设计

### 8.1 当前用户权限快照

```http
GET /api/uniauth/me/permission-snapshot.htm?project=uniauth&page=uniauth.user-grid
```

示例响应：

```json
{
  "version": "2026-08-07T00:00:00Z/42",
  "tenantId": 1,
  "project": "uniauth",
  "permissions": [
    "uniauth.preference.read",
    "uniauth.preference.update",
    "uniauth.theme.read",
    "uniauth.theme.use",
    "uniauth.user.read"
  ],
  "resources": {
    "themes": {
      "crystal-tech": {
        "read": true,
        "use": true,
        "modes": {
          "dark": { "use": true, "skins": ["stellar-blue", "crystal-cyan"] },
          "light": { "use": true, "skins": ["stellar-blue"] }
        }
      },
      "candy-adventure": {
        "read": true,
        "use": false,
        "modes": {}
      }
    },
    "settings": {
      "uniauth.user.display": { "read": true, "update": true },
      "uniauth.page.layout": { "read": true, "update": false }
    },
    "actions": {
      "UniauthUserGrid.create": false,
      "UniauthUserGrid.update": true,
      "UniauthUserGrid.delete": false,
      "UniauthUserGrid.permissions": false
    }
  }
}
```

快照仅为界面裁剪服务，不替代后端接口鉴权。

### 8.2 权限管理接口

建议分为：

```text
GET  /api/uniauth/permissions/getStore.htm
GET  /api/uniauth/roles/getStore.htm
POST /api/uniauth/roles/create.htm
POST /api/uniauth/roles/update.htm
POST /api/uniauth/roles/delete.htm
GET  /api/uniauth/grants/getStore.htm
POST /api/uniauth/grants/save.htm
POST /api/uniauth/grants/delete.htm
```

批量保存授权必须在同一事务内完成，并验证：

- 当前操作人拥有 `assign` 权限；
- 主体和资源属于同一租户；
- 权限适用于目标资源类型；
- 系统内置角色和权限定义未被非法删除；
- 更新后权限版本号递增并触发缓存失效。

## 9. 前端接入设计

### 9.1 启动顺序

推荐页面启动顺序：

```text
加载当前身份
  → 加载权限快照
  → 加载项目设置 JSON
  → 注册允许访问的设置模块
  → 注册并展示允许访问的主题、模式和皮肤
  → 挂载页面组件和按钮
```

权限快照失败时不渲染受保护入口，并显示可恢复的权限加载错误，禁止临时按“全部允许”继续。

### 9.2 个性化设置注册表

当前 `UniauthSettings.schema.json` 中已有 `permission` 字段，可直接保留。应用装配层将权限快照转换为：

```javascript
canAccess(permissionCode, moduleDefinition)
```

公共 `selPersonalizationRegistry` 只过滤描述，不请求权限接口、不保存授权结论。

建议后续将单一 `permission` 扩展为：

```json
{
  "readPermission": "uniauth.setting.page.read",
  "updatePermission": "uniauth.page.layout.edit"
}
```

只读用户可以看到配置，但编辑控件必须禁用，保存接口也必须返回 403。

### 9.3 主题注册表

主题 manifest 继续只描述主题包自身，不写入具体角色或用户 ID。建议允许声明稳定资源键：

```json
{
  "id": "crystal-tech",
  "resourceKey": "crystal-tech",
  "modes": [
    {
      "id": "dark",
      "resourceKey": "crystal-tech:dark",
      "accents": [
        {
          "id": "stellar-blue",
          "resourceKey": "crystal-tech:dark:stellar-blue"
        }
      ]
    }
  ]
}
```

应用层使用权限快照过滤 `selThemeRegistry.list()` 的展示结果：

- 无 `read`：主题卡完全不显示；
- 有 `read` 无 `use`：可展示但明确标记不可用；
- 模式无权：不显示对应深浅模式；
- 皮肤无权：不显示对应颜色皮肤；
- 当前正在使用的主题后来失权：立即回退到后端指定的允许主题，不沿用失权资源。

公共主题注册表不直接认识用户、角色和租户，避免公共组件承担项目权限职责。

### 9.4 页面按钮与菜单

项目 JSON 中的每个动作增加稳定权限编码，例如：

```json
{
  "id": "delete",
  "labelKey": "删除",
  "permission": "uniauth.user.delete"
}
```

前端行为规范：

- 完全不可见的功能使用隐藏；
- 用户需要知道功能存在但暂不可用时使用禁用并提供原因；
- 禁用状态不能只依赖 CSS，事件处理器仍需阻止执行；
- 后端接口必须再次校验同一权限编码和目标资源。

## 10. 缓存与变更一致性

### 10.1 缓存键

```text
tenantId + userId + projectCode + permissionVersion
```

缓存内容可以是已展开的权限集合和受限资源集合，不缓存用户密码或完整授权管理数据。

### 10.2 失效条件

以下操作必须使相关用户权限缓存失效：

- 用户加入或移出角色；
- 用户加入或移出组织；
- 角色、组织或用户授权发生变化；
- 资源继承关系变化；
- 主题、模式或皮肤停用；
- 用户、角色、组织或租户状态变化；
- Everyone 默认授权变化。

第一版可以使用数据库权限版本号加本地缓存；多实例部署后改为事件通知或集中缓存，但权限版本号仍保留作为一致性兜底。

## 11. 安全约束

- 禁止前端提交角色列表后由后端直接信任；
- 禁止从主题 manifest 推导真实授权；
- 禁止用按钮是否显示判断接口是否可以执行；
- 禁止跨租户查询授权主体和资源；
- 禁止普通管理员给自己授予超出其授权范围的权限；
- 禁止删除系统内置权限编码、平台管理员角色和 Everyone 角色；
- 高风险授权修改必须记录审计；
- 权限拒绝不得回显其他租户资源、成员或授权明细；
- 缓存异常、权限接口异常和未知权限编码一律默认拒绝。

## 12. 跨业务适用性与扩展边界

### 12.1 方案定位

本方案适合作为 SELPLAT 各业务系统共享的统一授权内核，但不等同于每个业务系统的最终权限模型。Uniauth 统一回答主体是否具备某项基础操作资格；各业务系统仍需结合自身数据范围、业务状态、审批流程和字段敏感性完成最终判断。

后续业务接入时，统一判断需要从基础形式：

```text
can(subject, action, resource, context)
```

逐步扩展为能够同时返回布尔结论和执行约束的决策：

```text
decide(subject, action, resource, context)
  -> allowed + reasonCode + dataScope + fieldMask + obligations
```

- `dataScope`：允许访问的数据范围；
- `fieldMask`：允许读取或修改的字段集合及脱敏要求；
- `obligations`：执行前必须满足的附加要求，例如二次审批、审计或本人回避。

### 12.2 业务适配评估

| 业务系统 | 适配程度 | 复用能力 | 接入前必须补充的能力 |
| --- | --- | --- | --- |
| 进销存 | 中高 | 租户、角色、组织、仓库或单据资源授权 | 公司、门店、仓库和商品数据范围，单据状态，数量或金额阈值，成本价字段权限，经办人与审批人分离 |
| 论坛 | 高 | 用户、角色、版块和帖子操作授权 | 内容所有者关系、版主辖区、禁言与封禁、帖子状态、本人编辑时限、举报处理流程 |
| 网站发布 | 中高 | 站点、栏目、内容和发布操作授权 | 频道或栏目数据范围、草稿与版本、审核发布工作流、定时发布、回滚和发布人回避 |
| 财务管理 | 中低 | 角色、资源、基础操作和高风险审计 | 法人、账套、科目和会计期间，金额级审批，字段脱敏，职责分离，不可抵赖审计 |
| 考勤管理 | 中 | 用户、组织和基础操作授权 | 本人、下属和部门数据范围，管理层级、排班关系、考勤周期、补卡审批和敏感信息保护 |
| 网站用户 | 高 | 租户、站点成员、角色和页面或接口授权 | 内外部用户分类、注册与账号生命周期、隐私同意、风控和限流；后四项不应混入授权表 |

### 12.3 通用扩展能力

#### 数据范围

权限不能只返回“允许或拒绝”，还需要表达当前主体可以访问哪些业务数据。建议至少支持：

```text
SELF
CURRENT_GROUP
CURRENT_GROUP_AND_DESCENDANTS
ASSIGNED_RESOURCE_SET
TENANT_ALL
```

业务查询必须把已验证的数据范围转换为服务端查询条件，禁止先查询全量数据再依靠前端过滤。

#### 结构化条件策略

授权应支持金额、数量、资源所有者、业务状态、有效时段、渠道和地区等受控条件。例如：

```text
采购单金额 <= 10000
帖子作者 = 当前用户
凭证状态 = 待复核
仓库属于当前用户被分配的仓库集合
```

第一阶段优先使用具有字段白名单、操作符白名单和类型校验的结构化条件，禁止直接保存和执行任意脚本或 SQL。

#### 字段级权限

记录级读取权限不代表可以读取或修改全部字段。成本价、工资、银行账号、证件信息等敏感字段必须分别定义读取、修改和脱敏策略；后端序列化与更新接口必须执行字段级限制。

#### 工作流与职责分离

发布审批、采购审批、财务复核和补卡审批属于业务流程，不应全部转换成静态 `UniauthGrant`。Uniauth 判断用户是否具备参与某类流程节点的资格，业务系统判断当前业务状态是否允许操作、当前节点是否轮到该用户，并执行以下职责分离规则：

- 制单人与审核人不得为同一人；
- 授权人不得在无上级批准时扩大自己的权限；
- 高风险操作必须满足规定的复核人数或审批层级；
- 已关闭会计期间、已发布版本或已结算单据不得仅因拥有普通修改权限而被改写。

#### 多维资源关系

单一 `parentResourceId` 资源树适合主题、栏目等单继承场景，但不能完整表达“用户属于部门、管理某仓库、帖子属于版块、单据同时属于门店和项目”等多维关系。后续应增加受控的资源关系或数据范围模型，并明确关系类型、方向、租户边界和有效期，避免把所有业务关系强行压入一棵资源树。

### 12.4 Uniauth 与业务系统职责边界

```text
Uniauth
├── 身份、租户、角色、组织和站点成员关系
├── 权限、资源、授权、统一决策、缓存和授权审计
└── 返回数据范围、字段限制和附加义务

业务系统
├── 定义本领域资源、稳定操作编码和业务上下文
├── 判断单据、内容、考勤或财务对象的当前状态
├── 执行查询过滤、字段脱敏、工作流和职责分离
└── 记录业务操作审计并调用 Uniauth 完成基础授权判断
```

认证、隐私同意、账号找回、验证码、反滥用、限流和业务审批分别属于身份安全、隐私、风控或工作流能力，不应通过增加 `UniauthGrant` 记录替代。

### 12.5 后续扩展验收要求

未来任一业务系统声明完成 Uniauth 权限接入前，至少验证：

1. 服务端查询已经应用数据范围，不存在前端过滤全量敏感数据；
2. 业务状态、金额或数量边界在后端执行；
3. 敏感字段具有独立读取、修改或脱敏控制；
4. 审批资格与当前工作流节点同时校验；
5. 职责分离规则不能被普通角色授权绕过；
6. 多维资源关系不会造成跨租户或越级访问；
7. 授权审计与业务操作审计可以通过请求追踪号关联。

## 13. 分阶段实施计划

### 阶段一：权限基础模型

1. 新增角色、组织、权限定义、资源、授权和审计表；
2. 建立管理员、Everyone 和普通用户种子数据；
3. 实现当前身份上下文；
4. 实现 `PermissionService.decide/can/require`；
5. 完成租户边界、ALLOW/DENY 和资源继承测试。

### 阶段二：用户管理接口接入

1. 为用户查询、新建、修改、删除接口增加后端鉴权；
2. 将表格按钮和菜单绑定权限编码；
3. 增加角色、组织和授权管理接口；
4. 实现授权变更审计和缓存失效。

### 阶段三：个性化设置接入

1. 提供当前用户权限快照接口；
2. 将设置模块区分读取和修改权限；
3. 用 `canAccess` 过滤无权模块；
4. 为页面布局、字段和按钮配置保存接口增加后端鉴权。

### 阶段四：主题权限接入

1. 将主题、模式和皮肤登记为资源；
2. 给主题 manifest 增加稳定资源键；
3. 权限快照返回允许的主题树；
4. 主题库按 `read/use` 区分隐藏、只读和可切换状态；
5. 后端校验用户保存的主题选择是否合法；
6. 实现主题失权后的安全回退。

### 阶段五：性能与多实例

1. 加入权限版本缓存；
2. 加入跨实例缓存失效事件；
3. 建立授权命中率、拒绝率和计算耗时指标；
4. 对大组织树、大角色集和大量主题资源做性能测试。

### 阶段六：跨业务授权扩展

1. 增加数据范围、字段限制和附加义务的决策结果；
2. 建立结构化条件白名单及安全求值机制；
3. 建立业务资源关系模型并验证租户边界；
4. 选择论坛或网站发布作为首个业务接入样板；
5. 在进销存、考勤接入前完成组织和数据范围回归；
6. 在财务接入前完成金额条件、职责分离、字段脱敏和不可抵赖审计专项验证。

## 14. 测试要求

### 14.1 单元测试

- 无授权默认拒绝；
- Everyone、角色、组织和用户授权合并；
- `DENY` 优先于 `ALLOW`；
- 过期授权不生效；
- 父资源继承与子资源显式覆盖；
- 未知权限编码拒绝；
- 平台管理员策略仅在明确条件下放行。

### 14.2 真实数据库集成测试

- 租户内用户、角色、组织和授权关系查询；
- 跨租户主体与资源不能建立授权；
- 授权批量保存事务回滚；
- 权限版本号和缓存失效；
- 角色或组织停用后的权限变化；
- 主题、模式和皮肤资源树授权。

### 14.3 Web 回归测试

- 未认证返回 401；
- 无权调用返回 403；
- 跨租户资源不泄露；
- 前端隐藏按钮后，手工请求仍被后端拒绝；
- 只读设置可见但不可保存；
- 无权主题不显示；
- 可见但不可用主题不能切换；
- 当前主题失权后回退到允许的默认主题；
- 中文、英文、日文切换不改变权限和当前允许主题状态。

## 15. 第一版验收标准

满足以下条件才可认为第一版权限实现完成：

1. 权限事实来自后端数据库，不来自前端静态 JSON；
2. 前端和后端使用同一稳定权限编码；
3. 用户接口、设置保存接口和主题选择保存接口均有后端鉴权；
4. 用户、角色、组织、Everyone 与资源继承规则均有自动化测试；
5. 所有查询和授权写入都受 `tenantId` 约束；
6. 主题能细分到主题、模式和皮肤三级授权；
7. 权限修改能及时使缓存和前端快照失效；
8. 所有授权变更均可审计；
9. 前端隐藏不被当作安全边界；
10. 权限服务异常时默认拒绝，不出现临时全量放行。

## 16. 结论

Uniauth 应保留 TRS“主体—资源—操作”和“前端裁剪、后端复核”的核心思路，同时用字符串权限编码、显式 ALLOW/DENY、租户隔离和资源树替换旧位图实现。

这套模型既能覆盖用户、角色、组织、菜单和按钮，也能自然覆盖当前正在扩展的主题、深浅模式、颜色皮肤、页面布局、字段显示和个性化设置。新增主题或组件时只需要登记资源键和权限编码，无需再次发明一套独立权限逻辑。

对于进销存、论坛、网站发布、财务管理、考勤管理和普通网站用户等后续场景，本方案应作为统一授权基础继续复用；涉及数据范围、业务条件、字段敏感性、工作流和职责分离时，必须按第 12 节扩展并由业务系统执行最终约束，不得把基础 RBAC 或前端界面裁剪误当作完整业务安全边界。
