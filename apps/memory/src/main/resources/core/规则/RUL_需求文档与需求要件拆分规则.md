# 需求文档与需求要件拆分规则

## 需求分析师职责

- 同一个需求分析师 Agent 负责整理需求文档并把已确认需求拆分为需求要件，不建立独立的需求要件分析师角色。
- 需求文档必须保留用户目标、范围、非范围、参与者、场景、约束、依赖、风险、验收条件、开放问题和来源事实。
- 重大业务选择未确认时必须标记阻断，不得由需求分析师代替用户决定。

## 功能拆分单位

- 一个需求要件只对应一个能够独立开发、调用、测试和验收的功能。
- 页面交互以一个按钮触发的一次完整业务动作作为一个功能；同一按钮涉及的页面、接口、业务逻辑和数据库处理不得按技术层重复拆分。
- 批处理以一个可独立启动的批处理入口及其一次完整调用作为一个功能。
- 监听程序以一个独立事件接收入口及其一次完整处理调用作为一个功能。
- 没有按钮的 API 或命令入口，以一次可独立调用并产生可验证结果的业务动作作为一个功能。
- 一个入口包含多个可独立发布或独立验收的业务动作时必须继续拆分；仅为实现同一动作服务的内部步骤不得伪装成多个需求要件。

## 要件内容

- 每项要件必须具有稳定 ID、来源需求、功能名称、触发入口、输入、处理、输出、异常、前置条件、验收标准和验证方式。
- 每项要件必须能够独立交给后续架构、详细设计、实现和测试角色，不依赖隐含上下文才能理解。
- 重复功能必须合并并记录替代关系；无法独立验证或缺少来源的条目不得进入架构阶段。
