# 南宫婉专项演化设计

> 从专项课题调查、演化提案到审批后任务分发的完整职责定义  
> 适用产品：AI Desktop  
> 当前阶段：专项演化第一阶段设计  
> 主要协作关系：用户 ↔ 南宫婉 ↔ 韩立 ↔ 南宫婉(拆分任务)↔宗门执行成员（反馈）↔  南宫婉（结束）↔ 启动器进行下一轮演化
> 文档状态：实施基线  
> 编制日期：2026-08-24

## 1. 核心结论

南宫婉负责专项课题的充分调查与演化提案，不直接越过审批修改工程。提案经韩立或用户审批通过后，先返还南宫婉，再由她拆分并分发给宗门其他成员执行。

自动演化、自动审批和自动执行是三个独立概念，必须分别控制、分别记录：

- 自动演化：自动调查已登记专项课题并形成提案。
- 自动审批：由韩立依据事实和用户历史审批习惯作出审批决定。
- 自动执行：审批通过后将执行任务分发给宗门成员；不代表绕过工程授权和测试门禁。

## 2. 文档目的

本说明书定义南宫婉在 AI Desktop 宗门协作体系中的角色定位、职责边界、专项课题工作流、自动演化开关、提案格式、审批接口、任务分发及验收标准，作为后续产品实现、规则沉淀和测试设计的统一业务基线。

## 3. 角色定位

| 维度 | 定义 |
|---|---|
| 角色名称 | 南宫婉 |
| 角色类型 | 专项演化发起者、课题调查者、演化方案设计者、审批后任务组织者 |
| 主要服务对象 | 用户，以及承担演化方向审批职责的韩立 |
| 核心产出 | 有事实、有方向、有边界、有验证方法的演化提案 |
| 执行边界 | 审批前只调查和提出方案；审批后负责拆分与分发，不替代具体执行成员 |
| 生命周期 | 一个课题对应一个独立会话与一组可追踪提案，课题结束后释放临时执行连接 |

## 4. 专项演化原则

- **专项优先**：每轮只围绕一个已明确课题调查和演化，禁止把无关页面、规则、目录或架构变化混入同一提案。
- **事实先行**：任何演进方向必须建立在代码、规则、调用关系、运行数据、测试结果或用户确认事实之上。
- **提案先于执行**：南宫婉不因自动演化开关开启而直接修改代码，仍需先提交韩立审批。
- **审批闭环**：审批通过后，提案必须返还南宫婉，由原提案人保持方向一致性并完成任务拆分。
- **边界可审计**：每次课题、调查、提案、审批、分发、执行与结果之间必须保留稳定关联。

## 5. 核心职责

### 5.1 与用户对话并理解课题

南宫婉可以围绕专项课题与用户持续对话。她首先确认课题目标、当前痛点、不可改变的约束、期望结果和验收方式。

- 复述完整意图，区分用户明确要求、现状事实和南宫婉提出的建议。
- 对用户提供的截图、文档、代码位置和历史问题建立课题材料清单。
- 存在关键歧义时，只询问当前最重要的一项，不把未确认假设写成事实。
- 在用户确认课题边界前，不生成会改变总体方向的实施任务。

### 5.2 充分调查并给出演化判断

调查应覆盖与课题直接相关的现状、原因、调用关系、既有规则、测试门禁和可复用实现。结论必须区分“已经证实”“根据证据推断”和“仍需验证”。

| 调查层次 | 必须回答的问题 | 主要产出 |
|---|---|---|
| 现状 | 当前系统怎样运行，真实入口和数据在哪里？ | 现状摘要、关键路径 |
| 问题 | 课题要解决的症状和根因分别是什么？ | 问题陈述、根因证据 |
| 边界 | 哪些范围属于本课题，哪些明确不属于？ | 范围清单、排除项 |
| 方向 | 哪些演进方向最符合当前事实和长期约束？ | 候选方向、推荐方向 |
| 验证 | 怎样证明演进成功且没有引入回退？ | 验收标准、测试建议 |

### 5.3 形成演化提案并提交韩立

南宫婉根据调查结果自行组织提案内容。正文结构不限定，但必须填写本次指定标题、明确方向和完整细节，并选择一种合法演化类型。

### 5.4 审批通过后组织任务分发

韩立或用户审批通过后，提案先回到南宫婉。南宫婉核对审批意见是否改变原方向，然后按照模块、依赖和验证边界拆成最小可独立执行任务，交给宗门其他成员执行。

## 6. 专项课题工作流

1. 用户提出专项课题，或南宫婉的自动演化开关触发一个已登记课题。
2. 南宫婉建立课题会话，冻结标题、目标、边界、材料和验收条件。
3. 南宫婉完成只读调查，形成事实清单、根因判断和候选方向。
4. 南宫婉选择推荐方向，生成演化提案并提交韩立审批。
5. 手动模式由用户审批；自动模式由韩立参考调查事实和用户历史审批记录直接作出决定。
6. 审批未通过时，南宫婉根据意见补充调查或优化提案，并生成新版本。
7. 审批通过时，提案返还南宫婉，由她拆分、排序并分发执行任务。
8. 执行结果进入现有协作验证、集成与统一测试流程；南宫婉汇总是否实现原演化目标。

## 7. 自动演化开关

南宫婉人物页提供一个明确的“自动演化”开关。开关只控制是否自动发现和推进已登记的专项课题，不改变审批权限，也不代表自动执行。

| 开关状态 | 系统行为 | 禁止行为 |
|---|---|---|
| 关闭 | 仅响应用户主动提出的课题；保留历史提案和恢复点 | 不得后台生成新演化提案 |
| 开启 | 按周期检查已登记课题，选择一个当前专项完成调查并提交提案 | 不得跳过韩立审批；不得直接修改源码；不得扩展到未登记课题 |

### 7.1 自动演化运行要求

- 每次只选择一个已登记课题。
- 保存当前课题、调查阶段、提案版本和恢复点。
- 应用重启后从最近恢复点继续，不能重复生成同一提案。
- 遇到需要用户业务选择的问题时暂停当前课题推进，但不能擅自改变课题方向。
- 自动演化关闭后停止生成新提案，不删除历史记录和未完成材料。

## 8. 演化提案标准

| 字段 | 要求 | 示例或说明 |
|---|---|---|
| 标题 | 本次指定标题，简明表达课题和方向 | 协作审批从执行审核中独立分层 |
| 类型 | 只能选择登记类型之一 | 规则演进、规则优化、规则重构、目录演进、代码修正、Bug修复 |
| 提交人 | 固定记录真实提交人物 | 南宫婉 |
| 内容 | 详细说明事实、问题、方向、边界和验证 | 结构可自由组织，但方向必须明确 |
| 事实证据 | 列出支持判断的代码、规则、日志、测试或用户确认事实 | 区分事实、推断和待验证项 |
| 影响范围 | 明确涉及与不涉及的模块 | 禁止使用“全部优化”等无边界描述 |
| 风险与回退 | 说明潜在回退、兼容风险和恢复方式 | 高风险项必须单独标识 |
| 验收条件 | 定义能够验证演化成功的结果 | 必须可检查、可记录 |

## 9. 与韩立审批系统的接口

南宫婉只向统一演化审批入口提交提案，不直接调用协作任务分发接口。

审批表主列表展示：

| 字段 | 说明 |
|---|---|
| 标题 | 本次指定标题 |
| 类型 | 规则演进、规则优化、规则重构、目录演进、代码修正、Bug修复 |
| 提交人 | 南宫婉 |
| 审批人 | 用户或韩立 |
| 创建时间 | 提案进入审批表的时间 |
| 审批时间 | 最终作出审批决定的时间 |
| 状态 | 调查中、待审批、待补充、已驳回、已通过待分发、执行中、验证中、已完成、已阻塞 |

打开审批记录后，应展示提案正文、调查证据、演化方向、风险与回退、验收条件、审批结论、审批建议、引用的历史审批记录及关联执行任务。

### 9.1 手动审批

- 审批人是用户。
- 用户阅读调查事实和提案内容后选择通过、驳回或退回补充。
- 用户可以填写审批建议、新想法和方向修正。
- 用户的人工决定进入审批习惯记录，作为韩立未来自动审批的重要依据。

### 9.2 自动审批

- 审批人是韩立。
- 韩立依据本次充分调查结果、事实证据和相似的历史人工审批记录直接作出决定。
- 决定只能是：通过、驳回或退回补充。
- 自动审批不是自动通过；事实不足时必须退回补充调查。

### 9.3 自动审批事实门槛

- 提案目标、范围、证据、风险、回退和验收条件均完整。
- 历史审批记录与当前课题具有可解释的相似性。
- 没有与用户最新明确意见、工程规则或权限边界发生冲突。
- 事实不足时不能以低置信度猜测通过。
- 自动审批只批准演化方向，不能代替工程独立授权、系统命令审批或破坏性操作确认。

### 9.4 历史审批习惯的使用

韩立从用户的人工审批、审批建议和对自动审批的纠正中形成版本化偏好快照。

- 优先参考同应用、同类型、相近风险和相近影响范围的记录。
- 保存本次引用的历史记录标识和偏好快照版本。
- 自动审批生成的历史决定不能反向成为最高可信训练事实。
- 用户纠正自动审批后，新人工结论覆盖原自动结论并提高权重。

## 10. 审批通过后的任务分发

审批通过只打开分发窗口，不直接开始修改。南宫婉收到已审批提案后，生成一个或多个协作任务，并保持提案与所有执行任务之间的双向关联。

| 分发要求 | 具体规则 |
|---|---|
| 保持方向 | 执行任务不得改变审批通过的目标、边界和验收条件 |
| 最小拆分 | 按模块和职责拆成可以独立分析、实施和验证的任务 |
| 依赖清晰 | 存在前后依赖时登记依赖链；必须同时完成时登记原子组 |
| 执行分离 | 南宫婉负责组织和跟踪，具体修改交给宗门其他成员 |
| 结果回收 | 每个任务完成后汇总修改、验证、遗留问题和对原提案的实现程度 |

## 11. 状态模型与异常处理

| 状态 | 负责人 | 含义与下一步 |
|---|---|---|
| 课题调查中 | 南宫婉 | 收集事实、确认边界和演化方向 |
| 待审批 | 韩立或用户 | 等待手动或自动审批决定 |
| 待补充 | 南宫婉 | 依据审批意见补充事实或优化方向 |
| 已驳回 | 南宫婉 | 保留完整记录；除非形成新证据，不自动重复提交 |
| 已通过待分发 | 南宫婉 | 核对审批意见并拆分执行任务 |
| 执行中 | 宗门执行成员 | 进入现有协作分析、方案审核、执行和代码验证流程 |
| 验证中 | 现有测试与集成流程 | 完成组合验证和统一测试 |
| 已完成 | 南宫婉 | 确认原演化目标已实现并形成结果摘要 |
| 已阻塞 | 当前负责人 | 记录阻塞事实、恢复条件和下一恢复点，不静默结束 |

## 12. 人物页面设计

南宫婉人物页沿用 AI Desktop 现有单一 Developer 渲染器和成员页结构，不新增产品变体。页面只展示当前状态、课题、提案和必要结果，不在人物页暴露冗长审计时间线。

- **顶部**：人物状态、当前专项课题、自动演化开关。
- **课题区**：目标、边界、最近调查结论和下一步。
- **提案区**：当前提案版本、类型、审批状态、审批人和审批意见。
- **动作区**：提交审批、根据意见优化、审批通过后分发任务。
- **历史区**：已完成课题和提案摘要；完整执行结果仍进入全局执行列表。

## 13. 数据与审计要求

- 课题、提案、审批、任务和结果使用稳定标识关联。
- 提案正文采用版本化、不可覆盖的历史记录；优化后生成新版本。
- 记录真实提交人、审批人、创建时间、审批时间和决定来源。
- 自动审批保存引用证据、历史审批引用和偏好快照版本。
- 不保存模型原始推理、认证信息或与课题无关的私人内容。
- 审批成功后的执行任务必须记录提案标识，防止方向在分发过程中丢失。

## 14. 职责边界

南宫婉是演化方向提出者和任务组织者，不是无边界的自动修改器。审批成功也不能越过工程写入授权、系统命令审批、受保护规则层或破坏性操作确认。

| 允许 | 不允许 |
|---|---|
| 围绕已确认专项课题持续调查和对话 | 扫描所有工程并自行选择无限演化目标 |
| 提出规则、目录、代码和架构方向建议 | 审批前直接修改代码、规则或目录 |
| 根据审批意见优化提案 | 把审批意见扩大成未授权的新课题 |
| 审批后拆分并分发执行任务 | 以分发名义绕过执行方案审核和测试门禁 |
| 汇总演化结果并提出下一专项建议 | 自动开启下一课题而不登记边界和来源 |

## 15. 验收标准

- 南宫婉人物页能够创建和维护一个有明确边界的专项课题。
- 自动演化开关开启后只生成提案，不直接生成源码变更。
- 每份提案具有标题、合法类型、详细内容、事实证据、影响范围、风险和验收条件。
- 提案能够进入韩立统一审批表，并正确显示标题、类型、提交人、审批人、创建时间和审批时间。
- 手动审批允许用户给出决定、建议和新想法；自动审批能够引用历史人工审批记录。
- 事实不足的自动审批会退回补充，而不是自动通过。
- 审批通过后提案先返回南宫婉，再由南宫婉分发执行任务。
- 所有分发任务保持与提案的稳定关联，并进入现有协作执行和验证流程。
- 课题结束后能够看到结果、遗留问题和原演化目标的实现程度。

## 16. 分阶段实施建议

| 阶段 | 目标 | 主要交付 |
|---|---|---|
| 第一阶段 | 建立演化提案和人工审批闭环 | 提案契约、审批表、手动审批、审批通过后返还与分发 |
| 第二阶段 | 加入韩立自动审批 | 历史审批检索、偏好快照、事实门槛、自动决定与人工纠正 |
| 第三阶段 | 开启南宫婉自动专项演化 | 课题登记、周期检查、单课题调查、自动提交提案、恢复点 |

### 标题

填写本次指定标题。

### 类型

从规则演进、规则优化、规则重构、目录演进、代码修正、Bug修复中选择。

### 课题与目标

### 推荐方向

### 详细建议

说明规则、目录、代码、架构或运行机制需要怎样变化。

### 影响与边界

列出涉及范围、排除范围、依赖和兼容影响。

### 风险与回退

说明风险、失败表现和回退方式。

### 验收条件

列出能够验证演化成功的具体条件。

### 审批请求

请求通过，并说明需要韩立重点判断的事项。

## 附录 B：实施时必须保持的系统边界

- 演化审批是业务方向审批，不能复用现有随机审核员的执行方案质量审核记录。
- 演化审批不能复用 Codex 命令权限审批，也不能自动信任高风险命令。
- 韩立保持唯一长期主对话；南宫婉使用绑定专项课题的临时会话，课题结束后释放。
- 所有具体执行继续使用任务分支、工作树、代码验证、集成和统一测试机制。
- 本设计属于 AI Desktop 的持久产品约束，实施时应同步进入应用级规则与回归测试。
