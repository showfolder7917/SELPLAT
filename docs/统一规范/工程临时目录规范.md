# 工程临时目录规范

本规范只定义源码之外的缓存、构建、临时和归档数据边界。Node.js/TypeScript 应用源码、配置、脚本、测试和包边界见同目录的《Node工程结构标准》。

本文档是 SELPLAT 开发态 `build/`、`cache/`、`OPTION/temp/` 目录边界的权威说明。三者必须保持独立，不得合并、互相替代或指向同一物理目录。

## 1. 工程名解析

`<工程名>` 表示当前正在操作的真实工程名。例如当前工程是 `ai-desktop` 就使用 `ai-desktop`，当前工程是 `ai-factiory` 就使用 `ai-factiory`。

工程名必须从当前应用登记信息或工程清单中解析，禁止在公共程序中固定写死 `ai-desktop`，也禁止把任意路径直接作为工程名。

## 3. 三类目录职责协议

| 目录 | 核心职责 | 数据特征 | 不得存放 |
| --- | --- | --- | --- |
| `build/<工程名>/` | 保存由源码和构建配置产生的输出 | 可以通过同一源码、锁定依赖和工具链重新构建 | 依赖缓存、下载原件、待执行任务、运行锁和未归档证据 |
| `cache/<工程名>/` | 保存为加速构建或运行而复用的资源 | 可以由明确来源重新生成或重新获取 | 唯一正式成果、任务状态、审计记录和无来源的唯一离线文件 |
| `OPTION/temp/<工程名>/` | 保存待执行、运行中和尚未归档的任务现场 | 具有任务或测试生命周期，可能包含恢复所需状态 | 永久源码、长期依赖缓存、正式构建产物和历史查询记录 |

目录归属必须根据数据的来源、用途和生命周期判断，不得只根据扩展名、文件大小或“看起来像临时文件”判断。

### 3.1 禁止合并

- `build/`、`cache/`、`OPTION/temp/` 必须是三个独立的物理根目录。
- 禁止通过配置、符号链接、Windows Junction 或其他别名让两类目录指向同一位置。
- 数据可以按生命周期在目录间流转，但每一时点必须只有一个明确归属。
- 任务终态记录必须从 `OPTION/temp/` 归档到 `log/`；禁止使用 `build/` 或 `cache/` 充当归档目录。

## 4. 临时目录约束

`OPTION/temp/<工程名>/` 下只允许存在两个一级目录：

```text
执行日志/
临时材料/
```

禁止直接在应用临时根下建立 `screenshots`、`interaction`、`test-evidence`、`downloads`、`schema-temp`、`playwright-output` 或任意任务名称目录。

- 执行过程数据进入 `执行日志/`。
- 截图、证据、解压、转换等一次性材料进入 `临时材料/`。
- 暂时无法归类的文件只能进入 `临时材料/其他/`，任务结束前必须重新判断归属并清理。

## 5. 执行生命周期

```text
OPTION/temp/<工程名>/执行日志/待执行/
        ↓ 开始执行，原子移动
OPTION/temp/<工程名>/执行日志/运行中/
        ↓ 任务结束，提取摘要、事件、结果和证据清单
log/<工程名>/归档日志/对应归档目录/
        ↓ 确认归档完整
清理 OPTION/temp 中对应的运行材料
```

必须遵守：

1. 待执行任务开始时必须原子移动到“运行中”。
2. 成功、失败、取消、驳回终止和部分完成都属于终态，都必须归档。
3. 只有归档写入成功并完成完整性检查后，才能清理运行中材料。
4. 归档失败时，原始材料必须留在“运行中”等待恢复。
5. 程序异常退出后，必须能够通过执行锁和任务标识恢复运行中任务。
6. 禁止先删除临时材料，再尝试生成归档。

## 6. 目录职责边界

### `apps/<工程名>/`

只保留正式源码、正式测试代码、永久脚本、配置文件、依赖清单和工程说明。禁止保存编译产物、测试结果、执行日志、截图、临时证据、下载或解压文件、运行缓存和历史归档。

### `cache/<工程名>/`

只保存可以重新生成或从明确来源重新获取的数据，包括依赖、下载、转换、Playwright 浏览器和编译工具缓存。删除该目录不得造成源码、审计记录或正式结果丢失。

清理前必须区分“可选性能缓存”和“当前离线构建所需缓存”。SELPLAT 默认离线构建，`cache/gradle-user-home/`、`cache/gradle-project-cache/` 和 `cache/cache-jars/` 等目录的文件即使属于可重建缓存，删除后也可能使当前机器在离线状态下无法立即构建。批量清理前必须确认重建命令、资源来源和离线回退均可用。

### `build/<工程名>/`

只保存可以通过源码重新构建的编译结果、前端产物、主进程产物、Sites 产物、安装包和构建报告。不同工程必须使用独立工程名根目录。

清理前必须确认没有构建、测试、运行或打包进程正在使用目标，需要交付或归档的产物已转移，且源码、锁定依赖和工具链足以重建。

### `OPTION/temp/<工程名>/`

只保存待执行任务、运行中任务、执行锁、恢复状态、尚未归档的测试材料和可丢弃的一次性材料。该目录不是历史查询来源。

禁止清理待执行任务、运行中任务、有效执行锁或尚未完成归档与完整性检查的材料。只有在确认没有活动任务，并且需要保留的终态记录已完整归档后，才能清理对应任务材料。

### `log/<工程名>/归档日志/`

保存需要长期保留、支持查询和审计的终态执行、测试、协同、审批和诊断数据。归档内容禁止保存认证令牌、密码、完整隐私数据和模型原始推理。

### Gradle 路径映射

- `gradle/` 只保存随源码提交的 Wrapper 配置和 JAR，它不是 `cache/` 的替代目录。
- Gradle 构建输出进入 `build/<project-path>/`。
- Gradle 用户缓存、项目缓存和离线 JAR 分别进入 `cache/gradle-user-home/`、`cache/gradle-project-cache/` 和 `cache/cache-jars/`。
- `.gradle/` 不是 SELPLAT 的标准项目缓存根；包装脚本和 IDE 必须优先使用 `cache/gradle-project-cache/`，不得把 `.gradle/` 与受 Git 跟踪的 `gradle/` 合并。

## 7. 依赖目录约束

如果要求 `apps/<工程名>/` 完全不保留生成数据，依赖安装到：

```text
cache/<工程名>/dependencies/<lockHash>/
```

执行构建或测试时可以建立受控的临时依赖链接，但必须满足：

1. 依赖与当前锁文件哈希完全一致。
2. 不同锁文件不得复用同一个依赖目录。
3. 临时依赖链接不得提交到 Git。
4. 执行、验证或打包结束后必须移除临时链接。
5. 依赖下载失败属于环境问题，不得记为业务审核驳回。
6. 禁止在多个工程之间共享未经锁文件验证的 `node_modules`。

## 8. 命名和安全约束

- `<工程名>` 必须来自工程登记或应用清单。
- `<工程名>`、`<taskId>`、`<runId>` 和 `<approvalId>` 必须经过安全格式校验。
- 标识只能包含字母、数字、短横线和下划线。
- 标识禁止包含 `/`、`\`、`..` 或绝对路径。
- 最终路径必须验证仍位于对应工程根目录内。
- 不同任务、测试和工程不得覆盖彼此的数据。

## 9. 完成标准

- `apps/<工程名>/` 不存在运行数据和构建产物。
- 所有缓存进入 `cache/<工程名>/`。
- 所有构建产物进入 `build/<工程名>/`。
- 所有待执行、运行中和一次性材料进入 `OPTION/temp/<工程名>/`。
- `build/`、`cache/` 和 `OPTION/temp/` 不存在物理合并、路径别名或跨职责混放。
- `OPTION/temp/<工程名>/` 下不存在未分类的散落目录。
- 所有终态数据进入 `log/<工程名>/归档日志/`。
- 归档按年月和任务标识隔离。
- 归档成功后才清理临时材料。
- 工程名由当前工程动态解析，不在公共逻辑中固定写死。
