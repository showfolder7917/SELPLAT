# Java 规范目录蓝图

## 1. 目的

本文件用于定义：

- `SELPLAT` 中给 AI 使用的 Java 规范目录应该如何分层
- 这套目录如何同时适用于权限、考勤、规则协议、CRM、CMS 以及后续新增模块
- 哪些文档属于平台级通用规范
- 哪些文档属于某类模块的基线规范
- 哪些文档属于迁移步骤、同步修正和模块接入规则

本文件是通用蓝图，不等同于某一个模块私有文档。

## 2. 结论

Java 规范目录不应继续散落在：

- `docs/architecture`
- `apps/<module>/doc`
- 单个模块 README

更合适的真实落点应统一进入：

```text
SELPLAT/ai-standards/
```

并在其下新增独立的 Java 规范目录。

推荐真实目录：

```text
SELPLAT/ai-standards/standards/java/
```

这样分层的意义：

1. `docs/architecture` 继续放高层蓝图。
2. `ai-standards` 继续承接给 AI 使用的规范、修正索引和迁移说明。
3. Java 规范可以长期扩展，不会和主题、模块、数据库修正索引混在一起。

## 3. 目录定位

这套 Java 规范目录的定位不是“某个模块说明”，而是：

- 给 AI 执行 Java 迁移、重构、新增模块时看的统一规范入口
- 给后续每个模块复用的编码与分层规范
- 给“以某个模块为样板抽出共性”的基线文档提供容器

因此，它必须是平台级目录，而不是模块级目录。

## 5. 各层职责

### 5.1 `platform/`

这里放平台级 Java 通用规范。

这部分内容与具体业务无关，应适用于：

- `uniauth`
- `attendance`
- `rule-engine`
- `crm`
- `cms`
- 后续新模块

应该放：

- 包结构规范
- 命名规范
- 注释规范
- 异常处理规范
- 返回结构规范
- 主键与业务编号规范

不应该放：

- 某个模块独有 DTO 字段
- 某个模块独有表结构
- 某个业务模块专有术语

### 5.2 `backend/`

这里放 Java 后端分层代码规范。

重点覆盖：

- Controller
- Service
- ServiceImpl
- DAO
- 按需启用的 Mapper XML
- Domain 模型
- 事务边界
- 多数据源

这部分是你后续真正写代码时最常用的一层。

### 5.3 `migration/`

这里放模块迁移规范。

这层不讲“某个类怎么写”，而讲：

- 从旧工程抽模块时先做什么
- 哪些目录先建
- 哪些边界先切
- 迁移后要联动检查哪些地方

它适合和 `ai-standards/sync` 配合使用。

### 5.4 `baselines/`

这里放“样板模块基线”。

注意：

- 这里不是平台通用规则本体
- 这里是拿现有成熟模块提炼样板

例如：

- `uniauth` 作为权限工程样板
- `attendance` 作为考勤工程样板

这层的作用是：

- 给 AI 一个“照着现有成熟模块写”的参考点
- 解决“通用规则说得太抽象，落不到具体写法”的问题

### 5.5 `sync/`

这里放 Java 规范自身的同步修正索引。

例如：

- 改了 DAO 规范后，还要同步哪些文档
- 调整主键策略后，还要同步哪些说明
- 新增一个样板模块后，还要更新哪些索引

## 6. 平台通用规范与样板基线的边界

这是这套目录最关键的边界。

### 平台通用规范

适合写：

- 所有模块都必须遵守的编码约束
- 所有模块都适用的分层规则
- 与具体业务无关的通用写法

例如：

- DAO 不写跨领域大而全接口
- 仅实际使用专用 XML SQL 的 Mapper XML 与 DAO 一一对应
- Service 不手工生成主键
- Controller 不直接拼装持久化 SQL 参数

### 样板基线规范

适合写：

- 某个模块目前已经存在、且实践成熟的组织方式
- 某个模块当前的包结构样板
- 某个模块内 DAO / Service / Domain 如何拆分

例如：

- `uniauth/user/dao`
- `uniauth/role/dao`
- `uniauth/menu/dao`

这层是“参考实现”，不是“唯一正确实现”。

## 7. 为什么不能只保留 `uniauth`

你现在是以权限工程作为起点，这没问题。  
但这套目录蓝图必须设计成通用的，原因是：

1. 后续还要迁移考勤工程。
2. 后续会有规则协议工程。
3. CRM、CMS 和别的业务模块也会进来。
4. 如果目录从一开始就绑定 `uniauth`，后续很容易误把权限工程私有习惯当成全平台唯一标准。

所以正确做法是：

- 平台共性规则放 `platform/` 和 `backend/`
- `uniauth` 只作为 `baselines/` 里的第一套样板

## 8. DAO 规范在整套目录中的位置

如果后续先从 DAO 开始写规范，推荐真实位置是：

```text
SELPLAT/ai-standards/standards/java/backend/13-DAO代码规范.md
```

原因：

- DAO 规范是平台通用后端分层规范的一部分
- 不应直接挂在 `uniauth` 下
- 但可以在 DAO 规范文档中引用 `baselines/uniauth/DAO样板说明.md`

也就是说：

- `backend/13-DAO代码规范.md`
  写“规则”
- `baselines/uniauth/DAO样板说明.md`
  写“参照样板”

这个分层最稳。

## 9. 推荐编号规则

建议 Java 规范目录统一编号，便于 AI 和人按顺序检索。

推荐规则：

- `00-09`
  平台总则
- `10-19`
  后端分层代码规范
- `20-29`
  迁移规范
- `30-39`
  样板模块说明
- `40-49`
  同步修正与检查清单

这样后续扩展不会乱。

## 10. 推荐最小首批落地顺序

后续真正开始建 Java 规范目录时，建议按这个顺序：

1. `README.md`
2. `索引.md`
3. `platform/00-Java总则.md`
4. `backend/13-DAO代码规范.md`
5. `backend/14-MapperXML规范.md`
6. `backend/11-Service代码规范.md`
7. `baselines/uniauth/DAO样板说明.md`
8. `sync/Java规范修正索引.md`

这样做的原因：

- 你现在最急的是 DAO 起手规范
- DAO 一旦定了，按需启用的 Mapper XML、Service 的边界才更好写

## 11. 与 `docs/architecture` 的关系

这份蓝图文档放在：

```text
docs/architecture/
```

是因为它当前还处于“目录设计阶段”。

真正的规范目录和规范文件，应放到：

```text
ai-standards/standards/java/
```

所以两者关系是：

- `docs/architecture`
  放“Java 规范目录应该怎么设计”
- `ai-standards/standards/java`
  放“真正给 AI 用的 Java 规范文件”

## 12. 一句话定版

`SELPLAT` 的 Java 规范目录应设计为一套平台级通用目录，真实落点放在 `ai-standards/standards/java/`，按 `platform`、`backend`、`migration`、`baselines`、`sync` 五层分开；`uniauth` 只作为第一套样板基线，而不是整套规范的唯一归属。
