# AI 修正索引目录蓝图

## 1. 目的

本文件用于定义：

- `SELPLAT` 内是否应该新增面向 AI 的修正索引目录
- 这个目录建议放在哪里
- 它与 `docs/architecture`、普通 `README`、执行文档之间的职责边界
- 当主题、模块、数据库工程发生新增、删除、重构时，AI 应如何找到需要同步修正的文档索引

本蓝图当前只定义结构和规则，不直接创建目录。

## 2. 结论

建议新增一个专门面向 AI 的修正索引目录，而且应该放在 `SELPLAT` 工程根目录下独立存在。

推荐目录名：

```text
ai-standards
```

不建议直接并入：

- `docs/architecture`
- `shared/frontend/theme`
- `SELFMEMORY/OPTION`

原因是这三类位置分别承担：

- 工程架构说明
- 开发说明
- 会话期执行内务

而 AI 修正索引的职责是：

- 为后续 AI 执行提供稳定的同步修正入口
- 记录某类变更后必须联动修改的文件索引
- 约束 AI 不再按旧描述执行

它属于“工程内长期有效的 AI 导航层”，应该单独分层。

## 3. 推荐位置

推荐路径：

```text
SELPLAT/ai-standards/
```

这个位置优于放进 `docs/architecture` 的原因：

1. `docs/architecture` 更适合存放架构事实，而不是 AI 执行导航。
2. `ai-standards` 可以按主题系统、模块系统、数据库系统持续扩展，不会污染架构目录。
3. 后续 AI 只要命中“增删改结构后要同步哪些文档”这一类任务，就可以优先查这里。

## 4. 与其他文档的职责边界

### 4.1 `docs/architecture`

这里放工程事实、架构分层、长期结构蓝图。

例如：

- 主题家族和皮肤如何分层
- 模块工程和宿主如何分层
- 数据库工程与运行库文件如何分离

### 4.2 `ai-standards`

这里放“发生某类变更后，AI 必须同步修正哪些文件”的导航规则。

例如：

- 新增皮肤后，哪些清单、说明、入口必须一起改
- 删除模块后，哪些 manifest、架构说明、README 必须一起清理
- 调整数据库工程目录后，哪些架构文档和说明索引必须同步

### 4.3 各目录 README

这里放面向开发者的局部说明。

README 可以描述：

- 当前目录放什么
- 当前目录不放什么
- 推荐子结构

但不适合作为 AI 的主修正索引入口，因为：

- 信息容易分散
- 不利于汇总某一类动作的联动修正范围

### 4.4 `SELFMEMORY/OPTION`

这里适合会话期临时修正提示、执行中间状态和短期提醒。

不适合作为 `SELPLAT` 工程内长期事实来源。

## 5. 推荐目录结构

```text
SELPLAT/
└─ ai-standards/
   ├─ README.md
   ├─ 索引.md
   ├─ 主题系统修正索引.md
   ├─ 模块系统修正索引.md
   ├─ 数据库工程修正索引.md
   └─ 预览入口修正索引.md
```

## 6. 各文件职责

### 6.1 `README.md`

用于说明这个目录的定位。

至少应包含：

- 这是给 AI 和自动化修改流程看的
- 当任务涉及新增、删除、重构时，应先查对应修正索引
- 这里记录的是“同步修正范围”，不是业务功能说明

### 6.2 `索引.md`

用于总览当前有哪些修正索引文件。

建议按系统分流：

- 主题系统
- 模块系统
- 数据库工程
- 预览入口

### 6.3 `主题系统修正索引.md`

用于处理：

- 新增皮肤
- 删除皮肤
- 新增主题家族
- 删除主题家族
- 调整主题预览入口结构

### 6.4 `模块系统修正索引.md`

用于处理：

- 新增模块工程
- 删除模块工程
- 模块改名
- 宿主与模块注册关系变化

### 6.5 `数据库工程修正索引.md`

用于处理：

- 新增 `data-h2` 一类数据库工程
- 调整 schema、seed、migration 分层
- 调整运行数据库文件与源码目录的边界

### 6.6 `预览入口修正索引.md`

用于处理：

- 静态预览页结构调整
- 左右布局、皮肤墙、卡片墙这类预览交互变化
- 需要同步修改哪些说明文档和架构文档

## 7. 主题系统修正模型

主题系统是当前最先落地、最容易频繁变动的一类内容，因此建议最先建立完整修正索引。

### 7.1 新增皮肤时必须同步检查

至少检查：

- `shared/frontend/theme/glass-theme/manifest/theme-family.json`
- `shared/frontend/theme/glass-theme/README.md`
- `shared/frontend/theme/README.md`
- `shared/frontend/theme/glass-theme/index.html`
- `docs/architecture/玻璃主题家族与皮肤分层架构蓝图_2026-06-09.md`

如果皮肤数量、分组方式、默认皮肤或预览模式发生变化，也应同步修正：

- 当前主题家族说明
- 预览入口行为说明
- 架构索引中对该文档的摘要说明

### 7.2 删除皮肤时必须同步检查

至少检查：

- `manifest` 中是否已移除皮肤名
- `index.html` 是否已移除入口
- `README` 中是否还有旧皮肤描述
- 架构文档里是否还保留旧皮肤示例

### 7.3 调整预览入口结构时必须同步检查

例如从“皮肤墙 + 下方预览”改成“左侧列表 + 右侧预览”时，至少应同步：

- `shared/frontend/theme/glass-theme/index.html`
- `shared/frontend/theme/glass-theme/README.md`
- `shared/frontend/theme/README.md`
- 若架构文档明确描述了旧预览方式，则同步更新对应架构文档

### 7.4 新增主题家族时必须同步检查

至少检查：

- `shared/frontend/theme/README.md`
- 新主题家族自己的 `README.md`
- 新主题家族自己的 `manifest`
- `docs/architecture` 下是否需要新增该家族蓝图
- `索引.md` 中是否补充新主题家族对应的修正入口

## 8. 模块系统修正模型

当 `apps/<module>` 新增、删除或改名时，AI 不应只改目录本身，还应检查：

- 模块自身 `manifest`
- 平台根 `README`
- `apps/README.md`
- 相关模块自己的 `README`
- 若属于架构层新增能力，是否要在 `docs/architecture` 增补蓝图

如果模块参与宿主装配，还应检查：

- 宿主注册表
- 模块发现入口
- 平台启动说明

## 9. 数据库工程修正模型

当数据库能力被视为独立工程时，AI 应同时关注两层：

- 工程层：如 `apps/data-h2`
- 运行层：如 `runtime/data/h2`

因此数据库修正索引应明确：

- 变更 schema、seed、migration 时改哪些说明
- 调整运行库文件路径时改哪些说明
- 调整数据库工程命名时改哪些架构文档

## 10. 推荐记录格式

后续每一份修正索引文档都建议固定采用这四段：

1. 触发动作
2. 必须同步修正的文件
3. 可选同步检查文件
4. 本次修正要避免的旧描述

例如：

```text
触发动作：新增皮肤
必须同步修正的文件：
- ...
可选同步检查文件：
- ...
需要避免的旧描述：
- ...
```

这样 AI 后续读取时可以直接命中，不需要从长篇架构说明里反复推断。

## 11. 与 AI 协作的实际价值

这个目录的价值不是再增加一层普通文档，而是减少 AI 后续执行时的遗漏。

主要收益：

1. 防止只改代码或目录，不改相关说明文件。
2. 防止旧架构描述长期残留。
3. 防止不同 AI 会话对“哪些文件必须一起改”产生不同理解。
4. 让主题、模块、数据库三类常见结构变更都能有统一入口。

## 12. 落地顺序建议

建议后续按这个顺序实施：

1. 先创建 `SELPLAT/ai-standards/`
2. 先落 `README.md` 和 `索引.md`
3. 第一批优先补 `主题系统修正索引.md`
4. 第二批补 `模块系统修正索引.md`
5. 第三批补 `数据库工程修正索引.md`

原因是主题系统当前已经在持续演进，最先需要稳定修正索引。

## 13. 一句话定版

`SELPLAT` 适合新增一个独立的 `ai-standards/` 目录，用来存放“某类结构变更后 AI 必须同步修正哪些文件”的导航索引；架构事实继续留在 `docs/architecture`，二者分层最清晰。
