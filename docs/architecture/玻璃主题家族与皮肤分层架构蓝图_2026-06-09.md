# 玻璃主题家族与皮肤分层架构蓝图

## 1. 目的

本文件用于评估当前两套玻璃风格皮肤：

- `indigo-amber-dark`
- `cyan-amber-dark`

是否适合归并为同一个玻璃主题家族，并定义后续在 `SELPLAT` 中扩展主题与皮肤的标准结构。

## 2. 结论

可以合并，而且建议合并。

原因很明确：

1. 两套皮肤的目录结构完全一致。
2. 四个 SVG 背景资产完全相同。
3. `components.css` 完全相同。
4. `cyan-amber-dark/tokens.css` 明显建立在 `seladmin-*` 这一套基础变量体系之上。
5. 当前差异主要集中在 token 层和业务风格层，不在资产层和聚合入口层。

因此它们更适合被定义为：

- 一个 `glass-theme` 主题家族
- 两套皮肤放在这个家族下面

而不是继续作为两个并列、互不相关的顶级主题目录存在。

## 3. 当前证据

已经完成的只读比对结果如下：

- `assets/liquid-grid-glow.svg` 相同
- `assets/liquid-mist.svg` 相同
- `assets/liquid-orb-amber.svg` 相同
- `assets/liquid-orb-cyan.svg` 相同
- `components.css` 相同
- `components/trees.css` 相同
- `tokens.css` 不同
- `buttons.css`、`forms.css`、`layout.css`、`overlays.css`、`tables.css`、`tabs.css` 不同
- `preview/index.html` 不同

这说明：

- 资产层可以共享
- 聚合入口层可以共享
- 皮肤层应该拆开
- 预览层应该保留皮肤级差异

## 4. 推荐主题家族命名

新的主题家族目录建议使用中性英文命名：

```text
glass-theme
```

这个名字优于继续用某一套现有皮肤名做父目录，因为：

- 它描述的是整套设计语言
- 不偏向后台业务或考勤业务
- 后续可以继续容纳更多玻璃风格皮肤

## 6. 统一命名规则

后续皮肤统一使用这种模式：

```text
主色-辅色-dark
```

当前对应关系：

- `indigo-amber-dark`
  靛蓝主色，琥珀辅色，偏稳重后台感
- `cyan-amber-dark`
  青蓝主色，琥珀辅色，偏明亮玻璃数据台感

这样命名的好处是：

- 不绑定业务
- 可以直接从配色理解皮肤风格
- 后续新增皮肤时命名规则稳定

后续新增示例：

- `emerald-amber-dark`
- `violet-cyan-dark`
- `slate-gold-dark`

## 7. 各层职责

### 7.1 `core/`

这里放玻璃主题家族的公共基座。

应该放：

- 共享背景资产
- 共享玻璃设计 token
- 共享组件基础样式
- 共享结构规则

不应该放：

- 某个业务独有的视觉语义
- 某个模块独有的页面调优
- 业务专属预览页面

### 7.2 `skins/`

这里放皮肤目录。

每个皮肤负责：

- 颜色与 token 覆盖
- 局部组件风格覆盖
- 皮肤级预览页面
- 皮肤说明文档

原则上，皮肤应尽量“扩展 core”，而不是复制一整套 core。

### 7.3 `manifest/`

这里放主题家族元数据，后续可扩展：

- 家族 id
- 默认皮肤
- 支持皮肤列表
- 预览入口映射

## 8. 迁移模型

后续真正实施重构时，不建议直接一次性硬切。

推荐步骤：

### 第一步

先保留当前兼容目录：

```text
shared/frontend/theme/indigo-amber-dark
shared/frontend/theme/cyan-amber-dark
```

### 第二步

新增：

```text
shared/frontend/theme/glass-theme
```

### 第三步

抽取共享内容进入 `glass-theme/core`。

当前优先候选：

- `assets/*`
- `components.css`
- 基础变量体系
- 共用组件结构规则

### 第四步

把现有两套皮肤收敛到：

```text
glass-theme/skins/indigo-amber-dark
glass-theme/skins/cyan-amber-dark
```

### 第五步

当消费方完成切换后，再决定是否删除旧兼容目录，或仅保留转发说明。

## 9. 未来新主题与新皮肤的判断规则

### 建新皮肤，而不是建新主题家族

如果满足以下条件，就应该新增 skin：

- 设计语言仍然是玻璃风格
- 组件结构大体不变
- 只是颜色、密度、强调感、视觉重心不同

例如：

- `indigo-amber-dark`
- `cyan-amber-dark`
- `emerald-amber-dark`
- `violet-cyan-dark`

### 建新主题家族

如果满足以下条件，才应该新增 theme family：

- 设计语言彻底变化
- 组件行为模型明显变化
- 已经不属于玻璃主题范式

例如：

- `paper-theme`
- `industrial-theme`
- `minimal-light-theme`

## 10. 推荐皮肤契约

每个皮肤目录建议稳定遵循下面的结构：

```text
skins/<skin-name>/
├─ skin-tokens.css
├─ skin-components.css
├─ overrides/
│  ├─ layout.css
│  ├─ buttons.css
│  ├─ forms.css
│  ├─ tabs.css
│  ├─ tables.css
│  └─ overlays.css
├─ preview/
│  └─ index.html
└─ README.md
```

推荐加载顺序：

1. `core/base-tokens.css`
2. `core/base-components.css`
3. `skins/<skin>/skin-tokens.css`
4. `skins/<skin>/skin-components.css`
5. `skins/<skin>/overrides/*.css`

这样可以把继承链固定下来。

## 11. 推荐 token 分层

当前已经能看出变量体系存在明显层次：

- `seladmin-*` 更像基础玻璃风格变量
- 皮肤自己的变量是在这套基础上做映射和覆盖

建议后续正式分成三层：

### A 层：主题家族核心语义 token

例如：

- `--glass-font`
- `--glass-text`
- `--glass-border`
- `--glass-surface`
- `--glass-shadow`

### B 层：皮肤别名 token

例如：

- `--indigo-theme-text`
- `--cyan-theme-text`

### C 层：业务模块局部 token

这一层应该留在业务模块内，不应反向沉积到主题家族里。

## 12. 预览策略

预览页应该保留在皮肤层。

原因：

- 预览内容本身也会表达皮肤气质
- 不同皮肤可能希望展示不同的示例页面
- 后续 CRM 或 CMS 若扩展玻璃皮肤，也不需要强行共用同一份 HTML

所以建议：

- 共享预览工具可以放 `core`
- 真正的 `preview/index.html` 保留在每个皮肤目录

## 13. 最终建议

最终建议很明确：

1. 当前两套皮肤应该统一纳入一个玻璃主题家族。
2. 皮肤目录统一采用中性英文命名，不再绑定业务名。
3. 当前两套皮肤统一命名为：
   - `indigo-amber-dark`
   - `cyan-amber-dark`
4. 架构文档、说明文档文件名和内容说明优先使用中文。
5. 代码路径、主题目录名继续保留英文，避免后续脚本和前端引用路径不稳定。

## 14. 一句话定版

后续主题体系建议固定为：

- 主题家族目录用英文
- 皮肤目录用中性英文命名
- 文档文件名和文档说明用中文
- 同一设计语言下优先扩展皮肤，不轻易新建主题家族
