# 多业务可插拔平台工程目录蓝图

## 1. 设计目标

你现在的工程已经不再是“单一考勤项目”，而是一个可承载多个业务工程的平台。  
这类平台最重要的不是目录是否简洁，而是下面四件事是否成立：

1. 每个业务模块可以独立接入。
2. 每个业务模块可以整体删除。
3. 公共能力不会被某个业务目录绑死。
4. 宿主平台只负责装配，不负责承载某个业务的私有实现。

所以目录设计的核心原则应该是：

- 先按“业务插件”纵向切分。
- 再在每个业务插件内部按 `backend/frontend/doc` 横向分层。
- 真正跨业务复用的内容，只能进入 `shared`。
- 真正平台级入口和装配逻辑，只能进入 `host`。

## 2. 推荐总结构

```text
platform-root/
├─ apps/
│  ├─ host/
│  ├─ uniauth/
│  ├─ attendance/
│  ├─ rule-engine/
│  ├─ crm/
│  └─ cms/
├─ shared/
├─ docs/
├─ scripts/
├─ build/
├─ cache/
├─ OPTION/
├─ package-meta/
├─ README.md
└─ .gitignore
```

这套结构的业务含义如下：

- `apps/`：所有业务插件与宿主工程入口。
- `shared/`：跨业务共用的公共代码、契约、工具、组件。
- `docs/`：平台级文档，不属于任何一个具体业务。
- `scripts/`：统一脚本入口，负责启动、构建、测试、打包。
- `build/`：Gradle 编译产物、测试报告和构建元数据。
- `cache/`：JDK、Gradle 依赖、离线 JAR 和其他可复用缓存。
- `OPTION/temp/`：脚本、能力和工具产生的日志、验证结果及临时数据。
- `package-meta/`：插件注册信息、版本声明、装配清单、开关配置。

## 4. 顶层目录职责说明

### 4.1 `apps/`

这里不是“技术目录”，而是“模块目录”。  
每个一级目录就是一个可装配、可下线、可迁移的业务单元。

适合放：

- 某业务独有的后端服务实现
- 某业务独有的前端页面与交互
- 某业务独有的设计文档
- 某业务独有的注册描述

不适合放：

- 两个以上业务共用的工具类
- 所有业务都要依赖的认证内核
- 平台统一布局组件
- 平台统一脚本

### 4.2 `shared/`

这里只能放“跨业务复用资产”。  
判断标准很简单：如果删掉 `crm`，这里的内容仍然应该成立，那它才配放在 `shared`。

适合放：

- 公共认证中间件
- 公共异常处理
- 公共 HTTP 请求封装
- 公共 Vue 组件
- 公共 API 契约
- 插件注册契约
- 公共测试支撑

不适合放：

- 只给 `attendance` 用的特殊逻辑
- 只给 `crm` 用的客户域模型
- 某个业务的私有菜单配置

### 4.3 `docs/`

这里只放平台级文档，不放某个业务自己的详细设计。

适合放：

- 总体架构文档
- 插件接入规范
- 统一命名规范
- 部署规范
- 运维规范
- 版本发布说明

### 4.4 `scripts/`

这里是所有入口脚本的统一归口目录。  
不要让启动脚本散落在 `apps/crm`、`apps/cms`、根目录、前端目录、后端目录里。

### 4.5 `build/`、`cache/` 与 `OPTION/temp/`

这三个目录分别承接构建产物、可复用缓存和工具运行数据，禁止再建立语义重叠的 `runtime/`。

归属规则：

- Gradle 编译结果、覆盖率和测试报告进入 `build/`
- 项目 JDK、Gradle 依赖、离线 JAR 和 Python 字节码进入 `cache/`
- 日志、Playwright 输出、调试结果和临时副本进入 `OPTION/temp/`

不适合放：

- 正式源码
- 正式文档
- 手写脚本
- 另建 `runtime/` 或其他重复运行目录

### 4.6 `package-meta/`

这个目录用来承载“插件是否启用、如何装配、依赖谁、版本是多少”的元数据。  
如果没有这层，你的可插拔最终还是会退化成硬编码引用。

## 5. `apps/host` 的职责

`host` 不是业务模块，它是平台壳。

建议结构：

```text
apps/host/
├─ backend/
│  ├─ bootstrap/
│  ├─ plugin-loader/
│  ├─ routing/
│  ├─ gateway/
│  └─ config/
├─ frontend/
│  ├─ shell/
│  ├─ router/
│  ├─ layout/
│  ├─ plugin-loader/
│  └─ app-entry/
├─ doc/
└─ manifest/
```

`host` 应该负责：

- 平台启动入口
- 模块装配
- 插件发现
- 统一路由挂载
- 统一菜单壳
- 统一上下文注入
- 平台级配置加载

`host` 不应该负责：

- CRM 的客户管理实现
- 考勤业务规则
- CMS 的内容建模
- 某个业务的独占页面

一句话判断：  
如果删掉某个业务后，`host` 还应该稳定存在，那这部分代码才应该放在 `host`。

## 6. `apps/uniauth` 的职责

权限工程建议既是一个业务插件，又拆出部分公共认证内核。

推荐做法：

- `apps/uniauth` 放“用户、角色、菜单、模块、租户、权限配置界面与管理流程”。
- `shared/backend/auth-kernel` 放“统一登录态、JWT 处理、鉴权拦截、当前用户上下文”等平台必备认证内核。
- `shared/contracts/permission` 放权限码、资源模型、授权契约定义。

这样拆的原因是：

- 权限管理页面是业务插件能力。
- 认证基础设施是平台基础设施。

如果全放在 `apps/uniauth`，以后禁用它会把平台登录基础也一起拆掉，边界会失真。

## 7. `apps/attendance` 的职责

这里放考勤业务私有资产：

- 排班
- 打卡
- 日次计算
- 月次汇总
- 考勤规则应用
- 考勤异常审批
- 考勤报表界面

可以放：

- `backend/domain/attendance/...`
- `frontend/src/projects/attendance/...`
- `doc/attendance/...`
- `manifest/module.json`

不建议抽出去的内容：

- 考勤专有 DAO
- 考勤专有接口入参出参
- 考勤专有页面状态管理

## 8. `apps/rule-engine` 的职责

如果你后续有规则协议工程，而且会被多个业务共用，就不应该挂在考勤下面。

建议它成为独立插件：

```text
apps/rule-engine/
├─ backend/
│  ├─ parser/
│  ├─ executor/
│  ├─ validator/
│  ├─ adapter/
│  └─ api/
├─ frontend/
│  ├─ rule-editor/
│  ├─ simulator/
│  └─ publish-console/
├─ doc/
└─ manifest/
```

它的职责是：

- 规则定义
- 规则解析
- 规则校验
- 规则执行
- 规则调试
- 规则版本管理

它不应该直接内嵌考勤、CRM、CMS 的业务细节。  
业务只通过契约对接它。

## 9. `apps/crm` 和 `apps/cms` 的职责

这两个目录应该是典型的可整包增删模块。

建议结构统一：

```text
apps/crm/
├─ backend/
├─ frontend/
├─ doc/
└─ manifest/

apps/cms/
├─ backend/
├─ frontend/
├─ doc/
└─ manifest/
```

设计要求：

- 自己的后端接口只放自己目录内。
- 自己的前端页面只放自己目录内。
- 自己的设计文档只放自己目录内。
- 自己的菜单、路由、权限、开关定义写在自己的 `manifest`。

这样删除 `crm` 时，只需要：

1. 删除 `apps/crm`
2. 删除 `package-meta/modules/crm.*`
3. 清理 `OPTION/temp` 中属于 `crm` 的运行数据

而不是全工程搜索 `crm` 字样。

## 10. `manifest` 建议放什么

每个业务插件下都建议保留 `manifest/`。

例如：

```text
apps/crm/manifest/
├─ module.json
├─ routes.json
├─ permissions.json
├─ menus.json
└─ dependencies.json
```

建议职责：

- `module.json`：模块标识、名称、版本、是否默认启用
- `routes.json`：前端路由挂载声明
- `permissions.json`：权限点清单
- `menus.json`：菜单挂载定义
- `dependencies.json`：依赖哪些共享能力或其他模块

这层很关键，因为它决定宿主能否通过“声明装配”而不是“代码写死”来接入模块。

## 11. `shared` 的推荐细分

### 11.1 `shared/backend`

建议拆成：

- `auth-kernel/`
- `common-web/`
- `common-db/`
- `common-test/`
- `sdk/`

其中：

- `auth-kernel`：平台认证内核
- `common-web`：统一返回结构、异常处理、基础拦截器
- `common-db`：数据库基础能力、分页基类、审计字段支持
- `common-test`：后端测试基座
- `sdk`：给各业务调用的平台 SDK

### 11.2 `shared/frontend`

建议拆成：

- `components/`
- `composables/`
- `services/`
- `theme/`
- `utils/`

其中：

- `components`：共享组件
- `composables`：共享组合式逻辑
- `services`：统一请求与会话服务
- `theme`：主题系统
- `utils`：纯工具函数

### 11.3 `shared/contracts`

建议拆成：

- `api/`
- `permission/`
- `routing/`
- `plugin/`

这部分的作用是让“模块之间协作”通过明确契约完成，而不是彼此直接引用内部实现。

## 12. `docs` 的推荐细分

```text
docs/
├─ platform/
├─ architecture/
├─ plugin-spec/
├─ development/
├─ deployment/
└─ operations/
```

建议含义：

- `platform/`：平台总览、模块地图
- `architecture/`：架构设计
- `plugin-spec/`：插件开发规范、manifest 规范、接入步骤
- `development/`：开发规范、命名规范、测试规范
- `deployment/`：部署结构、环境变量、打包规则
- `operations/`：日志、排障、监控、运维手册

业务详细设计文档仍然优先留在各自 `apps/<module>/doc`。

## 13. `scripts` 的推荐细分

```text
scripts/
├─ startup/
├─ build/
├─ test/
├─ package/
└─ maintenance/
```

建议职责：

- `startup/`：启动宿主、启动单模块、启动整套平台
- `build/`：构建前端、构建后端、构建模块包
- `test/`：单元测试、集成测试、E2E 测试
- `package/`：打模块包、出发布包
- `maintenance/`：清理缓存、清理日志、环境修复

不要再把 `.bat`、`.command`、`.ps1`、`.sh` 散落到各工程根目录。

## 14. 构建、缓存与运行数据的统一细分

```text
build/                 # 编译产物和构建报告
cache/                 # JDK、依赖与可复用缓存
└─ jdks/
OPTION/
└─ temp/               # 日志、验证输出与临时数据
```

建议原则：

- 所有 Gradle 构建结果和覆盖率报告都进 `build/`
- 所有项目级 JDK、依赖和可复用缓存都进 `cache/`
- 所有工具日志、验证输出和临时业务数据都进 `OPTION/temp/`

这样每类副作用只有一个稳定出口，源码目录也保持干净。

## 15. 删除单个业务模块时的边界规则

如果你要做到“删掉一个业务，就等于删掉一个工程”，必须满足下面规则：

### 规则一：业务私有代码必须全部收敛在 `apps/<module>`

不能把 `crm` 的页面散在 `shared/frontend/components`，也不能把 `crm` 的后端服务散在 `host/backend`。

### 规则二：宿主只认声明，不认硬编码

宿主应该读取：

- 模块清单
- 菜单清单
- 路由清单
- 权限清单

而不是在代码里写死：

- `if module == crm`
- `import crm.xxx`

### 规则三：共享层只存真正公共内容

如果 `shared` 被业务私货污染，删除模块时必然会残留。

### 规则四：业务间交互走契约，不走内部类直接引用

比如：

- CRM 调规则引擎，走 `shared/contracts/plugin` 或公共 API
- 考勤调权限上下文，走 `auth-kernel` 或权限契约

不要让一个业务直接 import 另一个业务的内部实现。

## 16. 推荐启用与装配方式

建议你未来把模块启用关系做成配置化，例如：

```text
package-meta/modules/
├─ host.json
├─ uniauth.json
├─ attendance.json
├─ rule-engine.json
├─ crm.json
└─ cms.json
```

每个文件可以定义：

- 模块编码
- 模块名称
- 版本
- 是否启用
- 前端入口
- 后端入口
- 菜单挂载点
- 路由前缀
- 权限前缀
- 依赖模块

这样禁用 `crm` 时，你不一定要物理删除，也可以先配置下线。  
真正删除时，再删 `apps/crm` 即可。

## 17. 实施建议

如果你要落地，不建议一次性全改。  
建议按下面顺序做：

1. 先建立总结构：`apps/shared/docs/scripts/build/cache/OPTION/package-meta`
2. 先把现有 `SELSP`、`SELVUE` 归并进一个业务模块
3. 先把 `uniauth` 和 `attendance` 从现有代码逻辑上拆成两个模块边界
4. 再补 `manifest` 和 `package-meta`
5. 最后再做 `crm`、`cms`、`rule-engine` 的独立接入

## 18. 最终建议

你的方向是对的，最合理的结构不是：

```text
backend/
frontend/
doc/
crm/
cms/
```

而是：

```text
apps/
├─ crm/
│  ├─ backend/
│  ├─ frontend/
│  └─ doc/
├─ cms/
│  ├─ backend/
│  ├─ frontend/
│  └─ doc/
```

也就是：

- 先按业务模块切
- 再在业务模块内部按技术分层

这样才真正符合“可插拔”和“可整包删除”的目标。

## 19. 一句话定版

如果你准备长期演进成插件平台，建议把工程固定为：

- `apps/<module>/backend frontend doc manifest`
- `shared/<cross-module-assets>`
- `docs/<platform-docs>`
- `scripts/<all-entry-scripts>`
- `build/<gradle-artifacts-and-reports>`
- `cache/<jdks-dependencies-reusable-cache>`
- `OPTION/temp/<logs-validation-and-temporary-data>`
- `package-meta/<module-enable-and-assembly>`

这是当前最适合你场景的主结构。
