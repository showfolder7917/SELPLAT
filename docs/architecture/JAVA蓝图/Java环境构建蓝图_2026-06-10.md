# Java 环境构建蓝图

## 1. 目的

本文件用于定义 `SELPLAT` 后续 Java 后端真正进入可编译、可运行、可测试状态时的环境构建方案。

本蓝图关注的不是某一个 Java 类怎么写，而是：

- Java 构建工具怎么选
- 多模块工程怎么组织
- `common-core`、`uniauth backend` 这类目录如何进入构建体系
- 本地开发、编译、测试、运行入口如何统一
- 后续 `attendance`、`rule-engine`、`crm`、`cms` 如何接入同一套构建环境

## 2. 当前现状

当前 `SELPLAT` 已经存在这些 Java 相关骨架：

- `shared/backend/common-core`
- `apps/uniauth/backend`
- `ai-corrections/standards/java`

当前已经有：

- 公共 Java 包：`com.sp.selplat.common`
- `uniauth` 用户模块的基础 `controller/service/dao/domain/mapper`
- 权限模块用户表 SQL：`apps/uniauth/backend/schema/01-ua_user.sql`

当前还没有：

- `build.gradle` 或 `pom.xml`
- 根 `settings.gradle`
- 可执行的 Spring Boot 启动类
- 统一依赖版本管理
- 测试依赖和测试任务

因此这份蓝图的目标，是把“已有源码骨架”提升为“可构建的 Java 环境”。

## 3. 构建工具结论

建议优先使用：

```text
Gradle
```

原因：

1. 原有 `SELATTENDANCE/SELSP` 已存在 `build.gradle`，迁移时更容易复用旧经验。
2. `SELPLAT` 本身是多模块平台，Gradle 的多项目结构更适合先搭骨架再逐步接入。
3. 后续如果继续拆 `common-core`、`uniauth`、`attendance` 为独立子项目，Gradle 的依赖声明会更清楚。

不建议当前阶段先混用：

- 根项目用 Gradle
- 某些子模块单独再搞 Maven

应统一成一套。

## 4. 推荐根构建结构

推荐在 `SELPLAT` 根目录建立：

```text
SELPLAT/
├─ settings.gradle
├─ build.gradle
├─ gradle.properties
├─ apps/
├─ shared/
└─ ...
```

其中职责如下：

- `settings.gradle`
  负责声明所有 Java 子项目
- `build.gradle`
  负责统一插件、JDK 版本、仓库、公共依赖和通用任务
- `gradle.properties`
  负责放构建参数、版本号、JVM 参数

## 5. 推荐多模块项目映射

推荐把真实参与 Java 构建的目录映射成 Gradle 子项目。

当前第一阶段建议纳入这些模块：

```text
:shared:backend:common-core
:apps:uniauth:backend
```

后续逐步加入：

```text
:apps:attendance:backend
:apps:rule-engine:backend
:apps:crm:backend
:apps:cms:backend
```

不建议一开始就把全部模块强行接入。  
应先让 `common-core` 和 `uniauth` 跑通，再扩张。

## 6. 目录与项目名映射建议

建议 `settings.gradle` 中按真实目录声明：

```text
include("shared:backend:common-core")
include("apps:uniauth:backend")
```

这样项目逻辑和物理目录能一一对应，避免后续 AI 和人工排查时迷路。

## 7. 各 Java 子项目职责

### 7.1 `shared/backend/common-core`

职责：

- 承接公共 Java 工具类
- 承接公共基础异常
- 承接公共返回结构基类
- 承接公共值处理、哈希、时间、字符串等稳定复用能力

原则：

- 不放业务模块私有代码
- 不放某个模块专属 SQL
- 不放某个模块私有 DTO

它应该被业务模块依赖，而不是反向依赖业务模块。

### 7.2 `apps/uniauth/backend`

职责：

- 承接权限模块的 Spring Boot 后端实现
- 承接 `controller/service/dao/domain`
- 承接权限模块资源文件
- 承接 `schema` 和后续 `data` 脚本

原则：

- 业务逻辑可以依赖 `common-core`
- 不应把本模块私有代码反向塞回 `common-core`

## 8. 推荐源码目录规则

每个 Java 子项目统一使用：

```text
src/main/java
src/main/resources
src/test/java
src/test/resources
```

当前已经符合的部分：

- `shared/backend/common-core/src/main/java`
- `apps/uniauth/backend/src/main/java`
- `apps/uniauth/backend/src/main/resources`

后续需要补：

- `src/test/java`
- `src/test/resources`

## 9. 推荐包路径规则

包路径应遵循：

- 公共工程：`com.sp.selplat.common`
- 权限模块：`com.sp.selplat.uniauth`
- 考勤模块：`com.sp.selplat.attendance`
- 规则协议模块：`com.sp.selplat.ruleengine` 或统一连字符映射后的合法 Java 包名

核心原则：

- 包路径和模块边界一致
- 公共包不使用业务名前缀
- 业务模块不复用旧工程里的混乱包名

## 10. 推荐依赖方向

当前建议依赖方向固定为：

```text
apps/<module>/backend  ->  shared/backend/common-core
```

禁止方向：

```text
shared/backend/common-core  ->  apps/uniauth/backend
```

也就是说：

- `common-core` 只能被依赖
- 不能依赖具体业务模块

## 11. 推荐插件方案

根构建建议统一使用：

- `java`
- `java-library`
- `org.springframework.boot`
- `io.spring.dependency-management`

推荐思路：

- `common-core`
  用 `java-library`
- 业务模块后端如 `apps/uniauth/backend`
  用 `org.springframework.boot`

原因：

- `common-core` 是公共库，不需要自己打成独立可启动应用
- `uniauth backend` 需要最终具备启动能力

## 12. 推荐 JDK 版本

建议统一到：

```text
Java 21
```

原因：

1. 当前本机与本轮构建环境已经稳定具备 Java 21 和 Gradle 8.11
2. Spring Boot 3.x 在 Java 21 下可以直接进入当前长期支持版本组合
3. 新平台后续继续扩张模块时，Java 21 更适合作为统一长期版本口径

不建议现在继续按旧工程习惯退回到过旧版本。

## 13. 推荐依赖分层

根项目统一管理这些依赖版本：

- Spring Boot
- MyBatis / MyBatis Spring
- 数据库驱动
- JUnit
- Lombok（如果后续决定使用）
- 日志框架

业务模块项目只声明自己需要的依赖，不在每个模块各写一遍版本号。

## 14. 数据库与资源文件接入建议

当前 `uniauth` 已经有：

- `schema/01-ua_user.sql`
- `src/main/resources/.../mapper/UniauthUserDao.xml`

后续建议：

- 模块级 schema 继续放 `apps/uniauth/backend/schema`
- Mapper XML 继续放 `src/main/resources` 下与 DAO 对齐路径
- Spring Boot 启动配置放模块自己的 `src/main/resources/application-*.yml`

不要把模块 schema 散落到根目录。

## 15. 本地开发与运行方式

推荐本地开发顺序：

1. 根项目执行依赖解析和编译
2. 单模块执行测试
3. 单模块执行启动

推荐后续脚本归口：

- `scripts/startup/java/`
- `scripts/build/java/`
- `scripts/test/java/`

不要把 Java 启动命令散落在模块目录里。

## 16. 推荐第一阶段可运行目标

第一阶段只追求这三个目标：

1. `common-core` 能单独编译通过
2. `apps/uniauth/backend` 能引用 `common-core` 编译通过
3. `apps/uniauth/backend` 能最小启动并连通 `ua_user` 的 CRUD

不要一开始就追求：

- 全模块一起跑
- 全量数据库脚本一次成型
- 全平台统一启动器

## 17. 推荐后续接入顺序

建议顺序：

1. 根 `settings.gradle`
2. 根 `build.gradle`
3. `shared/backend/common-core/build.gradle`
4. `apps/uniauth/backend/build.gradle`
5. `uniauth` 启动类和基础配置
6. 编译通过
7. `ua_user` CRUD 联调
8. 再接 `attendance`

## 18. 与 Java 规范目录的关系

这份文档只解决“怎么构建”。

它不替代：

- `ai-corrections/standards/java/platform`
- `ai-corrections/standards/java/backend`
- `ai-corrections/standards/java/migration`

关系应固定为：

- `docs/architecture/Java环境构建蓝图_2026-06-10.md`
  解决构建环境和模块关系
- `ai-corrections/standards/java/...`
  解决代码怎么写、目录怎么迁、样板怎么参考

## 19. 当前阻塞与已知缺口

当前仍缺：

- 根 `settings.gradle`
- 根 `build.gradle`
- `common-core/build.gradle`
- `apps/uniauth/backend/build.gradle`
- `uniauth` 启动类
- Spring Boot 配置文件
- 数据源和 MyBatis 配置
- 测试目录和测试依赖

所以当前还只是“源码和目录骨架”，不是可运行 Java 工程。

## 20. 一句话定版

`SELPLAT` 的 Java 环境应采用 Gradle 多模块构建，先把 `shared/backend/common-core` 和 `apps/uniauth/backend` 接入根构建体系，再逐步扩展到其他业务模块；公共库只被业务模块依赖，业务模块不反向污染公共库。
