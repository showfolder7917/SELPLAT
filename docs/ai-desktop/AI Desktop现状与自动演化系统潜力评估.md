# AI Desktop 现状与自动演化系统潜力评估

## 1. 文档状态

- 评估日期：2026-08-31。
- 适用工程：`apps/ai-desktop`。
- 评估性质：基于当前源码、协议、数据库结构、测试代码和构建脚本的静态工程评估。
- 本文不把设计文档或规则描述直接当作已经运行成功的事实。
- 本轮没有执行统一测试、真实 Electron 交互测试或发布验证，因此不对当前运行成功率作无证据保证。
- 本轮只生成评估文档，不修改业务源码。

## 2. 执行摘要

### 2.1 核心结论

AI Desktop 已经超出“桌面聊天工具”或“单 Agent 编程助手”的范围，当前源码中已经存在一套较完整的受控演化骨架：

```text
会话语料
   ↓
韩立研讨与确立专题
   ↓
南宫形成提案
   ↓
韩立审批
   ↓
南宫拆分并分发
   ↓
多个 Codex 执行者在隔离工作树实施
   ↓
令狐检查、修复、统一测试
   ↓
版本集成、候选验证和受控重启
   ↓
韩立真实应用验收
   ↓
归档、事件、语料和下一轮材料
```

这条链路并非全部停留在设计层。主进程已经实际组装 Codex、多人物会话、Evolution、协作执行、令狐自动保障、SQLite、事件中心、测试资源协调和版本集成发布组件。

但当前系统还不能被准确称为“成熟的连续自动演化系统”。主要原因是：

1. 一次性演化闭环比长期自动演化闭环完整。
2. 长期自动演化能够发现专题、形成提案、审批和分发，但普通长期开关流程到 `pending-acceptance` 后仍主要依赖韩立页面验收；自动最终验收主要接在一次性演化路径中。
3. 当前学习主要是保存语料、读取人工审批历史和语义补录，不等同于模型训练、策略学习或经过对照实验验证的能力提升。
4. 南宫、韩立、Evolution 和 Workflow 仍集中在大型 Facade/Store 中，模块所有权尚未完成解耦。
5. 当前存在丰富测试代码，但本轮没有执行统一测试，因此只能证明“有测试门禁设计”，不能证明当前版本全部通过。

### 2.2 当前成熟度判断

采用本文定义的六级模型，当前整体约处于：

```text
L2.8：受控多人物自动执行，已经接近一次性闭环演化
```

其中不同子系统成熟度并不相同：

- 一次性明确授权演化链：接近 `L3`。
- 多人物协作、隔离执行和测试恢复：`L3` 骨架较完整。
- 长期连续专题发现和循环推进：`L2-L3` 之间。
- 数据沉淀与可追踪性：接近 `L3`。
- 从历史中稳定学习并证明能力提升：约 `L1-L2`。
- 无人值守生产自治：尚未达到，也不应直接追求无边界自治。

### 2.3 潜力判断

在完成架构拆分、闭环补齐、在线质量评估和安全治理后，系统有较高潜力达到：

```text
L4：有人监督、边界明确、可持续运行的自动演化平台
```

不建议把最终目标定义成完全无人工主权的 `L5`。对于源码修改、命令执行、依赖下载、数据迁移和版本发布，合理的最终形态应是：

> 系统自动发现、调查、设计、实施、测试、修复和准备发布；用户保留目标、权限、高风险和最终主权门禁。

证据按四类标记：

| 等级 | 含义 |
|---|---|
| 已实现 | 源码存在，并且已在主进程或真实调用链中组装 |
| 部分实现 | 有实现和调用入口，但闭环、边界或验证证据不完整 |

## 4. 自动演化系统应具备什么

完整自动演化不是“让 AI 不断修改代码”。它至少包括五个相互约束的闭环。

### 4.1 目标闭环

系统需要知道：

- 为什么要演化。
- 要解决哪个真实问题。
- 哪些事实支持这个方向。
- 哪些内容明确不在范围内。
- 怎样判断结果有价值。

### 4.2 实施闭环

系统需要完成：

- 调查真实工程。
- 形成最小方案。
- 拆分不交叉任务。
- 隔离修改。
- 静态验证。
- 合并候选。

### 4.3 质量闭环

系统需要证明：

- 原问题是否真正解决。
- 原有能力是否回退。
- 交互和运行结果是否符合用户路径。
- 失败能否回到准确修正点。
- 同一失败是否被限制重试。

### 4.4 学习闭环

系统需要区分：

- 原始事实。
- 用户偏好。
- 人物判断。
- 自动决策。
- 实施结果。
- 验收结果。

只有经过结果验证的事实，才能影响下一轮判断；自动决定不能因为出现次数多就自动变成最高可信经验。

### 4.5 治理闭环

系统需要保持：

- 用户授权。
- 路径与工作区边界。
- 命令审批。
- 成本和轮次限制。
- 幂等与并发控制。
- 审计、回滚和人工接管。

## 5. 当前系统已经实现的能力

### 5.1 Codex 运行基础

状态：已实现。

当前存在：

- 固定版本 Codex Runtime 解析和校验。
- 内置或私有修复运行时。
- 登录、退出、模型列表。
- 命令和文件修改审批。
- 用户补充问题。
- 消息发送、取消和 steering。
- Thread 创建、恢复和清理。
- 多种流事件转换。
- 固定人物独立 Codex Session。

`main.ts` 实际创建了普通主会话、南宫、韩立、南宫研讨、南宫分发和语料语义补录等不同 Codex 使用实例。

这说明系统已经具备把“模型”作为可组合运行能力使用的基础，而不是只有一个聊天窗口。

### 5.2 多人物协作执行

状态：已实现，结构仍待解耦。

当前存在：

- 稳定人物名单。
- 人物级唯一 Writer 队列。
- 不同人物会话可以并行，同一人物保持串行。
- 协作任务持久化。
- 分析、执行、验证、集成和恢复状态。
- 人物心跳、协议进展和任务租约。
- 任务发起人、执行人和修复人事实。
- 中断后的恢复状态。
- 结构化结果摘要。

协作执行不再只是模型之间互发文字，而是已经关联任务 ID、工作树、结果 SHA、测试和集成状态。

### 5.3 南宫需求调查与提案

状态：已实现。

当前存在：

- 南宫独立只读会话。
- 对话消息持久化。
- 对话主题和用户意图元数据。
- 从对话生成可编辑专题草稿。
- 用户显式确认后将会话冻结为专题。
- 形成提案。
- 根据退回意见重新调查。
- 没有新增事实时阻止无意义提案版本。
- 审批通过后拆分任务。
- 预计修改文件重叠时阻止错误并行。

这部分已经具备“先调查，再形成方案”的基本产品语义。

### 5.4 韩立研讨、审批与验收

状态：部分实现到较高程度。

当前存在：

- 韩立读取对话语料并逐轮向南宫发问。
- 事实不足时继续追问。
- 达到轮次上限仍不足时阻断，而不是机械生成专题。
- 专题方向审批。
- 基于同类型人工审批记录的有限自动审批。
- 事实或人工偏好不足时退回补充。
- 真实应用验收计划生成。
- 白名单真实应用操作。
- 截图与步骤结果证据。
- 验收失败返还修正。

限制在于：

- 当前韩立职责仍大量位于 `NangongEvolutionFacade`。
- 长期自动演化路径的最终验收未像一次性路径一样完整自动接线。
- 验收质量依赖生成计划和受控操作覆盖范围，尚缺长期准确率统计。

### 5.5 Evolution 状态与一次性完整演化

状态：一次性链接近完整，长期链部分完整。

当前一次性演化支持：

- 南宫给出可见邀请。
- 用户独立确认。
- 确认事实持久化。
- 整理专题。
- 形成提案。
- 韩立自动事实审批。
- 退回后重新调查。
- 南宫任务拆分和分发。
- 等待真实协作任务。
- 令狐统一测试与恢复。
- 韩立真实应用验收。
- 完成或在明确卡点阻断。
- 应用重启或状态变化后从原运行恢复。

一次性运行没有自动打开长期演化开关，符合“单次授权不扩大为长期权限”的安全原则。

长期演化支持：

- 独立自动发现专题开关。
- 南宫来源和令狐来源分别自动审批。
- 审批后自动分发开关。
- 开始、暂停、恢复、停止和转人工。
- 最大研讨轮次和最大纠偏轮次。
- 每 30 秒轮询推进。
- 完成当前专题后重新进入韩立读库研讨。

但普通长期流程在任务完成后主要推进到 `pending-acceptance`，当前自动 Tick 没有像一次性演化一样直接执行真实应用验收并作出最终结果决定。因此“长期连续闭环”尚未完全闭合。

### 5.6 令狐自动保障

状态：已实现较完整的受控恢复骨架。

当前存在：

- 独立 `linghu` 垂直模块。
- 单一 Facade 入口。
- 原子状态文件和备份恢复。
- 默认关闭、用户显式开启。
- 每 30 秒检查。
- 全部人物非终态任务快照。
- 心跳、协议进展、状态时间和等待点联合判断。
- 结构化阻塞类型。
- 故障事实指纹。
- 同一故障最多三次恢复副作用。
- 本地修改归属不清时阻止自动重试。
- 缺失或取消任务的恢复点处理。
- 流程保障、测试漏点、审计完整性三个串行模块。
- 统一异常入口。
- 固定统一测试和受控重启。
- 完成报告和下一模块建议。

这是系统走向持续运行的重要基础，因为自动系统真正困难的部分通常不是“首次执行”，而是“失败后能否停止在正确位置并安全恢复”。

### 5.7 隔离工作树、测试与发布

状态：实现骨架较完整，生产可靠性待实际测试证明。

当前存在：

- 每个执行任务独立 Git 分支和工作树。
- 任务工作树验证。
- 共享依赖缓存租约。
- 测试资源跨进程互斥。
- 测试等待、占用、心跳、超时和孤儿锁恢复。
- 任务级固定测试 Runner。
- 版本候选工作区。
- 集成与发布全局串行锁。
- 发布批次 Store。
- 冲突文件和失败类型记录。
- 候选统一测试。
- 已验证可执行文件提升。
- 受控 Electron relaunch。

`main.ts` 已经把 Version Integration Pipeline、Test Resource Coordinator、令狐统一测试和应用重启连接在一起。

### 5.9 会话训练语料

状态：数据沉淀已实现，能力学习闭环部分实现。

当前存在：

- Codex rollout 增量入库。
- 完整回合门禁。
- 水位检查点。
- 失败后保留旧水位并重试。
- 外部 Codex 会话按工作区和来源过滤。
- 历史会话语义摘要补录。
- 南宫与用户原文保存。

> 保存“训练语料”不等于已经训练了模型。

## 7. 自动演化成熟度模型

### L0：普通聊天

- 只能回答问题。
- 不理解工程状态。
- 不执行可验证任务。

### L1：工具型 Agent

- 可以读写代码和运行命令。
- 单次任务由用户推动。
- 缺少持久流程和多角色治理。

### L2：受管多 Agent 协作

- 角色分工。
- 任务持久化。
- 隔离执行。
- 测试和恢复。
- 仍主要由人工启动和收尾。

### L3：受控闭环演化

- 从真实证据形成专题。
- 提案、审批、执行、测试、验收和归档形成闭环。
- 失败可以在原恢复点纠偏。
- 高风险和权限问题交给人工。

### L4：持续监督式演化

- 可以持续发现候选问题。
- 候选经过价值、风险、成本和证据治理。
- 多轮闭环稳定运行。
- 经验进入可验证学习系统。
- 用户以目标和治理为主，不需要逐节点操作。

### L5：开放自治演化

- 系统自行改变目标、权限、规则和生产能力。
- 很少或没有人工主权门禁。

L5 不适合作为本项目的直接目标，因为它会破坏用户授权、成本边界和可恢复性。

以下评分是静态工程成熟度，不是线上成功率。

| 维度 | 当前评分 | 说明 |
|---|---:|---|
| Codex 与工具运行基础 | 8/10 | 运行、认证、模型、审批、会话和流事件较完整 |
| 多人物角色与协作 | 7/10 | 角色、队列、任务和状态完整，模块边界仍混合 |
| 演化业务闭环 | 7/10 | 一次性链较完整，长期最终验收未完全闭合 |
| 隔离执行与版本管理 | 8/10 | Worktree、SHA、候选和冲突事实较扎实 |
| 测试、恢复与发布 | 7/10 | 结构完整，但缺当前统一测试和长期运行数据 |
| 持久化与审计 | 8/10 | SQLite、迁移、事件、时间线和恢复较强 |
| 安全与人工主权 | 8/10 | 默认关闭、明确确认、审批、轮次和重试限制较好 |
| 学习与反馈质量 | 4/10 | 有语料和审批历史，尚缺训练/评测/因果反馈闭环 |
| 模块化与可维护性 | 4/10 | 令狐较清楚，南宫/韩立/Evolution/Workflow 仍集中 |
| 生产运行证据 | 4/10 | 测试源码丰富，但本轮没有执行，长期指标未建立 |

综合静态成熟度约为：

```text
65 / 100
```

这个分数的含义不是“只完成了 65% 代码”，而是：

- 核心闭环构件大多已经存在。
- 从工程原型到稳定自动演化产品仍有明显距离。
- 最需要补的不是再增加更多人物，而是闭环可靠性、模块边界和可验证学习。

## 9. 当前系统最有价值的优势

### 9.1 已经把人物变成真实职责

南宫、韩立、令狐不只是不同提示词：

- 南宫持有调查、专题和提案职责。
- 韩立持有研讨、审批和验收职责。
- 令狐持有故障、恢复和统一测试保障职责。

这种职责分工比“多个 Agent 自由讨论”更容易审计和恢复。

### 9.2 自动化没有直接绕过用户主权

系统默认关闭自动开关，一次性确认不扩大为长期授权，自动审批需要人工历史，未知权限和本地修改归属会阻断。

这使系统具备向长期运行演进的安全基础。

### 9.3 已经重视失败事实和恢复点

系统记录任务状态、阶段、人物、代次、心跳、协议进展、失败类型、冲突文件和恢复点，并限制同一故障重复副作用。

这是自动演化系统比普通 Agent 更关键的能力。

### 9.4 数据和事件基础比界面更成熟

SQLite 中已经有流程、任务、审批、会话、演化轮次、语料和时间线结构。未来增加统计、质量模型和演化看板时，不必从零建立事实层。

### 9.5 测试与发布不是事后补充

测试资源锁、候选工作区、版本集成和受控重启已经进入主流程设计，而不是仅在文档里要求开发者手动完成。

## 10. 当前主要瓶颈

### 10.1 业务职责仍集中在大型 Facade 和 Store

`NangongEvolutionFacade` 同时包含：

- 南宫对话。
- 韩立研讨。
- 韩立审批。
- 韩立验收。
- Evolution 流程。
- 自动 Tick。
- 一次性状态机。

`NangongEvolutionStore` 同时保存多种人物和共同演化状态。

影响：

- 修改一个人物容易影响其他人物。
- 多人分支容易修改同一文件。
- 单元测试难以只验证一个职责。
- 未来新增人物会继续扩大中心文件。

这也是当前自动演化潜力向生产能力转化的首要架构障碍。

### 10.2 长期自动演化没有完整收尾

一次性演化有自动真实应用验收 Runner，但普通长期自动 Tick 在任务全部集成后主要把提案标记为 `pending-acceptance`。

这会导致：

```text
自动发现 → 自动审批 → 自动执行 → 自动测试 → 等待人工验收
```

而不是完整的：

```text
自动发现 → 自动审批 → 自动执行 → 自动测试 → 受控自动验收 → 归档 → 下一专题
```

最终是否自动验收不能简单复制一次性逻辑，需要先明确长期授权、验收风险分级和失败预算。

### 10.3 专题发现信号仍然偏窄

当前自动专题主要从南宫与 Codex 会话语料中提炼。

尚缺稳定接入的候选信号包括：

- 重复测试失败趋势。
- 页面交互失败频率。
- 用户反复纠正的问题。
- 性能与资源等待瓶颈。
- 崩溃和异常聚类。
- 发布后回归。
- 未完成承诺和长期待办。
- 代码复杂度、依赖风险和安全扫描。

令狐已有测试与审计检查，但这些信号还没有统一进入“候选演化主题池”。

### 10.4 语料沉淀还没有形成可验证学习

当前系统可以保存大量信息，但还缺：

- 数据集版本。
- 训练/评测切分。
- 去污染策略。
- 自动决定与人工事实的可信度分层统计。
- 每次能力升级前后的基线对比。
- 回退后样本降权。
- 模型或提示词版本登记。
- 在线 A/B 或影子评估。

没有这些机制时，语料越多不一定越聪明，也可能放大旧偏差。

### 10.5 自动价值判断尚缺结构化治理

系统强调不使用机械固定评分替代开放判断，这是正确的。但仍需要把以下事实结构化：

- 问题影响范围。
- 用户明确关注程度。
- 失败频率。
- 修复成本。
- 回退成本。
- 验证可行性。
- 权限等级。
- 与其他候选的冲突。

这些事实可以帮助 AI 作出可解释选择，但不能机械代替 AI 判断。

### 10.6 运行可靠性缺少长期指标

当前测试源码覆盖很多场景，但尚未在本次评估中获得以下运行统计：

- 端到端演化成功率。
- 平均返修轮次。
- 同一故障复发率。
- 自动恢复成功率。
- 误阻断和误通过率。
- 任务拆分冲突率。
- 候选集成失败率。
- 发布后回退率。
- 人工接管比例。
- 单轮时间和模型成本。

没有这些指标，无法判断系统是否适合长时间自动运行。

### 10.7 公共能力还没有完成分层

Codex、会话、测试、发布、事件、工作区和安全能力仍分散在根目录和 `collaboration`。

这使人物模块可能依赖具体实现，也让未来替换 AI Runtime、数据库或测试执行器的成本增大。

## 11. 三条闭环的真实状态

### 11.1 一次性授权闭环

```text
用户确认
 → 专题
 → 提案
 → 审批/返修
 → 分发
 → 执行
 → 测试/恢复
 → 真实应用验收
 → 完成或阻断
```

评价：代码结构接近闭合，是当前最适合作为生产化主线的能力。

### 11.2 长期连续演化闭环

```text
持续读库研讨
 → 建立专题
 → 提案
 → 自动审批
 → 自动分发
 → 执行与测试
 → pending-acceptance
```

评价：前半段较完整，收尾授权、自动验收、归档后继续下一轮仍需完善。

### 11.3 学习提升闭环

```text
会话/审批/执行/验收事实
 → 语料与记忆
 → 下一轮检索和参考
```

评价：已经形成记忆闭环，但尚未形成“能力版本 → 基线评测 → 升级 → 对照验证 → 保留或回退”的学习闭环。

## 12. 最终自动演化系统的合理形态

推荐最终系统保持七个稳定部分：

```text
Signal Center       候选信号中心
       ↓
Evolution           专题、提案和版本事实
       ↓
Workflow            跨人物状态机
       ↓
Personas            南宫、韩立、令狐和未来人物
       ↓
Capabilities        会话、执行、测试、发布、事件、规则
       ↓
Platform            Codex、数据库、工作区、安全、附件
       ↓
Learning/Evaluation 可验证经验、基线、指标和能力版本
```

### 12.1 Signal Center

统一收集候选事实，但不直接决定修改：

- 用户对话和纠正。
- 测试失败和重复故障。
- 审计缺失。
- 性能等待。
- 崩溃异常。
- 发布回归。
- 代码与依赖风险。

### 12.2 Evolution

保存候选、专题、提案、审批、执行、验收和归档的权威业务事实。

### 12.3 Workflow

只编排节点和恢复，不替人物作业务判断。

### 12.4 Personas

人物保持并列，通过 Port 协作，不直接引用其他人物 internal。

### 12.5 Capabilities 与 Platform

公共能力和底层技术实现独立，使人物专注业务判断。

### 12.6 Learning/Evaluation

只把经过验证的结果转成下一轮可使用经验，并能够回答：

- 哪个能力版本产生了结果。
- 使用了哪些证据。
- 通过了哪些评测。
- 是否比旧版本更好。
- 失败后怎样回退。

## 13. 推荐实施路线

### 阶段 A：先把现有闭环变得可证明

目标：不扩张自动权限，先证明一次性完整演化可靠。

工作重点：

- 执行全部登记测试。
- 建立真实端到端演化测试场景。
- 记录每个节点耗时、结果和失败原因。
- 验证重启恢复。
- 验证审批退回和返修预算。
- 验证统一测试失败修复。
- 验证真实应用验收失败回流。
- 验证候选发布与受控重启。

阶段出口：

- 至少一组固定样例可以连续多次完成一次性全链路。
- 失败时不产生重复任务、重复提交或状态丢失。
- 所有高风险情况准确阻断。

### 阶段 B：完成架构解耦

目标：让系统可以由多人并行维护和继续增加能力。

工作重点：

- 南宫、韩立、令狐并列拆分。
- Evolution 独立状态所有权。
- Workflow 独立编排。
- Codex 收拢到 Platform。
- 测试、发布、事件和会话进入 Capabilities。
- 每个模块只有一个公开 index。
- 外部禁止导入 internal。

阶段出口：

- 大型 Nangong Evolution Facade 不再同时承担五类职责。
- 人物之间没有直接依赖。
- `electron/services` 根层不再平铺具体 Service。
- 静态边界违规为零。

### 阶段 C：补齐长期连续闭环

目标：在明确长期授权下完成多个专题连续运行。

工作重点：

- 为长期自动验收定义独立开关和风险等级。
- 低风险且验收计划完全白名单化时允许自动执行。
- 中高风险继续要求人工验收。
- 完成后原子归档并开启下一轮研讨。
- 为每轮设置成本、时间、返修和恢复预算。
- 避免一个失败专题阻塞全部候选。

阶段出口：

- 多轮专题可以按预算连续推进。
- 每轮都能完成、暂停、转人工或明确阻断。
- 不存在无人认领的中间状态。

### 阶段 D：建立候选信号中心

目标：让演化来源不再只依赖会话语料。

工作重点：

- 统一信号 DTO。
- 建立来源、时间、置信度和可复现证据。
- 聚合重复故障和用户纠正。
- 保留相反证据和不确定性。
- 让韩立从候选池中研讨，而不是直接把信号变成专题。

阶段出口：

- 每个专题可以追溯到一组真实信号。
- 同一问题不会因为多来源重复而被计算成多个独立事实。
- AI 可以说明为什么选择当前专题而不是其他候选。

### 阶段 E：建立可验证学习闭环

目标：从“保存语料”升级为“证明能力提升”。

工作重点：

- 能力版本登记。
- Prompt、规则、代码和模型版本关联。
- 固定回归集与时间外验证集。
- 训练数据和评测数据隔离。
- 失败案例和反例保留。
- 自动升级使用影子模式。
- 新旧能力对照。
- 失败自动回退。

阶段出口：

- 每次所谓“能力升级”都有前后评测证据。
- 不能通过评测的升级不会成为默认能力。
- 用户纠正可以覆盖旧推断。

### 阶段 F：监督式持续演化

目标：达到 L4，而不是取消人工主权。

工作重点：

- 风险分级审批。
- 每日或每周期成本预算。
- 自动运行时间窗口。
- 生产发布门禁。
- 系统级停止开关。
- 异常趋势告警。
- 演化效果看板。
- 定期人工复盘和策略调整。

阶段出口：

- 系统可以持续运行，但任何时刻都能解释、暂停、回退和人工接管。
- 自动化扩大只来自明确授权，不来自模型自行推断。

## 14. 优先级建议

### P0：必须先完成

- 统一测试当前版本。
- 一次性演化真实端到端验证。
- 修复阻断性运行问题。
- 建立成功率、恢复率、返修率和耗时基线。

### P1：生产化基础

- 南宫、韩立、令狐并列拆分。
- Evolution 与 Workflow 解耦。
- 公共能力和 Platform 分层。
- 收紧公开 API 和 internal import。

### P2：完整连续演化

- 长期自动验收风险分级。
- 多专题调度。
- 完成归档后下一轮。
- 成本、轮次和超时预算。

### P3：智能质量提升

- 候选信号中心。
- 能力版本和评测系统。
- 影子运行和对照评估。
- 经验保留与自动回退。

### P4：规模扩展

- 新人物能力注册。
- 多工程和多应用演化。
- 远程协作资源。
- 更完整的组织级治理。

在 P0-P2 完成以前，不建议优先增加大量新人物。更多人物不会自动解决闭环、状态和质量问题，反而会增加调度和文件冲突。

## 15. 建议的量化指标

### 15.1 闭环指标

- 一次性演化完成率。
- 长期演化每专题完成率。
- 人工接管率。
- 无恢复点失败数量。
- 重复任务和重复副作用数量。

### 15.2 质量指标

- 验收一次通过率。
- 平均返修轮次。
- 发布后回退率。
- 同类故障再次出现率。
- 自动审批被人工纠正率。

### 15.3 执行指标

- 任务拆分文件冲突率。
- 工作树创建失败率。
- 测试资源平均等待时间。
- 集成冲突率。
- 自动恢复成功率。

### 15.4 学习指标

- 有人工或验收依据的经验占比。
- 能力升级前后评测差异。
- 旧偏好被用户纠正后的覆盖时延。
- 训练/评测污染事件数量。
- 回退后错误经验继续命中的次数。

### 15.5 成本指标

- 每个完成专题的模型调用量。
- 每个完成专题的构建与测试时间。
- 空转研讨轮次。
- 无新增事实的返修尝试。
- 重复读取和重复构建比例。

## 16. 安全与失控风险

### 16.1 错误自动放大

风险：错误专题经过自动审批、执行和发布后影响更大范围。

控制：人工历史证据、风险分级、验收白名单、候选验证、发布门禁和回滚。

### 16.2 语料污染

风险：自动生成内容再次进入语料后被当作用户事实。

控制：来源类型、人工事实、自动判断和验收结果必须分层；自动输出不能升级为最高可信用户偏好。

### 16.3 目标漂移

风险：系统从解决用户问题逐渐变成优化自身指标。

控制：每个专题必须关联用户目标或可验证运行事实，禁止把单一评分作为价值权威。

### 16.4 无限循环与成本失控

风险：研讨、返修、测试和恢复不断循环。

控制：最大纠偏轮次、故障指纹预算、时间预算、模型预算和人工接管。

### 16.5 权限扩大

风险：一次允许被扩张为长期自动执行或发布权限。

控制：一次性与长期授权分离，应用重启后高风险自动开关需要明确策略，未知审批不得自动通过。

### 16.6 状态分叉

风险：JSON、SQLite、工作树、事件和页面状态形成多个权威来源。

控制：明确每类状态唯一所有者，事件只是事实与投影，兼容层必须有删除时间点。

## 17. 不建议采用的方向

- 不建议通过增加更多巨大 Prompt 代替状态机和事实结构。
- 不建议人物之间直接继承或互相调用 internal。
- 不建议把所有公共能力塞进 `common`。
- 不建议只根据模型自评决定是否发布。
- 不建议把自动输出直接当作训练真值。
- 不建议在缺少统一测试结果时开启长期无人运行。
- 不建议把“运行没有报错”当作业务验收通过。
- 不建议为了自动化取消用户权限和高风险门禁。
- 不建议在架构尚未解耦时优先增加大量人物。

## 18. 建议的最终产品体验

用户不需要观看所有内部技术细节，但应始终能看到：

- 当前为什么选择这个专题。
- 使用了哪些证据。
- 当前由谁处理。
- 系统正在做什么。
- 已经修改了什么。
- 做过哪些测试。
- 为什么通过、退回或阻断。
- 需要用户作出什么选择。
- 怎样暂停、接管或回退。

理想交互不是“系统完全不问用户”，而是：

> 系统只在目标、权限、风险和无法由事实解决的选择上询问用户，其余可验证工程步骤自动完成。

## 19. 最终潜力评分

### 19.1 技术潜力

```text
高：85 / 100
```

原因：

- 核心构件已经存在。
- 状态、恢复、审计和发布意识较强。
- 不是只依赖单次 Agent 对话。
- 已经有真实角色分工和隔离执行。
- 数据结构足以继续建设质量和学习系统。

### 19.2 当前产品化程度

```text
中等：65 / 100（静态工程评估）
```

主要扣分来自：

- 未完成架构解耦。
- 长期自动闭环缺最终收尾。
- 缺少当前统一测试结果。
- 缺少长期运行指标。
- 学习系统仍以语料与记忆为主。

### 19.3 最适合达到的终态

```text
L4：持续监督式自动演化平台
```

系统可以自动完成大部分工程闭环，但目标主权、权限、高风险发布和最终停止权继续属于用户。

## 20. 最终判断

当前 AI Desktop 最重要的事实是：

> 自动演化的主要零件已经存在，下一阶段的核心工作不是继续堆功能，而是证明闭环、拆清边界、补齐长期收尾，并把“记住历史”升级成“可以证明能力真的变好”。

如果先完成一次性链真实验证，再完成模块解耦和长期验收闭环，系统有现实机会从当前的受控多人物工程原型发展为可以持续运行、能够纠偏、可审计、可回退的自动演化平台。

如果跳过这些基础，直接增加人物、扩大自动权限或让系统持续自行发布，现有大型 Facade、状态耦合和缺少质量指标的问题会被自动化成倍放大。

因此推荐路线是：

```text
先证明可靠
  → 再完成解耦
  → 再闭合长期循环
  → 再建立学习评测
  → 最后扩大自动运行范围
```
