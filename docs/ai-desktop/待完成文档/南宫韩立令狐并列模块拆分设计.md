# 南宫、韩立、令狐并列模块拆分设计

## 1. 文档状态

- 文档性质：架构拆分设计，不代表源码已经完成迁移。
- 适用工程：`apps/ai-desktop`。
- 适用运行边界：Electron 主进程、跨进程 Contracts、Renderer 人物界面。
- 核心目标：南宫婉、韩立、令狐老祖成为相互并列、可以独立维护和继续扩展的人物模块。
- 共同流程：由独立 `workflow` 模块编排。
- 共同数据：由独立 `evolution` 模块持有。
- 扩展目标：未来接入紫灵、元瑶等人物时，主要新增人物模块与能力登记，不修改现有人物内部实现。

本文档只设计目录、职责、依赖、迁移顺序和验证门禁。本轮不移动或修改现有业务源码。

## 2. 核心结论

目标架构不是让人物互相继承，而是：

```text
南宫婉 ─┐
韩立   ─┼── 并列人物模块
令狐   ─┘

Evolution = 中立共享业务数据
Workflow  = 跨人物流程编排
```

交叉关系按以下规则处理：

| 情况 | 采用方式 |
|---|---|
| 人物都有身份、启动和停止能力 | 小型 `interface` |
| 人物共同使用某项能力 | 组合与依赖注入 |
| 南宫完成后轮到韩立 | Workflow 编排 |
| 多个人物读取同一提案 | Evolution 中立数据 |
| 一个人物需要通知另一个人物 | Workflow 事件或 Port |
| 多个人物复用纯计算 | 独立 Analyzer 或纯函数 |
| 真正稳定的父子类型关系 | 才允许类继承 |

禁止采用“出现交叉就继承”的方式。南宫不是韩立的父类，韩立不是令狐的父类，人物之间不存在 `is-a` 关系。

## 8. Evolution 中立数据模块

```text
evolution/
├─ index.ts
├─ evolution.facade.ts
└─ internal/
   ├─ create-evolution-runtime.ts
   ├─ evolution.store.ts
   ├─ evolution-topic.repository.ts
   ├─ evolution-proposal.repository.ts
   ├─ evolution-approval.repository.ts
   ├─ evolution-acceptance.repository.ts
   ├─ evolution-mutation.coordinator.ts
   └─ evolution-workbench-change.assembler.ts
```

### 8.1 Evolution 所有的数据

- 专题。
- 提案和提案版本。
- 提案来源人物。
- 方向审批。
- 结果审批。
- 分发计划。
- 任务执行关联。
- 验收计划。
- 验收运行结果。
- 演化档案。
- 工作台查询投影。

### 8.2 为什么必须中立

同一个提案可能依次被南宫、韩立、协作执行者和令狐处理：

```text
南宫创建提案
    ↓
韩立审批提案
    ↓
协作人物执行
    ↓
令狐测试和恢复
    ↓
韩立最终验收
    ↓
南宫读取结果
```

如果共同状态放在 `nangong`，韩立和令狐就会被迫依赖南宫内部实现；如果拆成多份 Store，又会造成状态不一致。

### 8.3 唯一状态所有者

Evolution 必须保持一个逻辑上的聚合状态所有者。内部可以按 Repository 拆文件，但一次状态变更仍需要：

- 一个版本号。
- 一个原子提交入口。
- 一个幂等键。
- 一个统一事件。
- 一个回滚或失败记录。

禁止南宫、韩立、令狐分别保存完整提案副本。

## 9. Workflow 公共流程模块

```text
workflow/
├─ index.ts
├─ collaboration-workflow.facade.ts
└─ internal/
   ├─ create-collaboration-workflow-runtime.ts
   ├─ persona-capability.registry.ts
   ├─ evolution-flow.orchestrator.ts
   ├─ workflow-state-machine.ts
   ├─ task-distribution.service.ts
   ├─ workflow-recovery.service.ts
   └─ workflow-event.router.ts
```

### 9.1 Workflow 负责

- 判断当前轮到哪个人物。
- 维护流程节点和允许的状态迁移。
- 调用人物公开 Port。
- 调用 Evolution 读写共同状态。
- 分发协作任务。
- 处理暂停、恢复、停止和人工接管。
- 记录跨人物流程事件。
- 防止同一个流程节点重复执行。

### 9.2 Workflow 不负责

- 生成南宫调查结论。
- 替韩立作出审批判断。
- 替令狐分析故障。
- 保存人物私有会话。
- 保存人物提示词。
- 直接实现人物性格和提示词逻辑。

### 9.3 典型流程

```text
Workflow 读取 Evolution 当前状态
    ↓
通知 NangongPort 调查并形成提案
    ↓
Evolution 保存提案
    ↓
通知 HanliPort 审批
    ↓
Workflow 分发协作任务
    ↓
通知 LinghuPort 执行统一测试和恢复
    ↓
通知 HanliPort 真实应用验收
    ↓
Evolution 完成归档
```

## 10. 人物之间的依赖规则

### 10.1 禁止人物直接依赖

禁止：

```text
nangong -> hanli
hanli   -> linghu
linghu  -> nangong
```

禁止源码形式：

```ts
import { HanliApprovalService } from "../hanli/internal/...";
```

```ts
import { NangongProposalService } from "../nangong/internal/...";
```

### 10.2 正确依赖

```text
Workflow -> NangongPort
Workflow -> HanliPort
Workflow -> LinghuPort

Nangong -> EvolutionPort
Hanli   -> EvolutionPort
Linghu  -> EvolutionProposalPort
```

人物模块只知道稳定 Port，不知道其他人物类名和内部文件。

### 10.3 依赖方向

```text
Contracts
    ↑
人物 Facade / Evolution Facade / Workflow Facade
    ↑
Runtime 组合
    ↑
Electron main 与 IPC
```

内部 Store、Analyzer、Runner 和具体 Service 不能反向成为外部依赖。

## 11. Interface、继承和组合规范

### 11.1 公共生命周期接口

允许建立小型稳定接口：

```ts
export interface PersonaLifecyclePort {
  readonly memberId: string;
  start(): void;
  stop(): void;
}
```

三个人物可以分别实现：

```ts
NangongRuntime implements PersonaLifecyclePort
HanliRuntime implements PersonaLifecyclePort
LinghuRuntime implements PersonaLifecyclePort
```

### 11.2 人物能力接口

```ts
export interface ProposalAuthorPort {
  createProposal(input: CreateProposalInDto): Promise<ProposalReferenceOutDto>;
}

export interface ProposalReviewerPort {
  reviewProposal(input: ReviewProposalInDto): Promise<ProposalDecisionOutDto>;
}

export interface FlowGuardianPort {
  checkNow(): Promise<void>;
}
```

人物只实现真正拥有的能力：

| 人物 | 能力接口 |
|---|---|
| 南宫 | 生命周期、调查、专题、提案作者 |
| 韩立 | 生命周期、研讨、审批、验收 |
| 令狐 | 生命周期、流程保障、统一测试 |

### 11.3 禁止巨大父类

禁止：

```ts
abstract class BasePersona {
  createTopic() {}
  approveProposal() {}
  runUnifiedTests() {}
  inspectApplication() {}
  archiveResult() {}
}
```

原因：

- 人物职责不同。
- 新人物会被迫实现无关方法。
- 父类会成为新的共享热点。
- 父类状态变化会同时影响全部人物。
- TypeScript 不支持多重类继承。

### 11.4 允许继承的条件

只有同时满足以下条件才允许 `extends`：

1. 子类确实是父类的一种。
2. 父类行为对所有子类都成立。
3. 父类没有人物专属业务。
4. 不需要通过覆盖方法改变核心语义。
5. 新人物不会被迫实现无关能力。

通常优先使用 `implements` 和依赖注入。

## 12. 人物能力注册表

### 12.1 目标

未来增加人物时，不能在多个共享文件不断增加：

```ts
if (memberId === "nangong-wan") {}
else if (memberId === "han-li") {}
else if (memberId === "linghu-ancestor") {}
else if (memberId === "zi-ling") {}
```

应由 Workflow 内部注册表按能力查找人物。

### 12.2 登记结构示例

```ts
export interface PersonaRegistration {
  memberId: string;
  displayName: string;
  runtime: PersonaLifecyclePort;
  capabilities: readonly PersonaCapability[];
}
```

```ts
registry.register({
  memberId: "nangong-wan",
  displayName: "南宫婉",
  runtime: nangongRuntime,
  capabilities: ["investigation", "proposal-authoring"],
});
```

```ts
registry.register({
  memberId: "han-li",
  displayName: "韩立",
  runtime: hanliRuntime,
  capabilities: ["deliberation", "proposal-review", "acceptance"],
});
```

```ts
registry.register({
  memberId: "linghu-ancestor",
  displayName: "令狐老祖",
  runtime: linghuRuntime,
  capabilities: ["flow-guard", "unified-test"],
});
```

### 12.3 按能力调用

```ts
const reviewer = registry.requireCapability<ProposalReviewerPort>("proposal-review");
const decision = await reviewer.reviewProposal(input);
```

Workflow 不需要知道当前审批者具体是韩立还是未来的新人物。

### 12.4 注册表边界

- 注册表只保存稳定人物描述和能力 Port。
- 不保存人物私有 Store。
- 不读取人物内部文件。
- 不替人物执行业务判断。
- 同一独占能力出现多个实现时必须有明确选择策略，禁止随机调用。


### 14.5 DTO 方向

每个模块分别站在自己的边界判断：

- 数据进入本模块：`InDto`。
- 数据离开本模块：`OutDto`。
- 本模块主动输出事件：`EventOutDto`。

共享提案不能同时在南宫和韩立目录复制定义。提案本体属于 Evolution，人物 DTO 只携带提案 ID、人物输入和人物输出判断。

- 令狐修正提案。

## 18. 每阶段测试门禁

### 18.1 静态边界测试

必须检查：

- 人物目录相互不导入 internal。
- 外部只能通过各模块 index。
- Workflow 不导入人物 internal。
- 人物不直接导入其他人物 Facade 文件。
- Evolution 不依赖人物模块。
- Store、Runner 和 Repository 不从公开 index 导出。
- 旧平铺文件最终不存在。

### 18.2 Contracts 测试

必须检查：

- 文件使用 `.in.dto.ts` 或 `.out.dto.ts`。
- 类型使用 `InDto`、`OutDto`、`EventOutDto`。
- 每个文件说明生产方、接收方、流向和禁止职责。
- 共同提案类型只有一个权威定义。
- 不存在跨人物 DTO 循环导入。

### 18.3 业务回归

至少覆盖：

- 南宫对话失败与重试。
- 对话转换专题。
- 专题证据不足。
- 提案创建、修订和版本递增。
- 韩立研讨多轮追问。
- 自动审批与人工审批。
- 退回补充和驳回。
- 分发计划校验。
- 多任务执行结果汇总。
- 令狐修正提案进入审批。
- 统一测试失败恢复。
- 韩立验收计划和真实应用检查。
- 应用重启后的流程恢复。

### 18.4 并发和幂等

- 同一提案不能重复审批。
- 同一 Mutation Key 不能重复提交。
- 同一 Workflow 节点不能同时由两个人物执行。
- 测试资源仍由唯一协调器管理。
- 状态版本冲突必须失败，不能静默覆盖。

## 19. 多人分支协作规则

目标是让不同开发者尽量修改不同目录：

| 开发范围 | 主要目录 |
|---|---|
| 南宫对话和调查 | `nangong/` |
| 韩立审批和验收 | `hanli/` |
| 令狐保障和测试 | `linghu/` |
| 提案数据和 Repository | `evolution/` |
| 跨人物流程 | `workflow/` |

多人协作时：

- 一个任务必须声明主要模块所有权。
- 人物内部变化不能顺便修改 Workflow。
- Workflow 变化不能顺便重写人物判断。
- DTO 变更必须先修改所属 Contracts index，再迁移消费者。
- 跨模块变更应拆成端口变更和各模块适配两个阶段。
- 避免多人同时修改 `electron/main.ts`，运行时组装优先放入各模块 Runtime 工厂。

## 20. 风险与控制

### 20.1 状态拆散风险

风险：把当前大 Store 机械拆成南宫 Store 和韩立 Store，造成提案状态不同步。

控制：先中立重命名为 Evolution Store，保持单一原子提交，再只拆人物私有状态。

### 20.2 循环依赖风险

风险：南宫调用韩立，韩立调用令狐，令狐再调用南宫。

控制：人物之间只通过 Workflow、Evolution Port 和事件交互。

### 20.3 过度抽象风险

风险：为了未来人物提前建立大量无调用方接口。

控制：接口只能从当前真实调用方提取，每个接口必须有生产实现和消费者。

### 20.4 巨大父类风险

风险：把所有人物方法放入 `BasePersona`，形成新的共享热点。

控制：只允许小型生命周期接口和能力接口，优先组合。

### 20.5 行为回退风险

风险：目录迁移时改变审批、恢复或自动运行语义。

控制：每阶段先保持对象字段和事件编码不变，业务变化另立任务。

### 20.6 数据迁移风险

风险：重命名 Store 后旧数据库或 JSON 无法恢复。

控制：保留版本迁移器、备份读取和旧字段兼容测试，统一测试通过后再删除旧兼容。

## 21. 回滚策略

每个阶段必须具备独立回滚点：

1. 目录壳层阶段只回滚导入路径。
2. Store 中立化阶段保留旧状态读取器。
3. 南宫提取阶段保留旧 Facade 方法转发，待调用方迁移后删除。
4. 韩立提取阶段同样保留短期转发。
5. Workflow 提取阶段保留旧事件编码和恢复点。
6. Contracts 拆分阶段保留短期类型别名，但不得保留两份运行数据定义。

禁止使用无法恢复的批量删除作为第一步。

## 23. 最终验收标准

全部满足后才能认为拆分完成：

1. 南宫、韩立、令狐是并列一级目录。
2. 每个人物拥有唯一 index、Facade 和 Runtime。
3. 人物之间没有直接实现依赖。
4. Workflow 独立编排跨人物顺序。
5. Evolution 是共同提案和审批状态的唯一所有者。
6. Facade 不公开内部 Store、Runner、Repository 和常量。
7. Contracts 按模块和数据方向拆分。
8. Renderer 人物页面与共享演化视图分开。
9. 新人物可以通过新增目录、实现能力接口和注册能力接入。
10. 新人物接入不要求修改现有人物内部文件。
11. 不存在巨大 `BasePersona`。
12. 不存在人物之间的循环依赖。
13. 旧平铺文件和旧公开出口全部删除。
14. 旧状态数据可以恢复或完成受控迁移。
15. 边界、业务、并发、交互、构建和启动测试全部通过。

```text
人物模块决定“自己怎么做”；

Evolution 保存“大家共同处理的数据”；
人物交叉使用 Port、事件和组合，不使用人物之间的类继承。
```
