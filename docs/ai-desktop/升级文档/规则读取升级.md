# AI Desktop 提示词与长期规则记忆架构方案

## 1. 文档目标

AI Desktop 需要同时管理两类能够改变 AI 行为的资源：

- 提示词：描述当前人物在当前业务阶段要完成什么、如何表达以及返回什么格式。
- 规则：保存用户长期积累的判断标准、工程约束、人物职责、测试要求和规则自我完善方式。

提示词不能代替长期规则，规则也不能代替程序权限和状态机。本方案在保留现有提示词库的基础上，把 `ruleengine` 建设为 AI Desktop 的长期规范记忆库，并支持有源码与无源码两种持续运行方式。

## 2. 已确认的总体原则

1. `AGENTS.md` 是 Codex 和 AI Desktop 的统一启动入口，不再使用 `AiAgent.md`。
2. AI Desktop 运行时只进入当前用户规则层，不加载 `local/core`，不加载 `local/common`。
3. 当前用户不能写死为 `XUNAN`；优先从 `AGENTS.md` 读取，未填写时使用 UI 当前登录并连接的账号。
4. 当前用户只能新增、更新和删除自己的规则，不能修改 core、common 或其他用户规则。
5. 发生同逻辑 ID 或同规则语义冲突时，以当前用户规则为准。
6. 韩立、南宫婉、执行者和令狐拥有各自长期专有规则，但共享同一当前用户身份和规则索引体系。
7. AI 根据索引判断需要的专项规则，程序负责校验逻辑 ID、路径、依赖、用户边界和加载回执。
8. UI 目录树当前主工程是判断 AI Desktop 源码是否存在的唯一入口，不增加另一套路径选择器。
9. 检测到 AI Desktop 源码时，现有 Git、构建、测试、发布和重启流程保持不变。
10. 未检测到 AI Desktop 源码时，使用 AI Desktop 本地规则工作区；规则修改后立即供后续任务加载，并生成 ZIP 等待异步上传。

## 3. AGENTS 统一入口

### 3.1 源码布局目标

完整 `AGENTS.md` 正文迁入：

```text
apps/ai-desktop/ruleengine/AGENTS.md
```

工程根保留一个最小转发入口，供从工程根启动的 Codex 自动发现：

```text
AGENTS.md
  → 要求完整读取 apps/ai-desktop/ruleengine/AGENTS.md
```

完整正文是唯一权威内容，根文件不得复制规则正文。AI Desktop 直接读取 `ruleengine/AGENTS.md`，不经过根转发文件。

### 3.2 AI Desktop 最小启动链

```text
AGENTS.md
  → 解析当前稳定用户
  → 读取根 RULE_INDEX 中的 USER_RULE_INDEX_PATTERN
  → 进入 local/<active-user>/RULE_INDEX.md
  → 加载当前人物专有规则
  → 根据当前任务加载专项规则
  → 完成阶段执行测试和规则沉淀门禁
```

AI Desktop 可以读取根索引中的用户入口模式，但不得继续加载根索引登记的 core 规则，也不得进入 common 子树。

### 3.3 必须保留的完成门禁

完整 `AGENTS.md` 至少保留并驱动以下固定门禁：

- 稳定用户与规则沉淀完成门禁；
- 测试门禁；
- 当前回合训练语料元数据。

用户可见最终回答执行训练语料元数据门禁；人物之间的内部结构化交接使用业务事件字段，不向内部协议正文机械追加 HTML 注释。

## 4. 当前用户解析与隔离

### 4.1 用户解析顺序

```text
1. AGENTS.md 填写了安全、唯一的当前稳定用户 ID
   → 使用该用户

2. AGENTS.md 没有填写当前用户
   → 使用 UI 当前登录并连接账号的稳定身份

3. 两者都不存在
   → 阻止开始人物任务并提示用户登录
```

现有 `XUNAN` 来自 `AGENTS.md`，不得在 Electron、加载器或人物服务中写死。

### 4.2 登录账号映射

UI 显示名称可以改变或重复，不能直接作为规则目录名。内部使用认证提供方返回的不可变账号标识建立一次性映射：

```json
{
  "provider": "account-provider",
  "accountSubject": "immutable-account-id",
  "displayName": "UI 当前显示名称",
  "stableUserId": "U_7F3A91"
}
```

界面需要同时显示当前规则用户、身份来源和规则目录。稳定用户 ID 建立后不能随昵称、头像或邮箱显示值变化。

### 4.3 用户边界

AI Desktop 运行模式固定为：

```text
allowedLayers = [active-user]
```

允许写入：

```text
local/<active-user>/**
```

禁止写入：

```text
local/core/**
local/common/**
local/<other-user>/**
```

当前用户规则发现 core 或 common 不完整时，只能在当前用户层新增或升级近义规则。用户规则需要局部覆盖时使用 `override_mode=extend`；需要整体否定低层语义时使用 `override_mode=replace`。AI Desktop 的 active-user-only 加载器不能通过依赖闭包重新进入 core 或 common。

切换登录账号时，正在执行的任务继续使用已经冻结的用户和规则快照，新任务使用新账号；规则目录、ZIP 队列、上传记录和会话数据不能跨用户混用。

## 5. UI 主工程与规则工作区解析

### 5.1 唯一目录来源

只使用 UI 目录树 `workspaceState.primaryId` 对应的 `root.path`，禁止扫描多个挂接目录猜测 AI Desktop 源码位置。

当前主目录同时具备以下文件时，认定 AI Desktop 源码存在：

```text
<workspaceRoot>/apps/ai-desktop/package.json
<workspaceRoot>/apps/ai-desktop/ruleengine/AGENTS.md
<workspaceRoot>/apps/ai-desktop/ruleengine/rules/RULE_INDEX.md
<workspaceRoot>/apps/ai-desktop/ruleengine/rules/local/<active-user>/RULE_INDEX.md
```

当前 SELPLAT 的解析结果为：

```text
workspaceRoot = C:/opt/workspace/SELPLAT
aiDesktopSourceRoot = C:/opt/workspace/SELPLAT/apps/ai-desktop
ruleRoot = C:/opt/workspace/SELPLAT/apps/ai-desktop/ruleengine/rules
```

### 5.2 源码模式

检测到 AI Desktop 源码时，保持现有流程不变：

```text
修改源码中的 ruleengine/rules/local/<active-user>
  → 更新所属 RULE_INDEX
  → 在任务 worktree 验证
  → Git 提交与集成
  → 构建
  → 统一测试
  → 发布
  → 重启加载新程序版本
```

规则 Markdown 本身修改后可由下一轮任务重新加载；Electron 或 Renderer 程序源码修改仍必须经过完整构建、测试、发布和重启。

### 5.3 无源码模式

未检测到 AI Desktop 源码时，使用 AI Desktop 拥有的可写规则工作区：

```text
<userData>/rule-workspace/
├─ AGENTS.md
├─ rules/
│  ├─ RULE_INDEX.md
│  └─ local/
│     └─ <active-user>/
│        ├─ RULE_INDEX.md
│        └─ ...
├─ releases/
├─ upload-outbox/
├─ upload-history/
├─ state.json
└─ .git/
```

安装包中的规则快照只用于首次初始化和损坏恢复。初始化完成后，本地规则工作区是无源码模式的权威规则来源。应用升级不得覆盖它。

无源码模式允许规则继续新增和升级，并在本地规则仓库记录版本。以后重新引入 AI Desktop 源码时，根据逻辑 ID、规则版本和内容哈希生成同步提案，审查后再合入源码 Git，禁止直接整目录覆盖。

## 6. 规则发现与加载能力

### 6.1 不能只依赖模型读文件

AI 可以根据索引判断需要什么规则，但程序必须提供受控规则能力：

```text
searchRules(role, stage, taskSummary)
loadRule(logicalId)
loadRuleBundle(logicalIds)
getRuleReceipt()
reportRuleGap(existingRuleId, evidence, proposal)
```

程序负责：

- 解析当前用户；
- 只允许进入当前用户索引树；
- 校验逻辑 ID、相对路径和索引可达性；
- 递归补齐当前用户层内的显式依赖；
- 阻止 core、common、其他用户和路径逃逸；
- 返回已加载逻辑 ID、真实路径、版本和内容哈希回执；
- 缓存未变化的规则快照，并在索引或规则文件变化后失效。

### 6.2 分析阶段也加载规则

分析阶段必须读取相关规则，否则无法判断问题属于代码还是规则：

```text
代码不符合已有规则
  → 建议修正代码

规则与当前真实代码事实冲突
  → 建议升级当前用户规则

现有规则没有覆盖可复用问题
  → 建议新增当前用户规则

只是一次性业务差异
  → 不沉淀规则
```

分析人物可以登记规则修正候选，但没有授权时不能修改规则文件。

### 6.3 任务规则快照

每个任务开始时冻结：

```text
activeUserId
ruleRevision
loadedRuleIds
loadedRuleHashes
ruleReceipt
```

正在执行的任务继续使用冻结快照，避免执行中途规则漂移。新任务和人物下一轮分析使用最新规则版本。

## 7. 四类人物专有规则

四类人物共享当前用户身份和索引入口，但不能加载完全相同的规则集合。

建议建立人物职责子索引：

```text
local/<active-user>/selplat/应用/ai-desktop/
├─ RULE_INDEX.md
├─ index/
│  └─ 人物职责/
│     └─ RULE_INDEX.md
└─ rule/
   ├─ RUL_AIDesktop韩立用户代理提问规则.md
   ├─ RUL_AIDesktop南宫婉调查与规划规则.md
   ├─ RUL_AIDesktop执行者源码实施规则.md
   └─ RUL_AIDesktop令狐故障修复与统一测试规则.md
```

建议逻辑 ID：

```text
AI_DESKTOP_HANLI_USER_QUESTIONING_RULES
AI_DESKTOP_NANGONG_ANALYSIS_PLANNING_RULES
AI_DESKTOP_EXECUTOR_SOURCE_IMPLEMENTATION_RULES
AI_DESKTOP_LINGHU_FAILURE_TEST_RULES
```

### 7.1 韩立

韩立相当于用户代理提问者，主要负责向南宫婉持续提问并确认下一步改动：

- 结合完整会话、当前专题和相关规则找出唯一关键缺口；
- 确认问题、目标、范围、排除项、证据和验收条件；
- 判断南宫婉的回答是否足以形成下一步修改；
- 不替南宫婉调查源码，不替执行者修改源码；
- 不凭空创造用户没有提出的产品限制。

### 7.2 南宫婉

南宫婉负责调查、规划和规则缺口发现：

- 调查真实源码、历史事实、运行证据和当前用户规则；
- 区分已证实事实、合理推断和仍需验证内容；
- 判断应修代码、升级规则还是新增规则；
- 形成明确、可验收、可独立分发的修改方案；
- 授权和审批前保持只读，不直接修改源码或规则。

### 7.3 执行者

执行者只实施已经批准的明确任务：

- 不重新解释和扩大用户目标；
- 按目标文件和语言加载当前用户编码、架构、业务及测试规则；
- 在批准范围内修改源码或当前用户规则；
- 记录变更证据和待测项目；
- 不修改 core、common、其他用户规则或任务外文件。

动态普通成员复用同一个执行者 Runtime，人物身份作为任务参数传入，不能为每个姓名复制一套执行程序。

### 7.4 令狐

令狐负责失败调查、最小修复和统一测试：

- 先只读调查失败阶段、直接原因和真实证据；
- 根据调查结论建立独立修复指令；
- 只修复已经证实的问题，禁止借修复重新执行原专题；
- 执行统一测试、失败复测和发布前验证；
- 规则修复也只能写入当前用户层。

## 8. 规则持续优化闭环

人物可以持续发现和改善规则，但不能在后台静默改写：

```text
发现重复问题或规则缺口
  → 查询当前用户近义规则
  → 收集代码、运行和历史证据
  → 南宫婉形成规则修正候选
  → 韩立追问并确认必要性和边界
  → 取得用户授权
  → 执行者修改当前用户规则和索引
  → 令狐验证索引、依赖和相关测试
  → 保存规则版本
  → 后续新任务加载新 revision
```

规则变更必须得到以下结论之一：

- 升级现有当前用户规则；
- 新增当前用户规则；
- 无需沉淀，并记录近义规则和原因。

## 9. 无源码规则 ZIP 与异步上传

### 9.1 生成规则包

无源码模式完成一次规则修改并验证后：

```text
原子更新本地有效规则树
  → 更新 ruleRevision
  → 后续任务立即可用
  → 生成版本化 ZIP
  → ZIP 进入 upload-outbox
```

ZIP 至少包含：

```text
rule-package.json
AGENTS.md
rules/RULE_INDEX.md
rules/local/<active-user>/RULE_INDEX.md
rules/local/<active-user>/**
```

禁止包含会话原文、账号凭证、HTTP 密钥、Git 凭证、机器绝对路径、缓存、日志、临时文件、core、common 和其他用户规则。

`rule-package.json` 至少记录：

- 格式版本；
- 当前稳定用户 ID；
- 本次和上一个规则 revision；
- 创建时间；
- 每个文件的相对路径、大小和 SHA-256；
- 新增、修改和删除的逻辑 ID；
- 来源任务与授权记录；
- AI Desktop 版本；
- 上传幂等键和当前状态。

### 9.2 启动时单次异步上传

AI Desktop 每次启动只异步尝试上传一次：

```text
应用窗口启动
  → 本地规则工作区初始化和校验
  → 查找最新待上传 ZIP
  → 后台调用上传接口一次
  → 不等待上传结果，应用继续运行
```

约束：

- 每个应用进程最多自动尝试一次；
- 没有待上传 ZIP 时不发送请求；
- ZIP SHA-256 作为幂等键；
- 必须设置连接和响应超时；
- 上传成功后保存服务端回执并移出 outbox；
- 上传失败只记录原因，ZIP 留在 outbox，等待下次启动；
- 当前进程不循环重试；
- 上传失败不能阻断本地规则加载、人物对话和任务执行；
- 服务端响应不能直接覆盖本地规则，下载和合并属于另一条审批流程。

### 9.3 预留上传端口

```ts
interface RulePackageUploader {
  upload(request: {
    packagePath: string;
    packageSha256: string;
    stableUserId: string;
    ruleRevision: string;
    previousRevision: string | null;
    createdAt: string;
  }): Promise<{
    uploadId: string;
    acceptedRevision: string;
  }>;
}
```

默认接入 `DisabledRulePackageUploader`。未配置 HTTP 地址或凭证时仍然生成 ZIP、保存 outbox 并正常使用本地规则。以后通过 `HttpRulePackageUploader` 接入指定服务，业务层不依赖具体 HTTP 客户端。

启动组合根只进行一次非阻塞调用：

```ts
void rulePackageUploadCoordinator.uploadLatestPendingOnce();
```

协调器必须捕获全部异常，不能产生未处理 Promise。

## 10. 提示词库与规则库边界

现有 `apps/ai-desktop/prompts` 继续作为统一提示词库。两者职责固定为：

| 能力 | 负责内容 |
|---|---|
| 提示词 | 当前阶段任务、人物语气、表达方式、输出格式和动态变量 |
| 人物规则 | 人物长期职责、判断原则、禁止边界和工作方法 |
| 工程规则 | 目录、架构、编码、测试、发布和业务约束 |
| 程序门禁 | 工作区权限、沙箱、命令审批、状态机和事务 |
| 会话记忆 | 历史事实、用户偏好、过去问题和执行结果 |

业务代码继续通过稳定提示词 ID 调用 `PromptLibraryFacade.render()`。规则通过独立的索引查询和加载端口进入人物或任务上下文。修改提示词或规则都不能扩大程序授予的文件、命令、网络或审批权限。

## 11. 构建和安装资源

构建时需要生成能够初始化无源码规则工作区的完整只读快照：

```text
apps/ai-desktop/ruleengine/AGENTS.md
+ rules/RULE_INDEX.md
+ 当前发布允许携带的用户规则树
  → build/ai-desktop/rule-bundle
  → resources/ruleengine
```

安装包中的快照不是长期可写权威库。源码模式使用 UI 主工程源码规则；无源码模式使用从快照初始化的 `userData/rule-workspace`。

## 12. 建议实施顺序

1. 将完整 `AGENTS.md` 迁入 `apps/ai-desktop/ruleengine`，工程根保留最小转发入口。
2. 删除空的 `local/XUNAN/AiAgent.md`。
3. 将工作区根和可选 AI Desktop 源码根拆成两个明确概念。
4. 实现 AGENTS 用户优先、登录账号兜底的身份解析和用户映射。
5. 实现 active-user-only 的 TypeScript 规则索引加载器和跨层依赖门禁。
6. 清理当前用户规则对 core/common 的运行时依赖，使用户规则树能够独立加载。
7. 建立韩立、南宫婉、执行者、令狐四套人物专有规则和人物子索引。
8. 为人物分析、任务执行和完成阶段接入按需规则加载及规则回执。
9. 实现源码规则模式和无源码本地规则工作区模式。
10. 实现规则 revision、任务冻结快照和文件变化失效机制。
11. 实现原子规则修改、ZIP 生成、outbox 和本地 Git 版本记录。
12. 预留上传端口，并在启动时异步调用一次。
13. 移除固定 14 条规则全文注入所有 Codex 会话的现有路径。
14. 完成规则索引、人物行为、用户隔离、热加载、ZIP、上传失败降级、构建和真实启动测试。

## 13. 测试与验收计划

- `AGENTS.md` 声明用户时始终优先使用该用户，代码中不存在 `XUNAN` 身份硬编码。
- `AGENTS.md` 未声明用户时使用 UI 当前连接账号的稳定映射。
- 无用户且未登录时明确阻断，不扫描目录猜测用户。
- active-user-only 模式不加载 core、common 或其他用户规则。
- 当前用户依赖闭包不能逃逸当前用户索引树。
