# AI Desktop 协作群时间轴与并行任务生命周期重构方案

## 1. 文档目标

本文解决协作群面板中的三个直接问题：

1. 时间线显示顺序不稳定，用户会感觉新旧消息上下位置混乱。
2. “下一阶段开始时上一阶段停止”缺少明确的任务范围，可能误伤南宫婉并行分发的其他任务。
3. 时间线投影和页面组件职责过多，增加一种节点或隐藏一种进度展示时，容易牵动整个实现。

本次建议采用**最小必要重构**，不重写事件中心，不新造完整工作流引擎，不把简单顺序强行升级成通用 DAG 平台。

AI Desktop 的终局仍是自动产品交付平台：客户向韩立提出需求，南宫婉调查、规划并分发，执行人物完成源码实施和自检，令狐老祖统一测试、修复和发布保障，韩立在真实运行版本上完成客户视角验收。时间线用于忠实展示和审计这条交付链，不能代替业务编排器做决定。

## 2. 结论先行

当前实现具有正确基础，但需要定向重构，不需要推倒重来。

保留：

- `CollaborationTimelineFacade` 统一门面；
- Renderer → DesktopApi → preload → IPC →应用服务的依赖方向；
- 当前三个 SQLite 时间线表；
- 只追加事件、读取时折叠最新节点状态的模型；
- 已有 `PersonaCapabilityRegistry` 人物能力注册机制；
- 已有类型化业务事件和事件中心入口。

重构：

- 建立唯一的时间线排序规则，统一专题卡、节点列表和自动滚动；
- 用“任务执行通道”限定阶段停止范围；
- 把阶段关闭与下一阶段启动集中到一个生命周期服务；
- 把大型时间线投影器按业务事件族拆分并静态登记；
- 把 `TaskCollaborationGroup` 的状态、行为和展示拆开；
- 专属节点展示使用可选渲染扩展，扩展缺失时退回通用节点；
- 删除通用路径中的人物 ID 判断，人物名称和能力从注册表取得。

暂不建设：

- 动态下载安装插件；
- 插件市场、插件权限系统和插件版本协商；
- 通用可视化工作流设计器；
- 为每条记录落库单一 `previousNodeId`、`nextNodeId` 的链表结构；
- 为尚未出现的业务提前建设完整 DAG 调度引擎。

因此，这个方案不会构成过度设计。它只提取已经重复出现且当前正在出错的职责。

## 3. 当前源码事实与问题定位

### 3.1 顺序混乱是架构边界不一致，不只是 CSS 问题

当前读模型存在两套方向：

- 专题卡查询按 `updatedAt DESC` 返回，新更新的专题在前；
- 同一专题内的节点按 `startedAt ASC` 返回，旧节点在上、新节点在下；
- 人物页面把多个专题直接 `flatMap`，再使用 `.at(-1)` 选择滚动目标。

这意味着“最后一个数组元素”不一定是业务上最新的节点。专题是倒序、专题内节点是正序，两者扁平化后会产生跨专题错位。用户看到的“时间显示乱”主要来自查询、组合和滚动目标没有共享同一个顺序定义。

整改原则：

```text
专题卡排序、专题内节点排序、人物消息筛选、当前节点选择、滚动目标
                         ↓
                  共享同一排序语义
```

页面不得通过数组位置猜测“最新节点”。

### 3.2 当前投影模型方向正确，但生命周期关闭散落

现有时间线使用不可变事实追加，再在查询时按 `nodeId` 折叠最新状态。这一设计适合审计，也能保留原人物、原时间和原正文，不应替换成可变快照。

问题在于阶段切换逻辑散落在大型投影器的多个 `if` 分支中。每个分支手工追加“旧节点完成”和“新节点当前”事实。当增加修复、复测或恢复分支时，容易出现：

- 忘记关闭旧节点；
- 关闭了错误任务的节点；
- 同一节点被不同分支以不同规则处理；
- 完成时间由页面或兜底逻辑推测；
- 业务事件已增加，但投影器没有登记对应分支。

### 3.3 页面组件承担了过多职责

`TaskCollaborationGroup` 同时负责节点排序、过滤、展开状态、耗时、恢复动作和 JSX 展示。人物页面还直接判断特定人物并嵌入专属面板。

这不是单纯的“文件太长”问题，而是状态所有权混在一起：

- 时间线业务状态应归主进程投影；
- 页面交互状态应归页面控制器；
- 通用节点展示应归时间线组件；
- 人物或节点专属能力应通过注册扩展提供。

## 4. 必须统一的业务语义

### 4.1 什么是“上一阶段自动停止”

“下一阶段开始时上一阶段自动停止”指的是**同一任务执行通道中的直接上一阶段计时停止**，不是：

- 停止整个专题的其他并行任务；
- 停止同一人物正在处理的所有任务；
- 停止所有时间轴；
- 将专题墙钟时间改为各节点耗时相加；
- 只因页面隐藏就停止或删除节点。

任务执行通道由以下范围确定：

```ts
interface TimelineStepScope {
  groupId: string;
  taskId: string;
  actorMemberId: string;
  assignmentId: string;
  attemptNumber: number;
}
```

其中真正决定前后阶段归属的核心键是：

```text
groupId + taskId + assignmentId + attemptNumber
```

`actorMemberId` 用于记录真实人物与占用，不用于把该人物的其他任务全部停止。

### 4.2 并行分发示例

南宫婉把同一专题拆成任务 A、B、C：

```text
专题分发完成
├─ A：分析 → 执行 → 自检 → 返回
├─ B：分析 → 执行 → 自检 → 返回
└─ C：分析 → 执行 → 自检 → 返回
                    ↓
             全部返回后封存批次
                    ↓
             令狐统一测试与发布
```

当 A 从“分析”进入“执行”时：

- A 的分析节点结束计时；
- A 的执行节点开始计时；
- B、C 的当前阶段保持不变；
- 专题总历时继续按最早开始到当前或最终完成的墙钟时间计算；
- 并行节点耗时不得相加成为专题总历时。

统一测试的开始不是任意任务的 `next`。它是汇合门禁：只有本轮应收任务集合全部返回，并且每个任务带有结果版本后，才封存唯一批次并进入令狐统一测试。

### 4.3 `pre/next` 的正确含义

每个可见节点可以提供 `previousNodeId` 和 `nextNodeId`，用于：

- 界面定位上一条、下一条；
- 展示同一任务通道的阶段关系；
- 测试时间线顺序；
- 帮助用户理解当前节点从哪里来、将去哪里。

它们不能作为跨并行分支的唯一业务依赖。第一阶段先在只读投影中计算，不修改 SQLite 表：

```ts
interface TimelineNodeView {
  node: CollaborationTimelineNodeOutDto;
  previousNodeId: string | null;
  nextNodeId: string | null;
}
```

这里的 `previousNodeId` 是同一执行通道内的直接前置节点，不是数据库中按时间戳排在前面的任意记录。

如果将来真实出现“一个步骤必须等待多个前置步骤、条件分支、人工回退到任意节点”等普遍需求，再把依赖升级为 `predecessorStepIds[]`。现在不增加通用 DAG 表。

## 5. 时间线顺序与滚动规范

### 5.1 唯一排序规则

时间线必须明确两层排序：

1. 专题卡：活动专题优先；同状态按 `updatedAt` 倒序；再以 `groupId` 稳定兜底。
2. 专题内节点：按 `sequenceNumber` 正序；`occurredAt` 和 `factId` 只用于同序号兜底。

节点的 `startedAt` 是业务显示时间，不作为主要排序依据。不同进程的墙钟可能轻微偏差，而事件序号才表示已经提交的业务发生次序。

建议只有一个命名清晰的比较函数：

```ts
function compareTimelineNodes(
  left: CollaborationTimelineNodeOutDto,
  right: CollaborationTimelineNodeOutDto,
): number {
  const sequenceDifference = left.sequenceNumber - right.sequenceNumber;
  if (sequenceDifference !== 0) {
    return sequenceDifference;
  }

  const occurredAtDifference = left.occurredAt.localeCompare(right.occurredAt);
  if (occurredAtDifference !== 0) {
    return occurredAtDifference;
  }

  return left.nodeId.localeCompare(right.nodeId);
}
```

实际字段应以最终 DTO 为准。不得在 Repository、页面控制器和 JSX 中各复制一份不同的排序。

### 5.2 人物页面的最新节点

人物页面不能再对“专题倒序 + 节点正序”的混合数组直接 `.at(-1)`。应先按人物和当前任务筛选，再用统一比较器求真实最新节点。

### 5.3 自动滚动

新节点提交后，只在以下条件全部满足时滚动到底部：

- 当前人物页或协作群页可见；
- 新节点属于当前可见专题或人物；
- 用户原本位于尾部附近，或者这是页面首次进入；
- 用户没有主动展开历史节点并停留阅读。

隐藏页签不得自动滚动。切换页签和任务完成不得丢失会话位置或历史节点。

## 6. 生命周期服务设计

### 6.1 单一职责

新增一个业务名称明确的服务，例如：

```text
CollaborationPhaseTransitionService
```

它只负责：

1. 根据权威业务事件解析任务执行通道；
2. 查找该通道当前活动节点；
3. 在权威下一阶段或真实交接发生时关闭直接上一节点；
4. 追加下一节点；
5. 保证同一事件重放幂等；
6. 拒绝同时存在两个同通道活动写入者。

它不负责：

- 决定南宫婉应该把需求拆成几个任务；
- 决定统一测试是否通过；
- 计算页面 CSS；
- 删除历史事实；
- 根据自由文本猜测任务阶段。

### 6.2 新手可读的实现风格

目标代码应把判断条件写成业务名称，使用明确 `if/else`：

```ts
async function moveToNextPhase(command: MoveToNextPhaseCommand): Promise<void> {
  const scope = createTimelineStepScope(command.event);
  const currentNode = await timelineRepository.findActiveNode(scope);

  if (currentNode === null) {
    await timelineRepository.appendStartedNode(command.nextNode);
    return;
  }

  const isSameTaskLane = isSameTimelineLane(currentNode.scope, scope);
  if (isSameTaskLane === false) {
    throw new Error("Cannot close a node from another task lane.");
  }

  const completionFact = createCompletionFact(currentNode, command.event);
  await timelineRepository.appendTransition(completionFact, command.nextNode);
}
```

避免把业务逻辑压缩成嵌套三元表达式：

```ts
// 不采用
const status = failed ? "failed" : returned ? "completed" : running ? "current" : "waiting";
```

改成清楚的业务判断：

```ts
function resolveNodeStatus(state: TimelineState): TimelineNodeStatus {
  if (state.failed === true) {
    return "failed";
  }

  if (state.returned === true) {
    return "completed";
  }

  if (state.running === true) {
    return "current";
  }

  return "waiting";
}
```

“新手写法”不是复制更多代码，而是让变量、分支、输入和输出能直接对应业务语言。

### 6.3 完成时间来源

阶段结束时间只能来自权威下一阶段事件或真实交接事件的发生时间。不得使用：

- 页面收到通知的时间；
- `Date.now()` 猜测历史完成时间；
- 下一次查询时间；
- Renderer 根据状态自行补齐的时间。

事件重放产生修正事实时，旧事实保持不变，查询投影折叠到最新有效状态。

## 7. 投影器拆分与可插拔边界

### 7.1 按业务事件族拆分

现有大型 `collaboration-timeline-flow.projector.ts` 建议按以下业务所有权拆分：

```text
timeline/projectors/
├─ submission-distribution.projector.ts
├─ execution.projector.ts
├─ self-check.projector.ts
├─ repair.projector.ts
├─ integration-verification.projector.ts
├─ acceptance-recovery.projector.ts
├─ unknown-event.projector.ts
└─ timeline-projector.registry.ts
```

拆分依据是事件族和状态所有权，不是为了把文件机械切短。

### 7.2 小接口、静态注册

第一阶段使用编译期静态注册：

```ts
interface CollaborationTimelineProjector {
  supports(event: CollaborationFlowEvent): boolean;
  project(event: CollaborationFlowEvent): Promise<void>;
}
```

注册表按事件类型找到唯一投影器。找不到映射时必须产生可读的未知事件节点并登记异常，不能静默丢弃。

静态注册已经满足“新增一种时间线业务不用修改巨型 `if/else`”的可插拔目标，也避免过早引入动态插件加载、权限、版本和隔离机制。

### 7.3 展示扩展可以拔掉，业务事实不能拔掉

展示层允许为特定节点类型登记可选扩展：

```ts
interface TimelineNodeRendererExtension {
  supports(node: CollaborationTimelineNodeOutDto): boolean;
  render(node: CollaborationTimelineNodeOutDto): React.ReactNode;
}
```

必须有通用兜底渲染器。某个扩展被禁用、删除或加载失败时：

- SQLite 历史事实仍保留；
- 通用节点仍显示人物、方向、状态、时间和正文；
- 当前计时仍由主进程投影负责；
- 其他节点不受影响；
- 页面不得把扩展不可用解释为业务节点不存在。

“不显示某个时间轴进度”只能是显示过滤，不能执行数据库删除，也不能修改任务生命周期。

## 8. Renderer 组件边界

建议把当前页面按职责整理为同级文件，而不是增加空包装层：

```text
TaskCollaborationGroup.tsx          # 组件装配与布局
TaskCollaborationGroupView.tsx      # 纯展示
TaskCollaborationGroup.types.ts     # 页面输入和展示模型
useTaskCollaborationGroup.ts        # 展开、滚动、交互控制器
TimelineNodeView.tsx                # 通用节点
timeline-node-renderer.registry.ts  # 可选专属展示登记
```

约束：

- JSX 中不写内联异步业务流程；
- 点击处理器使用命名函数；
- 页面只消费 DTO，不根据文案猜状态和人物；
- 耗时状态由主进程事实决定，页面只格式化显示；
- 可复用的 Disclosure、Button、Window 等视觉控件继续使用 SELUI；
- 特定人物面板通过正式扩展槽注入，不在通用页面判断人物 ID；
- 没有实际职责的 wrapper、manager、helper 不创建。

## 9. 人物注册与硬编码收敛

已有 `PersonaCapabilityRegistry` 是正确基础。时间线和人物页面应通过注册信息获得：

- `memberId`；
- 显示名称；
- 能力；
- 可选专属动作或展示扩展。

通用时间线路径不得再出现类似：

```ts
if (memberId === "linghu-ancestor") {
  // 注入专属面板
}
```

本次不新增创建、重命名或删除默认人物的接口。工程规则要求保留稳定默认人物和历史。这里的“可插拔”指能力和展示扩展可登记、可退回通用实现，不是允许页面删除人物和历史。

## 10. 数据兼容与迁移策略

### 10.1 第一阶段不改表

现有时间线表已经支持：

- 专题、任务和节点标识；
- 来源事实键；
- 序号；
- 状态；
- 开始和完成时间；
- 只追加事实和读取折叠。

因此第一阶段不新增 `pre/next` 数据库列。`previousNodeId` 和 `nextNodeId` 由投影查询按任务执行通道计算。

### 10.2 需要新增字段时的门禁

只有在现有事件无法稳定取得 `assignmentId` 或 `attemptNumber`，并且源码与真实数据证据证明仅靠现有字段会错误合并不同修复轮次时，才新增正式 schema 和迁移。

如需迁移，必须：

- 新增正式 SQL schema 文件和版本登记；
- 不原地修改已发布 SQL；
- 不从自由文本回填身份；
- 不删除 1009 至 1011 当前时间线表中的历史；
- 为新安装和现有数据库分别测试；
- 保持旧事实可读，新事实使用明确版本。

## 11. 实施顺序

### 阶段 A：先修排序和滚动

1. 定义唯一专题与节点比较器。
2. Repository 按 `sequenceNumber` 为主排序。
3. 人物页面不再扁平化后用 `.at(-1)` 猜最新节点。
4. 自动滚动增加可见性、尾部位置和人工阅读保护。

这是用户当前最直接可感知的问题，风险最低，应先独立交付。

### 阶段 B：集中生命周期切换

1. 定义 `TimelineStepScope`。
2. 建立同任务通道活动节点查询。
3. 建立 `CollaborationPhaseTransitionService`。
4. 把旧节点关闭和新节点开始放入同一事务性追加操作。
5. 将已有分支逐个迁移到该服务。

### 阶段 C：拆分投影器

1. 建立小型投影器接口和静态注册表。
2. 按事件族迁移现有分支。
3. 增加未知事件可读兜底。
4. 保持统一 Facade 和事件中心入口不变。

### 阶段 D：整理页面

1. 抽出页面控制器和展示模型。
2. 使用命名处理器替换 JSX 内联异步流程。
3. 建立通用节点和可选展示扩展注册表。
4. 扩展缺失时验证通用兜底。

### 阶段 E：收敛人物硬编码

1. 通用路径从 `PersonaCapabilityRegistry` 读取人物信息。
2. 专属能力使用 capability 或 extension key 登记。
3. 保留稳定默认人物、历史和受保护职责。

### 阶段 F：完整验证

源码实施完成后，按工程规则执行：

1. 目标单元测试和集成测试；
2. 类型检查；
3. 隔离 Electron 交互测试；
4. 正式构建；
5. 生产文件和正式窗口尺寸下的交互测试；
6. 实际启动、健康检查和页面验收。

## 12. 必须覆盖的测试

### 12.1 顺序

- 同一专题节点永远旧上新下；
- 事件时间存在时钟偏差时仍以 `sequenceNumber` 排序；
- 多专题混合时，人物页能找到真实最新节点；
- 同序号使用事件时间和稳定 ID 得到确定顺序；
- 重启后顺序与重启前一致。

### 12.2 同任务阶段切换

- A 的分析开始后只有一个活动分析节点；
- A 执行开始时，A 分析使用权威事件时间完成；
- A 自检开始时，A 执行完成；
- 重放同一事件不产生重复开始或重复完成副作用；
- 终态节点不会因为缺少历史时间一直计时。

### 12.3 并行隔离

- A 进入执行不会停止 B 的分析；
- A 失败进入令狐调查不会停止 B、C 的正常执行；
- 同一人物持有两个独立任务时，一个任务切阶段不会关闭另一个任务；
- 修复轮次 2 不会覆盖轮次 1 的历史；
- 当前人物占用数量按唯一活动任务计算，不按节点历史重复计数。

### 12.4 汇合门禁

- A 返回、B 未返回时不封存批次；
- 所有应收任务都返回且具有结果版本后只封存一次；
- 迟到或旧代次结果被拒绝；
- 统一测试失败后进入令狐调查、修复和复测，不伪造南宫婉再次转发。

### 12.5 可插拔与历史保护

- 删除一个展示扩展后通用节点仍可见；
- 隐藏一种进度只影响当前显示，不删除数据库事实；
- 未知事件产生可读兜底节点并登记异常；
- 一个投影器失败不会被 Renderer 静默吞掉；
- 通用时间线不依赖固定人物 ID。

### 12.6 页面交互

- 当前节点首次自动展开；
- 用户手工折叠后自动刷新不夺回控制权；
- 隐藏页签不滚动；
- 用户阅读历史时新消息不强制跳到底部；
- 用户位于尾部时新消息追加后滚动到最新；
- 切换人物和专题不丢失已完成历史。

### 12.7 可读性和边界

- 无嵌套三元表达式承载生命周期判断；
- JSX 无内联异步业务流程；
- 投影器之间不直接相互调用；
- Renderer 不直接访问 SQLite、文件日志或事件旁路；
- composition root 只装配，不包含阶段映射；
- contracts 保持纯净，不依赖 Electron、React 或数据库实现。

## 13. 完成定义

只有同时满足以下条件，才能宣布本次重构完成：

1. 时间线在协作群和所有人物页都按明确顺序显示。
2. 当前节点、最新节点和滚动目标使用同一业务排序语义。
3. 下一阶段只关闭同任务、同分配、同轮次的直接上一阶段。
4. 南宫婉并行分发的任务可以独立开始、停止和失败恢复。
5. 专题总历时使用墙钟时间，不累加并行节点。
6. 所有阶段切换来自权威类型化事件，不由页面猜测。
7. 历史事实保持只追加，重放幂等。
8. 投影器可以按事件族增加，未知事件不静默丢失。
9. 展示扩展可移除，通用时间线和历史数据不受损。
10. 通用实现不硬编码人物 ID。
11. 关键业务判断使用命名变量和清楚的 `if/else`。
12. 目标测试、构建、生产桌面交互和实际启动全部通过。
