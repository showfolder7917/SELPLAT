1. 观察模式
     用户与南宫婉正常对话，韩立只记录“问题—回答—用户后续反应—最终决策”。

  2. 影子模式
     每次用户回答前，韩立先在后台预测用户可能怎么问、怎么判断，但不直接发送。然后与用户真实回答比较。

  3. 辅助模式
     韩立生成建议回复，用户确认、修改或拒绝后再发给南宫婉。修改内容成为高价值训练样本。

  4. 委托模式
     韩立在明确范围内代替用户与南宫婉对话。低置信度、重大方向、删除、发布和扩大范围时交还用户。

  5. 自主模式
     韩立与南宫婉完成需求澄清、任务拆解、开发监督、测试和恢复，最终只向用户汇报结果及需要决策的事项。

  小部分交给 Sol。

  ### 韩立的四层记忆

   层级           内容                                    是否允许遗忘
  ━━━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━━━━━
   L0 硬规则      授权、删除、测试、发布、安全边界        永不自动遗忘
  ─────────────  ──────────────────────────────────────  ────────────────────────
   L1 用户原则    用户稳定的判断方法、关注点、提问习惯    只有用户新决定才能替代
  ─────────────  ──────────────────────────────────────  ────────────────────────
   L2 决策案例    特定场景下用户如何提问、批准或拒绝      按相关性检索
  ─────────────  ──────────────────────────────────────  ────────────────────────
   L3 原始历史    完整对话、附件、执行结果                长期归档，必要时回查

  每次只向 Sol 提供：

  - 当前任务和工程；
  - 命中的硬规则；
  - 相关用户原则；
  - 最相似的少量历史案例；
  - 最近一轮上下文；
  - 存在冲突时的冲突说明。

  不需要把十万条历史全部塞进去。

  ### 防止“检索不到就是忘记”

  单纯向量搜索不够，应同时使用：

  - 工程、应用、文件、业务类型等精确过滤；
  - 关键词全文检索；
  - 语义相似度检索；
  - 时间、新旧版本和确认等级；
  - 用户明确固定的高优先级；
  - 二次重排，选出最适合当前问题的记录；
  - 找不到可靠记忆时主动询问用户。

  一条记忆可以保存成：

  {
    "memory_id": "decision-203",
    "scope": {
      "project": "SELPLAT",
      "application": "ai-desktop",
      "topic": "test-approval"
    },
    "trigger": "用户要求修改程序源码",
    "preferred_action": "先取得独立1，再开始修改",
    "evidence_requirement": "完成后登记待统一测试项",
    "confidence": 1.0,
    "status": "active",
    "source": ["conversation-18"],
    "supersedes": null
  }

  ### 真正危险的不是数据量

  更大的风险是：

  1. 同一件事存在互相冲突的旧记忆；
  2. 把一次性要求错误提升为永久习惯；
  3. 新决定没有替代旧决定；
  4. 只找到语义相似、实际作用域不同的记录；
  5. 韩立置信度不足却假装理解用户；
  6. 原始对话被总结后丢失关键限定条件。

  因此必须保留：

  - 原始对话；
  - 记忆来源；
  - 生效范围；
  - 创建时间和最后确认时间；
  - 置信度；
  - 被哪条新记忆替代；
  - 用户是否明确确认；
  - 韩立为什么在本轮采用这条记忆。

  ### 大量数据的整理机制

  系统应定期做“记忆压缩”，但不能直接删除原始数据：

  50 条相似案例
      ↓
  提炼成 1 条稳定用户原则
      ↓
  保留 5 条代表案例
      ↓
  其他记录进入归档
      ↓
  原则仍链接到所有原始证据

  这样数据量可以持续增加，而每次推理使用的上下文仍然很小。

  ### AI Desktop 当前基础
  现有系统已经有：

  - SQLite 事件和会话记忆；
  - Conversation Topic；
  - Evolution Source Snapshot；
  - 用户意图与审批记录；
  - 规则包和 developer instructions；
  - 独立的韩立、南宫婉 Codex 会话。

  因此技术底座已经具备一部分，但还需要补齐：

  - 用户决策记忆模型；
  - 混合检索和重排；
  - 新旧记忆替代关系；
  - 记忆冲突检测；
  - 自动压缩与归档；
  - 韩立影子学习；
  - 提问预测准确率测试；
  - 用户纠正后立即更新的反馈闭环。

  结论是：韩立不会因为数据多必然忘记。只要把 Sol 当作推理引擎、把数据库当作长期记忆、把规则引擎当作不可越过的底线，就可
  以让韩立处理不断增长的历史，同时保持可追溯和可纠正。

当前实现会读取全部南宫婉和 Codex 会话原文，但直接一次性发送给韩立。对话库变大后会遇到上下文过长、处理中断和重复发问问题。

  下一阶段应实现：

  1. 按完整会话分组读取，绝不拆成 FTS 片段。
  2. 韩立分批综合每组会话，保存每批原始来源和阶段总结。
  3. 再综合各批结果，生成首个发问计划。
  4. 每轮记录 待提问 → 已提问 → 已回答 → 已判断 状态。
  5. 应用崩溃或重启后从最后一个状态继续，不能重复发问。
  6. 每次模型调用增加幂等键，避免同一轮产生两条问题或两个专题。
  7. 记录模型、会话ID、调用时间、失败、重试和原始返回。
  8. 专题确立时把所有批次依据和研讨轮次一起关联进专题档案。

  之后再做第二阶段：

  - 补齐任务命令、文件差异、截图、测试产物、发布版本和重启恢复点的专题关联。
  - 完善专题档案页的阶段导航、筛选和原始记录展开。
  - 增加专题暂停、恢复、人工接管和失败重试入口。

  优先级建议：

  可扩展的对话库综合
  → 可恢复的韩立研讨调度
  → 执行原数据完整关联
  → 专题档案页面增强

  这是继续写代码时最关键的一步。它完成后，自动演化才不会只在少量会话下工作。由于这是新的独立开发阶段，开始实施时需要再发送独立的 1。
