修改代码的硬性要求
每次修改前必须先检查结构，再决定如何修改：
1. 查清入口、完整调用链、状态所有者、重复实现和现有兼容路径。
2. 判断问题是否来自职责混乱、状态多源、模块耦合、生命周期分散或旧逻辑残留。
3. 如果是结构问题，先重构成高内聚、低耦合、单一职责和单一权威状态，再修复表面问题。
4. 代码组织必须符合新手的阅读顺序：入口清晰、命名直接、状态流向可追踪、函数职责单一。
5. 基础环境准备、恢复和重启生命周期应集中在明确的统一入口中，避免散落在多个条件分支里。
修复时必须退役旧代码：
- 删除已经替代的旧实现、旧入口、旧调用点和无调用代码；
- 删除旧兼容名称、兼容名单、例外桥接、回退分支和重复状态来源；
- 删除只服务于退役行为的测试和注册项；
- 修改后检查引用、导入、注册和测试，确认没有剩余调用者；
- 不允许新旧路径并存；
- 不允许用临时补丁、扩大条件分支或保留“以后可能有用”的旧代码防止复发。
复发应由清晰结构、权威状态、真实测试和验收规则防止，而不是依靠兼容旧代码。
