# 异常日志与国际化方案

## 1. 背景

当前问题有三层：

1. 代码里大量直接 `throw new IllegalArgumentException(...)`
2. 控制台只看到简单异常文本，排查时很难快速知道：
   - 哪个类
   - 哪个方法
   - 哪一行
   - 是系统异常还是业务异常
3. 异常信息目前基本写死，无法按中文、日文、英文等语言切换输出

参考 `C:\xsd-fts\src\main\resources\log4j.properties` 可以看出，它已经尝试输出：

- 行号
- 方法名
- 文件名

但仍然不够，缺少：

- 统一异常分类
- 统一异常编码
- 完整堆栈
- 国际化消息解析
- 控制层统一返回
- 日志文件与接口返回分离

本方案目标是把 SELPLAT 的异常输出升级为：

- 日志里有完整排障信息
- 接口返回有统一业务语义
- 文案支持中文 / 日文 / 英文切换
- 系统异常和业务异常都能统一收口

## 2. 现状判断

结合当前 SELPLAT 代码，现状如下：

1. `apps/uniauth/backend` 目前没有统一的 `@ControllerAdvice`
2. `shared/backend/common-db` 和 `apps/uniauth/backend` 内已经出现大量 `IllegalArgumentException`
3. 当前异常消息有中文，也有英文，例如：
   - `metadataReader must not be null`
   - `不支持的数据库产品类型: ...`
4. 当前没有看到统一 `MessageSource`、`messages_zh_CN.properties`、`messages_ja.properties`
5. 当前也没有统一的异常编码体系

结论：

- 现在是“代码直接抛异常 + 默认控制台/默认 Spring 异常输出”
- 适合尽快升级成“统一异常模型 + 统一日志 + 统一国际化消息”

## 3. 总体原则

### 3.1 日志和接口返回分离

必须区分两件事：

1. 日志内容
   - 面向开发、测试、运维
   - 要尽可能完整
   - 必须包含堆栈和定位信息

2. 接口返回内容
   - 面向前端或调用方
   - 要结构稳定
   - 要按语言返回可读消息

不能把“日志里详细异常”直接原样暴露给前端。

### 3.2 业务异常和系统异常分层

异常至少分两类：

1. 业务异常
   - 例如：`id 不能为空`
   - 例如：`loginName 已存在，不能重复`
   - 特点：是预期内的校验失败

2. 系统异常
   - 例如：数据库连接失败
   - 例如：元数据读取失败
   - 例如：时间类型转换失败
   - 特点：不是用户输入本身导致，而是系统执行链路出错

### 3.3 国际化不能写死在 throw 文本里

不要继续大量写：

```java
throw new IllegalArgumentException("metadataReader must not be null");
```

推荐改成：

```java
throw new BizException("COMMON_DB_VALIDATOR_METADATA_READER_NULL");
```

或：

```java
throw new BizException(CommonErrorCode.COMMON_DB_VALIDATOR_METADATA_READER_NULL);
```

消息文本由国际化资源文件决定。

## 4. 推荐落地结构

推荐把异常能力分三层：

### 4.1 common-core 放公共异常基础设施

建议目录：

`shared/backend/common-core/src/main/java/com/sp/selplat/common/exception`

建议类：

- `BizException`
- `SystemException`
- `ErrorCode`
- `CommonErrorCode`
- `GlobalExceptionHandler`
- `ExceptionLogSupport`
- `LocaleMessageSupport`

### 4.2 resources 放国际化消息文件

建议目录：

`apps/uniauth/backend/src/main/resources/i18n`

建议文件：

- `messages_zh_CN.properties`
- `messages_ja.properties`
- `messages_en.properties`

### 4.3 日志配置统一放 Spring Boot 当前主链路

如果 SELPLAT 后续继续走 Spring Boot 默认日志体系，推荐优先使用：

- `logback-spring.xml`

不建议新模块继续扩散老式 `log4j.properties`。

原因：

- Spring Boot 默认和 Logback 集成更顺
- MDC、异常堆栈、模式化输出更容易统一
- 后续国际化和 traceId 扩展也更方便

如果必须兼容旧工程的 Log4j 风格，也建议只把输出模式参考保留，不继续沿用旧式异常处理方式。

## 5. 异常模型设计

### 5.1 业务异常

建议定义：

```java
public class BizException extends RuntimeException
```

建议字段：

- `code`
- `messageKey`
- `messageArgs`

说明：

- `code` 用于稳定识别异常类型
- `messageKey` 用于国际化资源查找
- `messageArgs` 用于拼动态参数

示例：

- `USER_ID_REQUIRED`
- `USER_LOGIN_NAME_DUPLICATE`
- `COMMON_DB_QUERY_TABLE_NOT_FOUND`
- `COMMON_DB_METADATA_READER_NULL`

### 5.2 系统异常

建议定义：

```java
public class SystemException extends RuntimeException
```

建议字段：

- `code`
- `messageKey`
- `messageArgs`
- `cause`

示例：

- `SYSTEM_DATABASE_ACCESS_ERROR`
- `SYSTEM_METADATA_READ_ERROR`
- `SYSTEM_LOCAL_DATE_TIME_CONVERT_ERROR`

### 5.3 不再直接大面积抛 IllegalArgumentException

约束建议：

1. 业务输入校验错误：
   - 抛 `BizException`

2. 底层系统执行失败：
   - 抛 `SystemException`

3. 只有极小范围内部工具方法，且不会穿透到业务层时，才允许保留少量 `IllegalArgumentException`

但最终进入控制层前，也要被统一转换。

## 6. 国际化设计

### 6.1 消息资源文件

建议示例：

`messages_zh_CN.properties`

```properties
USER_ID_REQUIRED=用户ID不能为空
USER_LOGIN_NAME_DUPLICATE=登录名已存在，不能重复
COMMON_DB_VALIDATOR_METADATA_READER_NULL=通用查询校验器初始化失败：元数据读取器不能为空
SYSTEM_DATABASE_ACCESS_ERROR=系统数据库访问失败
SYSTEM_LOCAL_DATE_TIME_CONVERT_ERROR=系统时间字段转换失败
```

`messages_ja.properties`

```properties
USER_ID_REQUIRED=ユーザーIDは必須です
USER_LOGIN_NAME_DUPLICATE=ログイン名は既に存在します
COMMON_DB_VALIDATOR_METADATA_READER_NULL=共通クエリ検証器の初期化に失敗しました。メタデータリーダーは必須です
SYSTEM_DATABASE_ACCESS_ERROR=システムのデータベースアクセスに失敗しました
SYSTEM_LOCAL_DATE_TIME_CONVERT_ERROR=システムの日時変換に失敗しました
```

`messages_en.properties`

```properties
USER_ID_REQUIRED=User id is required
USER_LOGIN_NAME_DUPLICATE=Login name already exists
COMMON_DB_VALIDATOR_METADATA_READER_NULL=Common query validator initialization failed: metadata reader is required
SYSTEM_DATABASE_ACCESS_ERROR=System database access failed
SYSTEM_LOCAL_DATE_TIME_CONVERT_ERROR=System date-time conversion failed
```

### 6.2 语言选择来源

推荐优先级：

1. 请求头 `Accept-Language`
2. 用户资料中的 `locale`
3. 系统默认语言

对于 `uniauth`，当前实体里已经有 `locale` 字段，可以作为用户登录后场景的语言来源。

### 6.3 输出哪个语言

规则建议：

1. 接口请求带 `Accept-Language=zh-CN`
   - 返回中文

2. 接口请求带 `Accept-Language=ja`
   - 返回日文

3. 接口请求没带语言
   - 默认中文或系统配置默认语言

## 7. 日志方案设计

### 7.1 日志必须包含的内容

每条异常日志至少应包含：

- 时间
- 日志级别
- traceId
- 线程名
- 类名
- 方法名
- 行号
- 异常编码
- 国际化消息 key
- 当前语言
- 业务可读消息
- 原始技术异常消息
- 完整堆栈

### 7.2 推荐日志格式

推荐模式里包含：

- `%d`
- `%level`
- `%thread`
- `%logger`
- `%method`
- `%line`
- `%X{traceId}`

示例效果：

```text
2026-06-18 22:15:10 ERROR [http-nio-8080-exec-3] [traceId=abc123]
com.sp.selplat.common.db.query.DefaultCommonQueryValidator.validate:28
code=COMMON_DB_VALIDATOR_METADATA_READER_NULL
locale=zh-CN
message=通用查询校验器初始化失败：元数据读取器不能为空
technicalMessage=metadataReader must not be null
stackTrace=...
```

### 7.3 日志文件分离

建议至少分：

1. `application-info.log`
2. `application-error.log`

后续如有需要再拆：

3. `biz-error.log`
4. `sql-error.log`

### 7.4 SELPLAT 当前工程的日志落点要求

对于当前 `uniauth` 后端，异常日志输出必须按工程边界单独落盘，不能和其他工程混在一起。

当前工程边界：

- `C:\opt\workspace\SELPLAT\apps\uniauth`

推荐日志目录：

- `C:\opt\workspace\SELPLAT\apps\uniauth\log`

推荐文件命名：

1. `application_info_yyyy-MM-dd.log`
2. `application_error_yyyy-MM-dd.log`
3. `biz_error_yyyy-MM-dd.log`
4. `system_error_yyyy-MM-dd.log`

例如：

- `application_error_2026-06-18.log`
- `biz_error_2026-06-18.log`

这样做的目的：

1. 按工程隔离日志，避免后续多模块日志混写后难以归属
2. 文件名直接带日期，便于按天归档、检索和清理
3. 统一符合“日志文件名后面加下划线时间年月日便于归类”的要求

如果后续 `SELPLAT` 下还有：

- `apps/xxx`
- `apps/yyy`

则每个工程都建议按同样规则独立输出到各自工程目录下的 `log` 目录，不共用一个总日志文件。

### 7.5 参考旧 log4j.properties 的保留点

`xsd-fts` 现有写法可保留的思路只有一条：

- 日志格式里显式输出 `%L %M %F`

但不足点要补齐：

- 必须记录完整异常堆栈
- 必须增加 traceId
- 必须增加异常编码
- 必须把业务异常和系统异常区分

## 8. 控制层统一异常返回

### 8.1 全局异常处理器

建议：

```java
@RestControllerAdvice
public class GlobalExceptionHandler
```

分三类处理：

1. `BizException`
2. `SystemException`
3. `Exception`

### 8.2 返回结构建议

统一响应结构建议至少包含：

- `success`
- `code`
- `message`
- `locale`
- `traceId`
- `timestamp`

示例：

```json
{
  "success": false,
  "code": "USER_ID_REQUIRED",
  "message": "用户ID不能为空",
  "locale": "zh-CN",
  "traceId": "abc123",
  "timestamp": "2026-06-18T22:15:10"
}
```

### 8.3 控制层日志策略

建议：

1. `BizException`
   - 记 `WARN`
   - 不算系统故障

2. `SystemException`
   - 记 `ERROR`
   - 带完整堆栈

3. `Exception`
   - 记 `ERROR`
   - 统一兜底成系统未知异常

## 9. common-db 场景下的具体改造建议

### 9.1 当前问题点

当前 `common-db` 里有很多：

- `throw new IllegalArgumentException("metadataReader must not be null");`
- `throw new IllegalArgumentException("table not found: ...");`
- `throw new IllegalArgumentException("unsupported databaseType: ...");`

这些问题在于：

1. 消息未国际化
2. 没有稳定错误码
3. 控制层无法区分是业务问题还是系统问题
4. 日志里虽然可能带堆栈，但没有统一结构

### 9.2 推荐替换方式

#### 初始化参数缺失

例如：

- `metadataReader must not be null`
- `validator must not be null`
- `dialectFactory must not be null`

建议改成：

- `BizException(COMMON_DB_VALIDATOR_METADATA_READER_NULL)`
- `BizException(COMMON_DB_SQL_BUILDER_VALIDATOR_NULL)`
- `BizException(COMMON_DB_SQL_BUILDER_DIALECT_FACTORY_NULL)`

#### 真实系统执行失败

例如：

- 元数据读取失败
- JDBC 执行失败
- 时间转换失败

建议改成：

- `SystemException(SYSTEM_METADATA_READ_ERROR, cause)`
- `SystemException(SYSTEM_DATABASE_ACCESS_ERROR, cause)`
- `SystemException(SYSTEM_LOCAL_DATE_TIME_CONVERT_ERROR, cause)`

### 9.3 示例分类

#### 业务异常

- 表名为空
- 字段名为空
- 字段不存在
- 排序字段不存在
- 登录名重复
- 用户 ID 为空

#### 系统异常

- 获取 JDBC 连接失败
- 元数据读取失败
- SQL 执行失败
- 时间类型转换失败
- 当前数据库产品类型无法识别

备注：

数据库产品类型无法识别，通常更接近系统配置问题，建议归到系统异常，而不是业务异常。

## 10. 推荐实现顺序

### 第一阶段

先落基础设施：

1. `ErrorCode`
2. `BizException`
3. `SystemException`
4. `GlobalExceptionHandler`
5. `MessageSource` 配置
6. `messages_zh_CN.properties`
7. `messages_ja.properties`
8. `messages_en.properties`

### 第二阶段

改造 `uniauth`：

1. `UniauthUserServiceImpl`
2. `UniauthUserDaoImpl`
3. `common-db` 默认实现里的 `IllegalArgumentException`

### 第三阶段

补日志增强：

1. `traceId`
2. `logback-spring.xml`
3. 统一错误日志格式
4. 系统异常完整堆栈

## 11. 推荐技术路线

### 11.1 日志框架

推荐：

- `SLF4J + Logback`

不建议在 SELPLAT 新链路里继续扩散老式 `log4j.properties` 主导设计。

### 11.2 国际化

推荐：

- Spring `MessageSource`
- `LocaleContextHolder`

### 11.3 异常传播

推荐：

- 业务层 / DAO 层抛业务异常或系统异常
- 控制层不手工 `try/catch`
- 全交给 `@RestControllerAdvice`

## 12. 最终结论

结论一句话：

- 不能再依赖“直接 `throw IllegalArgumentException + 控制台打印`”这种方式排查问题
- 应升级成“统一异常类 + 统一错误码 + 统一国际化消息 + 统一全局异常处理 + 统一日志格式”

最关键的落地要求是：

1. 日志里必须能看到：
   - 类
   - 方法
   - 行号
   - traceId
   - 异常编码
   - 当前语言
   - 中文/日文/英文消息
   - 原始技术异常
   - 完整堆栈

2. 接口返回里必须能看到：
   - 稳定错误码
   - 当前语言消息
   - traceId

3. `common-db` 和 `uniauth` 里的直接字符串异常，后续都应该逐步替换成错误码 + 国际化消息模型

## 13. 对 SELPLAT 的直接建议

如果下一步要开始落代码，建议按这个顺序：

1. 先在 `common-core` 落异常基础设施
2. 再给 `uniauth` 落 `GlobalExceptionHandler`
3. 再把 `UniauthUserServiceImpl` 和 `UniauthUserDaoImpl` 的异常改造掉
4. 最后统一替换 `common-db` 里的直接 `IllegalArgumentException`

这样风险最小，也最容易逐步验证。
