# 新建表结构书写规范文档

## 1. 文档目的

本文档用于统一当前工程中新建业务表时的 SQL 书写方式，供后续新增 `schema-xxx.sql`、`data-xxx.sql` 时直接参照。

本规范以当前 `apps/uniauth/backend/src/main/resources/schema-uniauth.sql` 的实际落地风格为基础，总结出统一要求，避免后续不同模块各写各的，导致表名、字段名、注释和种子数据口径分裂。

## 2. 表名规则

### 2.1 表名必须使用驼峰命名

新表名统一使用驼峰风格，禁止再使用下划线表名。

正确示例：

- `UniauthUser`
- `UniauthTenant`
- `OrderMain`
- `SchoolCourse`

错误示例：

- `uniauth_user`
- `ua_tenant`
- `order_main`

### 2.2 表名要能直接表达业务含义

表名应尽量让人一眼看出所属模块和业务对象，不要过度缩写。

建议：

- 模块前缀 + 业务对象
- 保持和 Java 领域对象命名方向一致

例如：

- 统一认证租户表：`UniauthTenant`
- 统一认证角色表：`UniauthRole`
- 教务课程表：`EduCourse`

## 3. 字段命名规则

### 3.1 字段名必须使用驼峰命名

列名统一使用驼峰，禁止下划线字段。

正确示例：

- `tenantId`
- `loginUserId`
- `displayName`
- `createdAt`
- `updatedAt`

错误示例：

- `tenant_id`
- `login_user_id`
- `display_name`
- `created_at`

### 3.2 字段名应与 Java 实体字段口径一致

如果 Java 实体里字段叫 `tenantId`，数据库列也应叫 `tenantId`，不要一边驼峰、一边下划线。

这样做的目的：

- 减少映射配置转换成本
- 降低 DAO、Mapper、通用查询层的理解负担
- 保持表结构、实体、返回对象命名一致

## 4. 公共字段规则

### 4.1 所有业务表必须包含 `Domain` 公共字段

当前公共领域基类 `Domain.java` 已统一沉淀以下字段，新建业务表必须补齐：

- `id`
- `tenantId`
- `lastOperateUserId`
- `sortnum`
- `status`
- `createdAt`
- `updatedAt`

### 4.2 公共字段建议写法

推荐按以下顺序书写公共字段：

```sql
id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
tenantId BIGINT NOT NULL,
lastOperateUserId BIGINT NOT NULL,
sortnum DECIMAL(10, 2) NOT NULL DEFAULT 0.00,
status INTEGER NOT NULL DEFAULT 1,
createdAt TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
updatedAt TIMESTAMP DEFAULT CURRENT_TIMESTAMP
```

字段含义约定：

- `id`：记录主键标识
- `tenantId`：数据所属租户标识
- `lastOperateUserId`：最近一次操作该数据的用户标识
- `sortnum`：业务排序值
- `status`：逻辑状态，默认 `1` 为有效
- `createdAt`：创建时间
- `updatedAt`：最后更新时间

### 4.3 `tenantId` 和 `lastOperateUserId` 不能缺

只要是当前工程中的业务表，就必须带：

- `tenantId`
- `lastOperateUserId`

不能因为某张表“看起来是基础表”就省掉这两个字段。

### 4.4 `lastOperateUserId` 的语义固定为最近操作用户

`lastOperateUserId` 只用于保存主表当前这一条数据“最近一次是谁改的”。

它不是登录态变量，也不是完整历史审计表。

如果后续需要保留每一次操作记录，应单独建设历史表，在历史表中记录具体操作员、操作时间和动作类型，不要把主表字段滥用成全量审计流水。

## 5. 建表语句规则

### 5.1 使用 `CREATE TABLE IF NOT EXISTS`

新表统一使用：

```sql
CREATE TABLE IF NOT EXISTS 表名 (
    ...
);
```

这样便于本地初始化时反复执行脚本，不因为重复建表直接失败。

### 5.2 主键沿用当前脚本风格

主键默认按当前脚本风格使用：

```sql
id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
```

如果后续改为统一号段主键方案，再单独按公共规范调整；在正式切换前，不要每张表自己发明新的主键写法。

### 5.3 字段顺序保持稳定

建议字段按以下顺序书写：

1. 主键字段
2. 公共租户与审计字段中的前半段
3. 业务核心字段
4. 业务补充字段
5. 排序、状态和时间字段

参考顺序：

```sql
id
tenantId
lastOperateUserId
业务主字段
业务描述字段
业务状态字段
sortnum
status
createdAt
updatedAt
```

## 6. 注释规则

### 6.1 行注释用于阅读

字段上方保留 `--` 注释，便于开发直接阅读 SQL 时理解字段业务含义。

示例：

```sql
-- roleName 保存角色展示名称，便于后台列表和权限配置页面直接显示。
roleName VARCHAR(100) NOT NULL,
```

### 6.2 数据库注释必须真正落库

仅有 `--` 注释不够，因为数据库执行后不会保留。

所以每张表创建后，必须继续补：

- `COMMENT ON TABLE`
- `COMMENT ON COLUMN`

示例：

```sql
COMMENT ON TABLE DemoRole IS '系统角色主表';
COMMENT ON COLUMN DemoRole.id IS '角色记录标识';
COMMENT ON COLUMN DemoRole.tenantId IS '数据所属租户标识';
COMMENT ON COLUMN DemoRole.lastOperateUserId IS '最近操作用户标识';
COMMENT ON COLUMN DemoRole.roleName IS '角色展示名称';
```

### 6.3 注释内容要简短明确

注释不要写成空话，也不要机械重复字段名。

推荐写法：

- 说明该字段在业务里的用途
- 尽量一句话讲清
- 保持短、准、稳定

建议：

- `角色展示名称`
- `最近维护登录用户标识`
- `业务排序值`
- `数据更新时间`

不建议：

- `角色名称字段`
- `租户ID`
- `这个字段表示更新时间`

## 7. 种子数据规则

### 7.1 需要初始化数据时，同步维护 `data-xxx.sql`

如果该表在本地最小运行场景下需要默认数据，就要同步写入对应 `data-xxx.sql`。

### 7.2 种子数据沿用 `MERGE INTO`

当前脚本统一使用：

```sql
MERGE INTO 表名 (字段列表)
KEY(id)
VALUES (...);
```

这样便于重复初始化，不会因为主键已存在而直接插入失败。

### 7.3 种子数据字段清单必须和表结构同步

只要表结构加了：

- `tenantId`
- `lastOperateUserId`
- `sortnum`
- `status`

种子数据就要同步补齐对应列和值，不能只改 `schema` 不改 `data`。

## 8. 推荐书写模板

下面给一个可直接套用的新表示例，注意这是模板，不是要求照搬字段内容。

```sql
-- DemoRole 用于保存某业务域下的角色主数据。
CREATE TABLE IF NOT EXISTS DemoRole (
    -- id 作为角色记录标识，供权限关联和详情维护稳定引用。
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    -- tenantId 表达当前角色归属的租户边界。
    tenantId BIGINT NOT NULL,
    -- lastOperateUserId 记录最近操作该角色数据的用户标识。
    lastOperateUserId BIGINT NOT NULL,
    -- roleCode 保存角色业务编码，便于外部识别和程序内稳定引用。
    roleCode VARCHAR(50) NOT NULL UNIQUE,
    -- roleName 保存角色展示名称，便于列表和授权页面直接显示。
    roleName VARCHAR(100) NOT NULL,
    -- roleType 保存角色分类，便于区分系统角色和租户角色。
    roleType VARCHAR(30) NOT NULL,
    -- remark 保存角色补充说明，便于后台维护时记录用途。
    remark VARCHAR(255),
    -- sortnum 保存角色展示顺序，便于页面按业务顺序输出。
    sortnum DECIMAL(10, 2) NOT NULL DEFAULT 0.00,
    -- status 保存逻辑状态，默认 1 表示有效。
    status INTEGER NOT NULL DEFAULT 1,
    -- createdAt 记录角色创建时间。
    createdAt TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    -- updatedAt 记录角色最后更新时间。
    updatedAt TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

COMMENT ON TABLE DemoRole IS '系统角色主表';
COMMENT ON COLUMN DemoRole.id IS '角色记录标识';
COMMENT ON COLUMN DemoRole.tenantId IS '数据所属租户标识';
COMMENT ON COLUMN DemoRole.lastOperateUserId IS '最近操作用户标识';
COMMENT ON COLUMN DemoRole.roleCode IS '角色业务编码';
COMMENT ON COLUMN DemoRole.roleName IS '角色展示名称';
COMMENT ON COLUMN DemoRole.roleType IS '角色分类';
COMMENT ON COLUMN DemoRole.remark IS '角色补充说明';
COMMENT ON COLUMN DemoRole.sortnum IS '业务排序值';
COMMENT ON COLUMN DemoRole.status IS '逻辑状态标记';
COMMENT ON COLUMN DemoRole.createdAt IS '数据创建时间';
COMMENT ON COLUMN DemoRole.updatedAt IS '数据更新时间';
```

对应种子数据示例：

```sql
MERGE INTO DemoRole (id, tenantId, lastOperateUserId, roleCode, roleName, roleType, remark, sortnum, status)
KEY(id)
VALUES
  (1, 1, 1, 'SYS_ADMIN', '系统管理员', 'SYSTEM', '负责平台级权限维护', 10.00, 1);
```

## 9. 新建表时的自检清单

建完一张新表后，至少自检以下内容：

- 表名是否为驼峰
- 字段名是否全部为驼峰
- 是否补齐 `Domain` 公共字段
- 是否包含 `tenantId` 和 `lastOperateUserId`
- 是否保留了 `--` 阅读注释
- 是否补了 `COMMENT ON TABLE / COLUMN`
- 是否需要同步写 `data-xxx.sql`
- 种子数据列清单是否与表结构一致

## 10. 最终要求

后续新增业务表时，统一按本规范执行：

- 表名驼峰
- 字段名驼峰
- 公共字段完整
- 注释可阅读且可落库
- 种子数据与表结构同步

如果出现特殊场景确实不能遵守本规范，必须先说明原因，再决定是否单独放宽。
