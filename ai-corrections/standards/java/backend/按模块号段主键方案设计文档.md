# 按模块号段主键方案设计

## 1. 目标

本文档用于沉淀“按模块分段申请主键号段，在 JVM 内存中高性能发号，并由数据库统一仲裁多进程号段分配”的设计方案。

适用目标：

- 业务主键需要使用 `Long` 型数值主键。
- 主键只要求全局唯一，不要求严格连续。
- 允许因服务重启、发布或实例切换导致部分未使用号段废弃。
- 需要比“每次插入都实时查表取号”更高的新增性能。

不适用目标：

- 要求主键绝对连续。
- 要求跨系统无任何跳号。
- 更适合直接使用数据库自增主键的普通单表新增场景。

## 2. 核心思路

本方案不让每次新增都访问数据库取一个主键，而是按模块一次性向数据库申请一整段主键号段，再由当前 JVM 在内存中逐个发放。

例如 `UniauthUser` 模块：

- 模块编码：`UniauthUserId`
- 数据库当前可分配起点：`100000`
- 单次申请步长：`1000`

则某个实例本次申请到的号段为：

- `100000 ~ 100999`

该实例后续新增 `UniauthUser` 时，直接在内存中递增发号，不再逐条访问数据库。

号段用尽后，再次向数据库申请下一段。

## 3. 为什么多进程下仍然可以统一

多进程场景下，不要求所有进程共享同一个“当前号”，而是要求所有进程申请到的号段互不重叠。

例如：

- 实例 A 申请到 `100000 ~ 100999`
- 实例 B 申请到 `101000 ~ 101999`
- 实例 C 申请到 `102000 ~ 102999`

只要“申请号段”这一步由数据库统一仲裁，就不会出现重复主键。

因此，多进程统一性的关键不在“本地发号”，而在“数据库原子分段”。

## 4. 方案代价

本方案天然存在以下代价：

- 主键不连续。
- 实例重启时未使用完的号段会废弃。
- 步长越大，浪费号段的概率越高。
- 需要额外维护一张号段配置表和一套发号公共组件。

这些代价属于方案本身的正常特征，不是实现缺陷。

## 5. 建议表设计

建议新增号段控制表：`CommonSequenceSegment`

```sql
CREATE TABLE IF NOT EXISTS CommonSequenceSegment (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tenantId BIGINT NOT NULL,
    lastOperateUserId BIGINT NOT NULL,
    seqCode VARCHAR(64) NOT NULL UNIQUE,
    seqName VARCHAR(128) NOT NULL,
    nextStartId BIGINT NOT NULL,
    stepSize INT NOT NULL,
    versionNo INT NOT NULL DEFAULT 0,
    remark VARCHAR(255),
    sortnum DECIMAL(10, 2) NOT NULL DEFAULT 0.00,
    status INTEGER NOT NULL DEFAULT 1,
    createdAt TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updatedAt TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

字段说明：

- `id`：号段记录主键。
- `tenantId`：该号段配置归属的租户标识。
- `lastOperateUserId`：最近一次维护号段配置的用户标识。
- `seqCode`：号段编码，建议稳定命名，例如 `UniauthUserId`。
- `seqName`：号段中文名称，便于运维和排查。
- `nextStartId`：下一次申请时可分配的起始主键。
- `stepSize`：每次申请的号段大小。
- `versionNo`：乐观锁版本号，用于并发抢号段。
- `remark`：备注说明。
- `sortnum`：配置排序值，便于后台配置列表稳定展示。
- `status`：逻辑状态，统一承担有效/删除/停用语义，不再额外增加重复状态字段。
- `createdAt` / `updatedAt`：建档与更新时间。

## 6. 初始化示例

以 `UniauthUser` 为例：

```sql
INSERT INTO CommonSequenceSegment (
    tenantId,
    lastOperateUserId,
    seqCode,
    seqName,
    nextStartId,
    stepSize,
    versionNo,
    remark,
    sortnum,
    status
) VALUES (
    1,
    1,
    'UniauthUserId',
    '统一认证用户主键号段',
    100000,
    1000,
    0,
    '按模块缓存号段生成主键',
    10.00,
    1
);
```

含义如下：

- 首次可分配起始值为 `100000`
- 每次申请一段 `1000` 个主键

第一次申请成功后：

- 当前实例拿到 `100000 ~ 100999`
- 表中 `nextStartId` 更新为 `101000`

## 7. 多进程统一仲裁方案

### 7.1 推荐方案：乐观锁抢号段

步骤如下：

1. 查询当前号段记录。
2. 读取 `nextStartId`、`stepSize`、`versionNo`。
3. 以 `versionNo` 为条件更新 `nextStartId`。
4. 更新成功则说明当前实例抢号段成功。
5. 更新失败则说明有其他实例先抢到，当前实例重试。

查询示例：

```sql
SELECT id, tenantId, seqCode, nextStartId, stepSize, versionNo
FROM CommonSequenceSegment
WHERE seqCode = 'UniauthUserId'
  AND status = 1;
```

更新示例：

```sql
UPDATE CommonSequenceSegment
SET nextStartId = nextStartId + stepSize,
    versionNo = versionNo + 1,
    lastOperateUserId = 1,
    updatedAt = CURRENT_TIMESTAMP
WHERE seqCode = 'UniauthUserId'
  AND versionNo = 3
  AND status = 1;
```

若本次更新成功，且更新前：

- `nextStartId = 100000`
- `stepSize = 1000`

则当前实例拿到的可用区间为：

- `100000 ~ 100999`

数据库中新的 `nextStartId` 变为：

- `101000`

### 7.2 可选方案：悲观锁抢号段

若需要更直观、更易理解的实现，也可以使用数据库悲观锁。

查询示例：

```sql
SELECT nextStartId, stepSize
FROM CommonSequenceSegment
WHERE seqCode = 'UniauthUserId'
  AND status = 1
FOR UPDATE;
```

随后在同一事务中更新：

```sql
UPDATE CommonSequenceSegment
SET nextStartId = nextStartId + stepSize,
    lastOperateUserId = 1,
    updatedAt = CURRENT_TIMESTAMP
WHERE seqCode = 'UniauthUserId'
  AND status = 1;
```

该方案实现更简单，但高并发下锁等待更明显。

### 7.3 方案选择建议

- 实例数少、并发量一般：优先用悲观锁，落地简单。
- 实例数多、并发高：优先用乐观锁，吞吐更好。

若项目后续要做公共能力，建议优先实现乐观锁方案。

## 8. JVM 内存发号模型

数据库只负责分配整段号段，真正逐个发号在 JVM 内存完成。

建议定义号段对象：

```java
public class SequenceRange {

    private long currentValue;

    private long maxValue;

    public synchronized long nextId() {
        if (currentValue > maxValue) {
            return -1L;
        }
        return currentValue++;
    }
}
```

业务含义如下：

- `currentValue`：当前 JVM 下一次要发出的主键。
- `maxValue`：当前号段可发放的最大主键。
- `nextId()`：当前段未用完则直接发号；当前段已耗尽则返回失败标记，触发重新申请新号段。

## 9. 公共服务分层建议

### 9.1 `common-db` 层职责

当前 `common-db` 更适合承接“数据库取号段”能力，不适合直接承接 JVM 缓存发号能力。

建议放入：

- `SequenceSegmentDao`
- `SequenceSegmentDaoImpl`
- `SequenceSegment` 实体或配置对象

职责如下：

- 查询指定 `seqCode` 的号段配置。
- 通过乐观锁或悲观锁申请下一段号段。
- 向上层返回“本次成功申请到的起始值和结束值”。

### 9.2 `common-service` 层职责

建议把真正的发号门面放在 `common-service`。

建议接口：

```java
public interface SequenceGenerator {

    Long nextId(String seqCode);
}
```

建议实现：

- `SequenceGeneratorImpl`
- 内部维护 `ConcurrentHashMap<String, SequenceRange>`

职责如下：

- 先从本地缓存读取当前模块号段。
- 号段未用尽时直接在内存中返回主键。
- 号段已用尽时通过 `common-db` 重新申请新号段。
- 把新号段放回缓存后继续发号。

### 9.3 为什么不建议把缓存发号放进 `common-db`

原因如下：

- `common-db` 当前定位偏数据库访问与查询能力。
- 本地号段缓存属于内存状态管理，不是纯数据库操作。
- 并发控制、缓存续段、JVM 生命周期更接近服务层职责。

因此建议：

- `common-db` 负责“数据库统一仲裁”
- `common-service` 负责“JVM 本地高性能发号”

## 10. `UniauthUser` 接入建议

建议给 `UniauthUser` 固定一个稳定模块编码：

```text
UniauthUserId
```

不建议直接使用 Java 类名 `UniauthUser` 作为最终数据库号段编码，原因如下：

- 后续类名重构会影响数据库配置语义。
- 下划线编码更稳定，也更符合数据库配置习惯。

业务使用方式建议如下：

```java
Long userId = sequenceGenerator.nextId("UniauthUserId");
entity.setId(userId);
uniauthUserDao.insert(entity);
```

这样业务层只关心“按模块获取主键”，不关心具体号段申请过程。

## 11. 异常与边界场景

需要明确处理以下场景：

### 11.1 号段不存在

若 `seqCode` 未配置，直接抛出业务异常，不允许静默创建。

原因：

- 主键规则属于显式运维配置。
- 静默自动建档容易造成不同环境口径不一致。

### 11.2 号段被停用

若 `status != 1`，直接拒绝发号并抛出异常。

### 11.3 乐观锁冲突

若更新条数为 `0`，说明本次抢号段失败，应进行有限重试。

建议：

- 最多重试 `3 ~ 5` 次
- 超过次数后抛出异常并记录日志

### 11.4 服务重启

服务重启后，当前 JVM 未使用完的号段会丢失。

这会导致主键跳号，但不会导致重复。

### 11.5 多实例部署

多实例部署不会破坏唯一性，前提是所有实例都通过同一张 `CommonSequenceSegment` 表申请号段。

## 12. 性能结论

与“每次插入都查一次主键表”相比，本方案优势如下：

- 大幅减少数据库访问次数。
- 主键生成延迟更低。
- 大部分新增只走内存发号，不再受数据库 RT 影响。
- 更适合批量新增和高频新增场景。

代价如下：

- 主键不连续。
- 会有跳号。
- 步长配置不合理时可能造成更多废号。

因此，本方案本质上是“用少量主键连续性损失换取更高的系统吞吐”。

## 13. 步长建议

建议根据模块写入量设置 `stepSize`：

- 写入量低的模块：`100`
- 写入量中的模块：`500`
- 写入量高的模块：`1000` 或更高

初始建议：

- `UniauthUser`：先从 `1000` 开始

后续按实际写入量调整，不要一开始把步长设得过大。

## 14. 最终结论

对于当前工程，如果坚持使用“按模块取主键”的方式，推荐采用以下落地结构：

- 数据库：`CommonSequenceSegment`
- `common-db`：实现号段申请 DAO
- `common-service`：实现本地缓存发号 `SequenceGenerator`
- 业务模块：通过 `sequenceGenerator.nextId("UniauthUserId")` 获取主键

多进程统一性不依赖共享内存，而依赖数据库对“号段申请”这一步的原子仲裁。

因此：

- 本地发号可以分散
- 号段分配必须集中

只要数据库抢号段实现正确，多进程、多实例下就不会出现主键重复。

## 16. 当前实现边界

当前已经完成的是“公共 sequence 基础设施”落地，并未强行接入某个半成品业务新增入口。

原因如下：

- 当前 `uniauth` 模块已稳定落地的是 `store` 查询链路。
- 当前 `uniauth` 模块尚未形成完整的正式新增用户入口。
- 在没有完整新增接口、保存入参、DAO 持久化链路和联调路径前，先把公共号段能力落稳更合理。

## 17. 后续业务接入步骤

当后续某个业务模块正式新增保存入口时，建议按以下顺序接入：

1. 在业务 `service` 中注入 `SequenceGenerator`。
2. 在保存前调用 `sequenceGenerator.nextId("对应模块号段编码")`。
3. 把返回的主键写入实体或保存入参对象的 `id` 字段。
4. 再执行正式 `insert`。
5. 若该模块首次接入，需要先在 `CommonSequenceSegment` 中补齐对应 `seqCode` 种子配置。

以 `UniauthUser` 为例，后续接入时的调用方向应为：

```java
Long userId = sequenceGenerator.nextId("UniauthUserId");
entity.setId(userId);
uniauthUserDao.insert(...);
```
